MODULE 01
Prompt 工程
prompt_engineering · 输入侧的核心竞争力

📐 核心提示策略对比

策略原理适用场景注意事项
Zero-shot直接描述任务，无示例通用任务、快速验证依赖模型能力上限
Few-shot给 2~5 个输入输出示例格式敏感、分类、实体抽取示例质量 > 数量；格式必须一致
CoT在示例中展示推理过程数学推理、多步逻辑、代码生成简单任务反而降效；增加 token
Zero-shot CoT追加 "Let's think step by step"无标注数据时快速提升推理效果弱于有示例的 CoT
Self-Consistency多次采样 → 投票取多数有唯一正确答案的推理成本 = N × 单次；temperature > 0
Many-shot百级示例充满上下文长窗口模型 + 分类任务示例多样性比重复更重要
🧱 System Prompt 结构化设计
SYSTEM PROMPT TEMPLATE
# Role — 你是谁 你是一名专业的合同审查律师... # Context — 背景 用户将提供合同文本... # Instructions — 行为规则 1. 识别风险条款 2. 用中文回复 # Constraints — 禁止事项 不要给出法律建议 不要捏造条款 # Output Format 以 JSON 格式输出...
⚔️ Prompt 注入攻击与防御
  • Direct Injection — 用户输入覆盖系统指令
  • Indirect Injection — 文档/网页内嵌恶意指令（RAG 高危）
  • Jailbreak — 角色扮演、编码混淆绕过限制
防御手段
  • 输入过滤 + 异常结构检测
  • Sandwich Defense（前后重申规则）
  • 指令隔离标签 <user_input>
  • Guard Model（如 LlamaGuard）二次审核
  • RAG 场景：文档内容单独封装

🎯 输出格式控制 — JSON Mode vs Structured Output

JSON Mode

  • ✅ 强制输出合法 JSON 语法
  • ❌ 不保证字段名/类型/完整性
  • ❌ 需要 prompt 里说明字段
  • 适合简单场景快速使用

Structured Output (Schema 约束)

  • ✅ JSON Schema 约束字段名+类型
  • ✅ 必填字段有保证
  • ✅ 嵌套/枚举均支持
  • 生产环境首选
💡
面试考点：两者核心区别是 Schema 约束的强度。JSON Mode 只保证可解析，Structured Output 保证字段语义。生产代码必须做 validation + retry，不能假设输出一定合法。

MODULE 02
上下文工程
context_engineering · 管理模型的"记忆空间"
📌
核心命题：上下文窗口是有限的昂贵资源。上下文工程就是在有限 token 预算内，把最有价值的信息塞进去，同时管理好多轮对话、外部知识、工具结果之间的优先级。

Tool 执行结果

当前用户输入
Token 消耗从上到下叠加，总量受上下文窗口限制
📏 上下文长度管理策略
  • 滑动窗口 — 保留最近 N 轮对话，丢弃早期
  • 摘要压缩 — 用 LLM 将历史对话压缩为摘要
  • 分层存储 — 短期(原文) + 长期(向量/摘要)
  • Token 预算分配 — 为每个模块设上限
  • Prompt 压缩 — LLMLingua 动态删除冗余 token
🔖 上下文位置效应
⚠️
Lost in the Middle 效应：模型对上下文头部和尾部的内容记忆显著优于中间部分。
  • 关键指令 → 放在 System Prompt 或末尾
  • 重要文档 → 避免堆在中间
  • Reranker → 把最相关内容放首位
  • 实验验证：超过 16K 后中间遗忘显著
💾 多轮对话记忆类型

SummaryKV Store可配置

💰 Token 成本优化
  • Prompt Caching — 缓存静态 System Prompt（Anthropic 减 90% 输入成本）
  • Semantic Cache — 相似问题命中缓存回答
  • 模型路由 — 简单问题 → 小模型；复杂 → 大模型
  • LLMLingua — 对长文档做 token 压缩（可达 4x）
  • Streaming — 流式输出降低首字节延迟感知

MODULE 03
Harness 工程
llm_harness · 围绕模型调用的工程脚手架
📌
Harness 是指围绕 LLM 调用搭建的工程框架，包括输入预处理、调用管理、输出后处理、错误重试、可观测性等，本质是让 LLM 调用生产可用。

🏛️ Harness 全流程架构

01

输入预处理层

用户输入清洗 → 安全过滤 → Prompt 模板渲染 → Token 计数 → 超长截断/压缩

02

调用管理层

限流（Rate Limit）→ 重试（指数退避）→ 超时控制 → 多供应商路由（LiteLLM）→ Fallback 降级

03

输出后处理层

格式解析（JSON/Markdown）→ Schema 验证 → Hallucination 检测 → 内容安全过滤 → 结果缓存

04

可观测性层

Trace / Span 记录 → Token 用量统计 → 延迟监控 → 评估打分 → 版本化 Prompt 管理

🔄 重试与错误处理
PYTHON
async def call_with_retry(prompt, max_retries=3): for attempt in range(max_retries): try: result = await llm.call(prompt) # 验证输出格式 validate_schema(result) return result except RateLimitError: wait = 2 ** attempt # 指数退避 await asyncio.sleep(wait) except ValidationError: prompt = add_repair_hint(prompt) raise MaxRetriesExceeded()
  • JSON 解析失败 → 带错误信息重试
  • 429 限流 → 指数退避 + jitter
  • 超时 → Fallback 到备用模型
📊 可观测性工具链
工具核心功能
LangSmithTrace、评估、Prompt 版本管理
LangFuse开源、成本追踪、A/B 对比
Helicone代理层、token 统计、缓存
Phoenix (Arize)幻觉检测、嵌入可视化
✅
生产必备：每个 LLM 调用都应记录 input、output、latency、token_count、model_version
🌐 多供应商路由 (LiteLLM)
  • 统一接口调用 OpenAI / Anthropic / Gemini / 本地模型
  • 按成本/延迟/能力动态路由
  • 主供应商故障 → 自动 Fallback
  • 负载均衡：同一模型多 API Key 轮询
CONFIG

🛡️ 内容安全与 Guardrails
  • 输入侧 — 检测 PII、有害内容、注入攻击
  • 输出侧 — 事实核查、幻觉检测、合规过滤
  • NeMo Guardrails — 声明式规则引擎，可配置允许/拒绝话题
  • Guardrails AI — Schema 验证 + 自定义验证器

幻觉检测方法：RAG-Faithfulness（答案是否被文档支持）、Self-check（多次采样一致性）、外部事实核查 API

⚡ ReAct vs Plan-and-Execute
ReAct
  • • 思考与行动交替进行
  • • 实时感知反馈
  • • 适合动态、短任务
  • ⚠️ 步骤多时上下文膨胀
Plan & Execute
  • • 先生成完整计划
  • • 再逐步执行
  • • 适合复杂长任务
  • ⚠️ 计划难以动态调整
🕸️ 多 Agent 框架对比
框架模式特点
LangGraph有向图 DAG状态机，可循环，可视化强
AutoGen对话式多 AgentAgent 间互发消息协作
CrewAI角色分工高抽象，定义 Role/Task/Crew
OpenAI Swarm轻量切换Handoff 机制，极简
💾 Agent 记忆管理
  • Working Memory — 当前任务的中间状态（上下文内）
  • Episodic Memory — 历史任务执行记录（向量检索）
  • Semantic Memory — 领域知识库（RAG）
  • Procedural Memory — 技能/Workflow 定义
💡
记忆压缩策略：定期将 Working Memory 中已完成的步骤压缩为摘要，控制上下文增长。
🛡️ Agent 可靠性与安全
  • 步骤上限 — 设置 max_iterations 防止无限循环
  • 工具沙箱 — 代码执行在隔离容器（E2B/Docker）
  • 人工介入 — Human-in-the-loop 审批高风险操作
  • 权限最小化 — 工具只开放必要权限
  • 回滚机制 — 关键操作前创建检查点

MODULE 05
Function Calling / Tool Use
tool_use · 让模型操作外部世界

🔄 Function Calling 完整流程

1

定义工具 Schema

传入工具列表（名称、描述、参数 JSON Schema），描述越清晰，模型选择越准确

2

模型输出 Tool Call

模型决定调用哪个工具，输出 function_name + arguments（JSON），此时模型不执行，只生成调用意图

3

客户端执行工具

应用层解析 tool_call，调用真实函数/API，获取结果

4

结果回传给模型

将 tool_result 以 role:tool 的形式加入对话，模型根据结果生成最终回复

📝 工具定义最佳实践
JSON SCHEMA
{ "name": "search_order", "description": "根据订单ID查询订单状态 和物流信息。当用户询问订单 进度时调用此工具。", "parameters": { "type": "object", "properties": { "order_id": { "type": "string", "description": "订单号， 格式为ORD-XXXXXX" } }, "required": ["order_id"] } }
  • description 要说明何时调用
  • 参数说明要包含格式示例
  • 工具数量不宜超过 20 个
🔀 Parallel Tool Calling
⚡
现代模型（GPT-4o、Claude 3.5）支持单次输出多个工具调用，并行执行后统一回传结果。
LLM 输出
→
tool_call_1: get_weather
tool_call_2: get_news
↓ 并行执行 → 合并结果 → 再次请求模型
  • 显著减少总延迟
  • 需要客户端支持并发执行
  • tool_result 必须一一对应 tool_call_id
🎛️ tool_choice 参数控制
值行为适用场景
auto模型自主决定通用场景
none禁止工具调用纯文本回复
required必须调用工具强制路由
{"name":"X"}强制调用指定工具结构化提取
⚠️ 常见问题与调试
  • 工具选错 → 优化 description，更明确区分边界
  • 参数幻觉 → 加强参数描述，用枚举约束值域
  • 无限循环 → 设置 max_tool_calls 上限
  • 结果回传错误 → tool_use_id 必须与调用一一对应
  • 工具超时 → 异步执行 + 超时熔断

mcp · AI 工具集成的 USB 标准
📌
MCP 本质：Anthropic 提出的开放协议，定义了 AI 模型与外部工具/数据源之间的标准化通信方式。类比 USB-C — 统一接口，任意设备互插。

🔗 传输层协议

  • • 本地进程通信
  • • 标准输入输出
  • • 适合本地工具集成
HTTP/SSE
  • • 远程服务调用
  • • 支持流式推送
  • • 适合云端服务集成
🆚 MCP vs Function Calling
维度Function CallingMCP
标准化各厂商自定义开放统一协议
工具复用每次手工定义安装即用
数据访问仅参数传递支持 Resources
安全控制应用层负责协议层授权
生态广泛支持快速增长中
💡
MCP 不是替代 Function Calling，而是在其上提供标准化封装层。底层仍然通过 Tool Use 调用。
🔒 MCP 安全考量
  • 最小权限 — 每个 Server 只暴露必要能力
  • 用户确认 — 高风险操作需显式授权
  • 沙箱隔离 — Server 间互相隔离
  • Prompt Injection 防御 — 验证来自 Server 的内容
  • 审计日志 — 记录所有工具调用历史

MODULE 07
Skill 技能系统
skill_system · 可复用的 AI 能力单元
📌
Skill 是什么：将完成特定任务所需的 Prompt + 工具调用 + 数据流程封装为可复用的能力单元。是 Agent 系统中的"函数库"。

🧩 Skill 的组成结构

TRIGGER 触发条件

定义何时调用此 Skill（关键词/意图/条件），类似 Function 的签名，让 Agent 知道该选择它。

PROMPT 提示模板

任务专属的 System Prompt 和 Few-shot 示例，针对该任务高度优化，不依赖通用提示。

TOOLS 工具集

仅注入该 Skill 需要的工具，避免工具过多导致模型选择混乱。

OUTPUT 输出规范

严格的输出 Schema，方便下游 Skill 或流程消费结果。

🔧 Skill vs Tool 的区别
维度ToolSkill
本质单一函数调用封装的 LLM 工作流
包含 LLM❌ 纯代码✅ 含 Prompt+模型
复杂度单步原子操作可多步、可条件
复用方式函数调用Skill 注册表引用
📚 Skill 注册与选择机制
1

用户输入 → 意图识别（Routing LLM）

2

Skill 注册表检索 → 语义匹配候选

3

加载 Skill 专属 Prompt + Tools

4

执行 → 输出结果 → 返回主 Agent

🏗️ 常见 Skill 设计模式
  • Pipeline Skill — 串行子步骤，每步输出是下步输入
  • Branching Skill — 根据中间结果条件分支
  • Parallel Skill — 多子任务并行，汇聚结果
  • Recursive Skill — 自调用分解复杂任务
  • Critic-Actor — 生成器 + 批评者迭代优化
📐 Skill 质量评估
  • 触发精准率 — 正确场景调用正确 Skill 的比例
  • 输出合规率 — 输出符合 Schema 的比例
  • 任务完成率 — 端到端完成目标的比例
  • 延迟/成本 — Token 消耗和响应时间
  • 回归稳定性 — 模型升级后能力保持

🎯 必答题清单

模块高频考题核心答点
Prompt CoT 什么时候反效果？ 简单分类/检索任务，增加冗余 token 反而干扰；多步推理才有效
Prompt JSON Mode vs Structured Output 区别？ JSON Mode 仅保证语法；Structured Output 保证字段名/类型/必填
Context Lost in the Middle 是什么？ 模型对上下文中间位置内容遗忘，重要内容放首尾
Context 多轮对话记忆如何管理？ 滑动窗口 / 摘要压缩 / 向量化长期记忆，三层结合
Harness 生产 LLM 调用必须有哪些工程保障？ 重试退避、输出验证、限流熔断、Trace 可观测、成本监控
Agent ReAct vs Plan-and-Execute 如何选择？ 动态短任务选 ReAct；长计划任务选 P&E；复杂任务可混合
Agent Agent 如何防止无限循环？ max_iterations 上限 + 工具调用计数 + 相似状态检测
FC Parallel Tool Calling 实现要点？ 单次返回多个 tool_call，并发执行，tool_result 按 id 对应回传
MCP MCP 和 Function Calling 关系？ MCP 是标准化协议层，底层仍用 Tool Use；解决工具复用和跨模型问题
Skill Skill 和 Tool 的核心区别？ Tool 是纯代码函数；Skill 封装了 LLM + Prompt + 工具的完整工作流
Prompt Indirect Prompt Injection 如何发生？ RAG 检索到含恶意指令的文档，文档内容注入上下文覆盖系统指令
Agent Few-shot 示例选取策略？ 随机选 vs 相似度检索（kNN）；相似度检索效果更好，特别是长尾情况
