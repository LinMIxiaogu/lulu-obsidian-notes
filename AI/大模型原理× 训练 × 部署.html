Module One
模型基础理论
应用开发岗考察重点：能说清楚原理，而非手推公式

AI 应用开发岗不要求推导数学，但面试官会用几个关键问题判断你是否真正理解模型在做什么。核心考点围绕：注意力机制的直觉理解、KV Cache 的工程意义、位置编码的演化三条主线。

🔍 自注意力机制的本质

自注意力的核心问题是：序列中每个 token 应该「借鉴」其他哪些 token 的信息，借鉴多少？

输入 token X
↙
↓
↘
Q = X·WQ
「我想找什么」
K = X·WK
「我能提供什么」
V = X·WV
「我实际携带的信息」
↓
Attention = softmax(QKT / √dk) · V
Q 和 K 点积 → 相关性打分 → softmax 归一化 → 加权聚合 V
高频考点
Q 和 K 为何用不同矩阵？
分离的 WQ 和 WK 让模型独立学习「查询角色」和「被匹配角色」。若两者共享权重，同一词对自身的注意力永远最高，无法捕捉非对称关系。

直觉：「苹果」在查询「水果」和查询「手机品牌」时，应与不同 K 产生不同得分。
高频考点
为何除以 √dk？
点积结果的方差随维度 dk 线性增长，维度越大，点积值越大，softmax 进入梯度饱和区（输出接近 one-hot），梯度几乎为零。

除以 √dk 将方差稳定为 1，保持 softmax 分布平滑，训练稳定。
高频考点
多头注意力的价值
单头注意力只能捕捉一种关联模式。多头将 dmodel 拆分为 h 个子空间，每个头独立学习不同关系（如：句法依赖、指代关系、语义相似），最终拼接融合。

核心增益：多视角捕捉，而非单纯算力叠加。
⚡ KV Cache — 应用层最重要的推理概念

KV Cache 是 AI 应用开发岗必考的工程知识点，因为它直接影响你的 API 成本和响应延迟设计。

📌
本质问题：自回归生成中，每生成一个新 token，都需要计算它与所有历史 token 的注意力。历史 token 的 K、V 矩阵每次都要重算，产生大量冗余计算。
❌ 无 KV Cache
生成第 N 个 token 时
→ 重新计算前 N-1 个 token 的 K、V
→ 计算量 O(N²)
→ 长序列推理极慢
→
✅ 有 KV Cache
生成第 N 个 token 时
→ 读取缓存中已存的 K、V
→ 只计算新 token 的 K、V
→ 计算量 O(N)，速度显著提升
代价：显存占用随序列长度线性增长
⚠️
应用开发考点：KV Cache 的显存公式 = 2 × 层数 × 头数 × 每头维度 × 序列长度 × 批量大小 × 数据类型字节数。这就是为什么长上下文 API 调用贵得多，也是 vLLM 重点优化的对象。
工程影响
Prompt Caching 的底层原理
Anthropic / OpenAI 提供的 Prompt Cache 本质是在服务器端复用静态前缀的 KV Cache。相同 System Prompt 的请求命中缓存后，只需计算新增内容的 K、V，成本可降低 90%。
工程影响
Context Window 限制的本质
上下文窗口不只是「能输入多少字」的问题，背后是 KV Cache 的显存上限。128K 上下文意味着需要在显存中维护 128K 个 token 的 K、V 矩阵，这是模型部署成本的核心变量。
📍 位置编码演化路线

自注意力机制本身是排列无关的（Permutation Invariant）——打乱输入顺序，注意力得分不变。位置编码是为模型注入顺序信息的方式，理解它的演化逻辑比死记公式重要得多。

方案原理优势劣势代表模型
正弦余弦 PE 按维度用不同频率的 sin/cos 函数编码位置，加在 embedding 上 无需训练；可外推到训练时未见的长度 对相对位置建模间接；长序列效果下降 原版 Transformer, BERT
可学习绝对 PE 每个位置分配一个可训练向量，随模型端到端学习 灵活，能拟合数据中的位置模式 不能外推，超出训练长度效果崩溃 GPT-2, BERT 变体
RoPE 在计算 QK 点积前，对 Q 和 K 按位置做旋转变换，使点积天然包含相对位置 相对位置直接体现在注意力分数中；外推性好；显存零额外开销 实现略复杂 LLaMA, Qwen, DeepSeek
ALiBi 不修改 embedding，在注意力分数上直接减去与距离成比例的偏置 外推性极强；实现极简 位置信息编码方式有局限 MPT, BLOOM
🎯
面试核心答点：RoPE 为什么好？因为它让「两个 token 的注意力得分」天然只依赖它们的相对位置差，而非各自的绝对位置。这使模型在处理比训练时更长的序列时仍能保持相对位置关系，这就是主流开源模型都选 RoPE 的原因。
🏗️ Encoder-only vs Decoder-only — 应用选型逻辑
Encoder-only BERT 系
  • 注意力方向：双向，每个 token 能看到全句
  • 任务形式：理解 → 分类/相似度/抽取
  • 应用场景：语义搜索、文本分类、意图识别、NER、Reranker
  • Embedding 质量高，适合做向量化
Decoder-only GPT/LLaMA 系
  • 注意力方向：单向（因果），只看左侧历史
  • 任务形式：生成 → 自回归预测下一个 token
  • 应用场景：对话、代码生成、摘要、RAG 的 Generation 阶段
  • 规模效应强，主流大模型方向
💡
应用开发决策：RAG 的 Embedding 模型用 Encoder-only（如 BGE、E5）；RAG 的 Generator 用 Decoder-only（如 GPT-4o、Claude）。Reranker 也通常基于 Encoder-only 实现 cross-encoder 打分。

Module Two
微调与对齐
应用开发岗考察重点：知道何时选微调、选哪种方案、代价是什么

AI 应用开发岗不需要你亲自跑训练，但面试官会考察你的决策判断力：这个业务场景到底要不要微调？选 LoRA 还是全量？微调后效果变差怎么办？这些才是核心考点。

🤔 第一问：要不要微调？
🚨
应用开发最高频考点：80% 的场景不需要微调。面试官最怕你动不动就说「微调一下就好了」——这暴露了对工程成本的无知。
✅ 应先用 Prompt 工程 / RAG
  • 需要注入最新知识（知识截止问题）
  • 需要访问私有数据（安全问题）
  • 任务通过 Few-shot 可达到目标效果
  • 需求快速迭代，Prompt 更灵活
  • 成本敏感，没有 GPU 资源
🎯 微调有价值的场景
  • 需要固定输出格式/风格（如特定 JSON、专业语气）
  • 需要垂直领域专业能力（医疗、法律术语）
  • 推理时 Prompt 成本极高，需压缩
  • 模型行为一致性要求极高
  • 数据量充足（通常 >1000 条高质量样本）
🛠️ SFT 方案全景：从全量到 LoRA
方案原理显存需求效果适用场景
全参数微调 更新模型全部参数 极高（模型参数 × 约 16 倍） 最好 数据量大、算力充足、追求极致效果
LoRA 在注意力层旁并联低秩矩阵 A×B，冻结原始权重，只训练 A、B 低（仅 A、B 的梯度+优化器状态） 接近全量 当前主流首选，消费级 GPU 可跑
QLoRA 将冻结的基础模型量化为 4-bit，再做 LoRA 微调 极低（可在单张 24GB 显卡跑 70B 模型） 略低于 LoRA 显存严重受限时的首选
Prefix Tuning 在输入前添加可训练的「软提示」向量，模型参数全冻结 极低 一般 多任务场景，每个任务独立 prefix
🔬 LoRA 原理精讲

核心假设：模型微调时，权重矩阵的变化量 ΔW 是低秩的（即真正有效的信息维度远小于矩阵维度）。

原始权重 W

秩 r 通常取 4~64，训练参数量仅为全量的 0.1%~1%
推理时如何合并
Zero Overhead 合并
推理前可将 ΔW = A×B 直接加回 W，得到新的 W'，无需额外计算。等于零推理成本的个性化模型。
秩 r 的选择
r 越大效果越好？
并非如此。r 过大接近全量微调，失去参数高效的意义。实践中从 r=8 或 r=16 开始调，大多数任务 r=64 已足够。
🎯 对齐方法：SFT → RLHF → DPO

对齐（Alignment）解决的是：模型能力很强，但输出不符合人类期望的问题。三种方法的演化逻辑比各自的细节更重要。

1

SFT（监督微调）— 教模型「正确行为」

提供人工标注的「指令 → 理想回答」对，用交叉熵损失微调。模型学会按指令回复，但无法区分「好回答」和「更好的回答」，且依赖标注质量上限。

2

RLHF（基于人类反馈的强化学习）— 教模型「人类更喜欢什么」

先用人类偏好数据训练奖励模型（RM），再用 PPO 强化学习优化语言模型，最大化 RM 打分，同时约束与原始 SFT 模型的偏差（KL 散度惩罚）。效果好但训练极复杂，需要同时维护 4 个模型。

3

DPO（直接偏好优化）— RLHF 的简化替代

数学上证明可以绕过 RM，直接用「好回答 vs 坏回答」的对比数据优化语言模型。将 RLHF 的 4 模型复杂流程简化为类似 SFT 的单模型训练，同等偏好数据下效果相当甚至更好。目前主流选择。

维度RLHF / PPODPO
训练复杂度极高（需要 Actor、Critic、RM、Reference 四个模型）低（单模型训练，类似 SFT）
数据格式需要人类偏好排序 + 奖励模型标注只需 (prompt, chosen, rejected) 三元组
稳定性PPO 超参数敏感，容易崩溃训练稳定，工程友好
效果上限高，可持续优化单轮效果接近 RLHF，多轮迭代稍弱
适用场景追求极致对齐（如 GPT-4 级别训练）大多数业务微调场景的首选
🧠 灾难性遗忘 — 微调的核心风险
⚠️
什么是灾难性遗忘：在特定任务上微调后，模型在原有通用能力上性能大幅下滑。例如微调成医疗问答模型后，数学推理能力明显变差。
解决方案 1
LoRA / PEFT 类方法
冻结原始参数，只训练旁路矩阵。原始权重完整保留，通用能力自然不受损。这是 LoRA 最大的工程价值之一，不只是省显存。
解决方案 2
混合数据训练
在微调数据中混入一定比例的通用数据（如 5%~15% 的原始预训练数据），让模型在学新技能的同时保持对旧知识的复习。
解决方案 3
EWC（弹性权重巩固）
为对原有任务重要的参数添加正则化约束，限制这些参数在微调时的变化幅度。理论优雅但工程实现成本高，实践中不如 LoRA 流行。
解决方案 4
降低学习率 + 早停
用极小的学习率（如 1e-5 以下）微调，减少对原始权重的扰动。配合验证集上的通用能力评估做早停，是最简单的工程实践。

推理与部署
应用开发岗考察重点：能评估方案成本，能选合适的部署工具栈

推理部署是应用开发岗的核心工程能力之一。你不一定要亲手运维 GPU 集群，但必须能回答：为什么用 vLLM？量化损失多少精度？本地部署怎么快速启动？

🚀 vLLM — 高性能推理引擎

vLLM 是目前最主流的开源 LLM 推理服务框架，其核心创新是 PagedAttention，解决了 KV Cache 显存碎片化问题，将 GPU 吞吐量提升 10-24 倍。

🧩 PagedAttention 的直觉理解
传统 KV Cache 的问题

为每条请求预分配连续的最大显存块（如为 2048 token 预留空间），但实际只用了 200 token：

  • 内部碎片：预留空间大量浪费
  • 外部碎片：无法塞入新请求
  • 批处理量（Batch Size）受严重限制
PagedAttention 的解法

借鉴操作系统虚拟内存的「分页」思想：

  • KV Cache 按固定大小的 Block 分配
  • Block 可不连续，用页表映射
  • 不同请求可共享 KV Block（前缀缓存）
  • 显存利用率接近 100%，Batch Size 大幅提升
⚡ Continuous Batching

传统推理框架：一个 batch 的所有请求必须等最长的那条完成才能释放。
Continuous Batching：每生成完一个 token 就检查是否有请求完成，随时插入新请求，GPU 不再空等。

Static
等待浪费
Continuous
持续填满
Continuous Batching 让 GPU 利用率从 30-50% 提升到 80-90%+

面试答题框架：选量化方案时先问三个问题：① 有没有 GPU（有 → GPTQ/AWQ，没有 → GGUF）；② 能接受多少精度损失（低损失 → INT8/AWQ，可接受 → INT4/GPTQ）；③ 部署环境是否有现成框架支持（Ollama → GGUF 天然支持）。
🧪 模型蒸馏 — 知识迁移到小模型

蒸馏（Distillation）是用大模型（Teacher）指导小模型（Student）训练，让小模型学到大模型的「行为模式」，而非仅仅学习 Ground Truth 标签。

↓

7B / 小模型
Student 同时学习 Hard Label（正确答案）和 Soft Label（Teacher 的概率分布），后者包含更丰富的「知识」
为什么 Soft Label 比 Hard Label 信息量更大
概率分布中的隐含知识
Hard Label：「答案是猫」（0/1）

Soft Label：「猫 0.7 / 豹 0.2 / 狗 0.1」

后者告诉 Student：猫和豹比猫和狗更相似。这种类间关系信息是 Hard Label 无法传递的。
应用开发场景
蒸馏 vs 微调 如何选？
  • 有大模型 API 访问权限 + 想要轻量本地模型 → 蒸馏
  • 有标注数据 + 想要特定能力 → 微调
  • 两者可组合：先用大模型生成数据，再微调小模型
实战常见模式
Data Distillation（数据蒸馏）
用 GPT-4 / Claude 生成高质量问答数据，再用这些数据微调 LLaMA / Qwen 等开源小模型。DeepSeek、Alpaca 等模型都用过这个思路。成本低效果好，是当前最流行的蒸馏变体。

Quick Reference
高频考点速查
按模块整理，面试前 30 分钟过一遍
模块一：模型基础理论
Q ≠ K 的权重矩阵，为什么不能共享？
共享导致自注意力变为对称操作，无法建模非对称依赖（A影响B ≠ B影响A）。分离权重让模型区分「查询角色」和「被查询角色」，大幅提升表达能力。
ATTENTION · 基础必答
注意力分数为什么除以 √dk？
防止高维向量点积过大，导致 softmax 进入梯度近乎为零的饱和区（输出趋近 one-hot），使梯度无法正常反传。除以 √dk 将方差稳定为 1。
ATTENTION · 基础必答
KV Cache 带来了什么问题，如何解决？
显存随序列长度线性增长，传统连续分配有严重碎片化。vLLM 用 PagedAttention 借鉴操作系统分页机制解决碎片问题，大幅提升批处理量和吞吐量。
KV CACHE · 工程必答
RoPE 相比正弦位置编码好在哪里？
RoPE 让注意力得分天然只依赖两个 token 的相对位置差，而非绝对位置，外推性更强。当前主流开源模型（LLaMA、Qwen、DeepSeek）均采用 RoPE。
POSITION ENCODING · 中高频
RAG 中 Embedding 为什么选 Encoder-only 而非 GPT 类模型？
Encoder-only 的双向注意力让每个 token 的表示包含完整上下文，向量语义更丰富。Decoder-only 的单向注意力导致表示质量较差，不适合语义搜索。
ENCODER · 应用必答
模块二：微调与对齐
什么情况下选微调，什么情况下用 Prompt + RAG？
需要注入最新/私有知识 → RAG；需要固定输出格式/风格、垂直专业能力、且有高质量数据（>1000条）和算力 → 微调。80% 场景 Prompt 工程先解决。
SFT · 决策高频
LoRA 的核心原理是什么？为什么不只是省显存？
假设 ΔW 低秩，用 A×B 旁路代替。核心价值有二：省显存只是其一；更重要的是冻结原始权重天然防止灾难性遗忘，推理时可零成本合并。
LORA · 高频必答
DPO 相比 RLHF/PPO 的核心优势？
数学等价地绕过了奖励模型，将 4 模型复杂流程降为单模型训练，训练稳定、工程友好。数据格式简单（chosen/rejected 对），效果接近 RLHF。
DPO · 高频必答
微调后通用能力下降怎么办？
优先选 LoRA/QLoRA（冻结原始参数）；若全量微调则混入 5~15% 通用数据；用极小学习率 + 早停；或用 EWC 约束关键参数变化幅度。

模块三：推理与部署
vLLM 为什么比原生 HuggingFace 推理快 10x 以上？
两个核心：① PagedAttention 解决 KV Cache 碎片化，大幅提升 GPU 显存利用率和 Batch Size；② Continuous Batching 让 GPU 持续满载而非等待最长请求。
VLLM · 高频必答
INT4 量化损失大吗？生产能用吗？
AWQ/GPTQ 的 INT4 量化在大多数任务上精度损失约 1-3%，已足够生产使用。显存降低 75%，可在消费级 GPU 运行 70B 级别模型。建议用评测集验证目标任务的实际损失。
QUANTIZATION · 中高频
Ollama 和 vLLM 怎么选？
Ollama：本地开发/原型/CPU 部署，极简运维，优先选。vLLM：生产 GPU 服务器，高并发，追求吞吐量，需要 Continuous Batching。两者都支持 OpenAI 兼容接口。
DEPLOYMENT · 高频
蒸馏和微调的区别与联系？
微调用标注数据优化模型能力；蒸馏用大模型的输出分布（Soft Label）训练小模型，传递隐含知识。实践中常组合：用 GPT-4 生成高质量数据，再微调开源小模型（Data Distillation）。
