// 03 ★ 面试高频

文本分块技术

分块是 RAG 最基础也最容易被忽视的环节。面试常问："你们的 Chunk 策略是什么？为什么这样选？"

为什么不能直接固定字数切？

固定字数切割会在句子中间截断，导致单个 Chunk 语义不完整，向量化后语义稀释，检索命中率下降。更严重的是会把同一个知识点切成两半，两个 Chunk 都召回不到完整信息。

分块方法核心原理优点缺点推荐场景
固定字符
CharacterTextSplitter		 按字数硬切，加 overlap 缓解 实现最简单 容易截断语义 快速验证原型
递归字符
RecursiveCharacterTextSplitter		 按段落→句子→词依次尝试切割，优先保持完整性 通用性强，语义完整 需调 chunk_size 参数 默认首选
语义分块
SemanticSplitter		 用 Embedding 计算相邻句相似度，相似度骤降处切割 每块一个完整主题 速度慢，需调阈值 文档主题边界清晰时
Agentic 分块
LLM-Based		 让 LLM 理解内容后判断最佳切割边界 质量最高，最像人类 成本最高，速度最慢 高价值文档离线处理

父子文档索引 — 面试必考

这是目前生产环境最推荐的策略，解决了"检索精度"和"上下文完整性"的矛盾。

Parent-Child Index Strategy
一句话记住：用小 Chunk（128 token）做向量检索保证精准，命中后自动回溯返回父 Chunk（512 token）给 LLM 保证完整。检索粒度和生成粒度解耦。

索引策略对比

滑动窗口索引

每个 Chunk 与前后 Chunk 有重叠（overlap），防止跨句代词（"它"、"这个"）丢失指代对象。解决语义断裂问题。

元数据过滤索引

Chunk 附带文件名、页码、时间等元数据。检索时先用元数据硬过滤（如"只看2024年财报"），缩小候选范围后再做向量搜索。

层级摘要索引

先生成章节摘要作为上层节点，具体文本块挂在下层。检索时先匹配摘要定位章节，再深入检索细节。适合大规模文档集。

// 04

前处理优化（Pre-Retrieval）

目标是让送进检索系统的 Query 和存进向量库的内容质量更高。

① 分块策略 Chunking

固定大小 + 重叠滑窗（chunk_size=512，overlap=50）防止语义截断；语义分块按句子/段落边界切割；Small-to-Big：检索用小 Chunk，喂 LLM 时返回父节点大 Chunk。

② Query 改写 Rewriting

Multi-Query：一个问题改写成 3-5 个不同表述，分别检索后合并去重。Step-back Prompting：把具体问题抽象成上位问题，先检索背景知识。

③ HyDE 假设文档

先让 LLM 基于 Query 生成一段"假设性答案文档"，用假文档向量去做检索，而不是用原始 Query。假文档向量分布比 Query 向量更接近真实答案。面试必考。

④ 元数据 + 层级索引

给 Chunk 附元数据（文档来源、章节、时间），检索时先硬过滤缩小范围，再做向量排序。层级索引（父文档→子 Chunk）让召回更灵活。

⑤ 混合检索 Hybrid Search

稠密向量检索（ANN，语义相似）+ 稀疏检索（BM25，关键词精确）并行，用 RRF（Reciprocal Rank Fusion）融合排序。目前工业界最主流方案。

HyDE 核心思路：用户 Query "Python 如何处理并发？" → LLM 生成假设答案："Python 处理并发主要通过 asyncio…" → 用这段假文档向量检索，命中率远高于直接用 Query 检索。

// 05 ★ 面试高频

查询路由（Query Routing）

面试常问："如果系统里同时有向量库、关系型数据库、图数据库，Query 进来怎么决定去哪查？"这就是查询路由，分两种思路。

逻辑路由 vs 语义路由
逻辑路由

让 LLM 分析 Query 意图，输出结构化指令（如 JSON）指定查询哪个数据源。灵活但有额外 LLM 调用开销。

典型场景：同一个问题可能走 SQL（查订单数据）或向量库（查政策文档）。

语义路由

预先准备多套 Prompt 模板并向量化，Query 进来后直接算与各模板的相似度，选最近的模板路径。无需 LLM 推理，速度快。

典型场景：客服系统区分"退款咨询"vs"技术支持"vs"产品查询"。

面试回答套路：先说"路由解决的是多数据源分发问题"，再对比两种方案的 trade-off——逻辑路由灵活但慢，语义路由快但需要预设模板。根据延迟要求和场景复杂度选择。

// 06

后处理优化（Post-Retrieval）

目标是过滤召回的噪声，让真正相关的内容以最佳方式送给 LLM。

① 重排序 Reranking

召回 Top-K 后用 Cross-Encoder（BGE-Reranker、Cohere Rerank）精排。Bi-Encoder 速度快但粗糙；Cross-Encoder 把 Query+Chunk 拼一起算相关性，精度高但慢，只用于精排阶段。

② 上下文压缩

Chunk 中只有部分内容和 Query 相关，用小模型把无关内容压缩掉，降低 LLM 输入长度，减少噪声干扰，节省 Token 成本。

③ Lost in the Middle

研究表明 LLM 对 Prompt 中间部分遗忘率高。最相关的 Chunk 应放在开头和结尾，而不是顺序堆叠。

④ Self-RAG

LLM 在生成时自我反思：这段 Context 是否和 Query 相关？生成的答案有没有幻觉？通过特殊 Token 控制是否需要继续检索。

⑤ Corrective RAG

检索质量低于阈值时自动回退，触发 Web Search 或扩展检索策略，保证 LLM 有足够好的 Context。

⑥ 引用溯源 Citation

生成答案时同时输出每句话对应的 Chunk 来源，便于用户核实，减少幻觉信任风险。Grounding 是 RAG 生产化的必选项。

// 07 ★ 面试高频

Corrective RAG 详解

原版 HTML 里 Corrective RAG 只有一句话。面试如果问到"当检索结果质量很差时你怎么处理？"，能说清楚这三条路径会非常加分。

核心思路：先评估，再分路径

在把检索到的文档送给 LLM 之前，先用一个轻量级评估器判断文档质量，然后根据质量结果走不同处理路径。

Corrective RAG — 三路径流程
路径一：Correct（文档质量高）

文档相关，但可能有噪声。把文档拆成句子级别，过滤掉与 Query 无关的句子，重新组合成精炼的内部知识 k_in，送给 LLM。

路径二：Ambiguous（文档质量模糊）

文档沾边但不够好。两条腿走路：对现有文档做提纯得到 k_in，同时触发 Web Search 补充外部知识 k_ex，两者合并送 LLM。

路径三：Incorrect（文档完全不相关）

直接丢弃检索结果，把原始 Query 重写成更适合搜索引擎的格式，触发 Web Search 获取外部知识 k_ex，用外部知识回答。

面试一句话：Corrective RAG 的本质是"给检索结果加一道质量门控"，根据质量高低走不同的知识补充策略，而不是无论如何都把召回结果直接喂给 LLM。

// 09

面试高频问题

文本分块策略怎么选？生产环境推荐哪种？
四种方法从简单到复杂：固定字符切割（不推荐生产）→ 递归字符分割（默认选择，LangChain RecursiveCharacterTextSplitter）→ 语义分块（主题边界清晰时）→ Agentic 分块（高价值文档，成本允许时）。

生产环境最推荐的是父子文档索引：子块（128 token）用于向量检索保证精准，命中后自动回溯返回父块（512 token）给 LLM 保证上下文完整性。这个策略解决了"精度与完整性的矛盾"，面试说出来很加分。

参数调优：没有银弹，用 Recall@K 和 MRR 跑评估集来验证，不要凭感觉定 chunk_size。
查询路由是什么？逻辑路由和语义路由怎么选？
查询路由解决的是"同一个系统里有多个数据源，Query 该去哪查"的问题。

逻辑路由：让 LLM 分析 Query 意图，输出结构化指令（JSON）指定查询目标。灵活，适合数据源差异大、需要推理判断的场景。缺点是多一次 LLM 调用，增加延迟和成本。

语义路由：预先准备好 N 套 Prompt 模板并向量化，Query 进来后算与模板的余弦相似度，选最近的路径。速度快，无 LLM 调用开销。适合问题类型固定、延迟敏感的场景（如客服分类）。

选型原则：场景复杂、数据源类型差异大 → 逻辑路由；场景固定、追求低延迟 → 语义路由。
Corrective RAG 和普通 RAG 的区别？什么时候用？
普通 RAG 不管检索质量好不好，都把 Top-K 结果直接拼进 Prompt 送给 LLM，导致低质量文档污染生成结果。

Corrective RAG 在检索后加一道质量评估，根据结果走三条路径：文档质量高 → 提纯后使用；文档不确定 → 提纯 + Web Search 补充；文档完全错误 → 丢弃，重写 Query 后 Web Search。

适用场景：知识库覆盖不全（用户可能问到库里没有的内容）、对答案准确性要求高、允许引入网络搜索的场景。代价是增加了评估器的调用和潜在的网络搜索延迟。
Chunk size 怎么选？有什么方法论？
没有银弹。通常先从 512 token 开始，用 Recall@K 和 MRR 跑评估集来调参。太小：语义不完整，召回片段无法独立成意；太大：引入噪声，Token 成本上升。

实际工程里常用 Small-to-Big 策略：检索时用小 Chunk（128 token）保证精准，但喂给 LLM 时扩展到父 Chunk（512 token）保证上下文完整性。这个策略在面试中非常加分。
HyDE 和 Multi-Query 分别适合什么场景？能叠加吗？
HyDE 适合用户 Query 非常简短或模糊的场景（比如单词搜索、专业术语查询），因为单词向量离文档向量语义空间差距大，假文档能桥接这个 gap。

Multi-Query 适合用户有明确意图但表述不规范，比如口语化问法。通过多角度改写扩大召回覆盖。

两者可以叠加：先用 Multi-Query 生成多个 Query，再对每个 Query 用 HyDE 生成假文档，检索结果做 RRF 合并。代价是 LLM 调用次数增加。
Reranking 用什么模型？Bi-Encoder 和 Cross-Encoder 有什么区别？
Bi-Encoder（向量检索阶段）：Query 和 Document 分别编码成向量，用余弦相似度比较。速度快（O(1) 查询），但精度低，因为 Query 和 Doc 没有交互。

Cross-Encoder（Reranking 阶段）：把 Query + Doc 拼接成一个输入，模型同时看到两者计算相关性。精度高，但无法预计算，只能对 Top-K 做精排。

开源首选 BGE-Reranker（BAAI 出品，中文效果好），商用首选 Cohere Rerank API。一般对 Top-50 做 Reranking，最终取 Top-5 送 LLM。
如何评估 RAG 系统质量？
两条评估链路：

检索质量：Recall@K（前 K 个里有多少命中真实答案）、MRR（第一个正确答案的排名倒数）、NDCG（考虑排名权重的综合指标）。

生成质量：Faithfulness（答案是否基于检索到的 Context，不幻觉）、Answer Relevancy（答案是否回答了问题）、Context Precision / Recall（Context 和答案的双向匹配）。

工具层面可以用 RAGAS 框架自动评测，它能在没有人工标注的情况下用 LLM 自动打分。
向量数据库为什么用 ANN 而不是精确 KNN？
百万量级向量做精确 KNN 是 O(N) 的，每次查询都要和所有向量计算距离，延迟不可接受（秒级甚至分钟级）。

HNSW（Qdrant/Weaviate 默认）和 IVF-PQ（Milvus/FAISS）都是以小幅精度损失换取 O(log N) 甚至 O(1) 的查询延迟，实际查询时间在 10ms 以内。HNSW 的 Recall@10 通常能达到 95%+，生产上完全够用。
Hybrid Search 的 RRF 融合是怎么做的？
RRF（Reciprocal Rank Fusion）公式：每个文档的最终得分 = Σ(1 / (k + rank_i))，其中 k 通常取 60，rank_i 是该文档在第 i 路检索结果中的排名。

举例：一篇文档在向量检索里排第 2，在 BM25 里排第 5，则 RRF 得分 = 1/(60+2) + 1/(60+5) ≈ 0.0161 + 0.0154 = 0.0315。

RRF 的优点是不需要对不同检索系统的分数做归一化，因为它只用排名，对异常值鲁棒。
Self-RAG 和普通 RAG 的核心区别是什么？
普通 RAG 是固定流程：检索 → 拼 Prompt → 生成，不管检索质量如何都会生成。

Self-RAG 让 LLM 动态决策：先判断这个问题是否需要检索；检索后判断每个 Chunk 是否真的相关；生成后判断答案是否基于 Context（是否幻觉）；如果不满足则触发重新检索或拒答。

通过训练特殊的 reflection token（如 [Retrieve]、[IsRel]、[IsSup]、[IsUse]）来实现，需要专门训练或微调模型。
