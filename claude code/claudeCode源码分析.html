Claude Code 源码解析：
别先背概念，先看它怎么把活干完

Claude Code 更像一套运行在终端里的 Agent 操作系统。它要解决的不是“怎么让模型回答代码问题”，而是“怎么让多个 Agent 在真实代码仓库里安全、并行、低成本地完成任务”。

这篇文章先追踪一条用户请求，再拆开看它背后的关键设计：

请求 → 拆解 → 执行 → 隔离 → 确权
协作模式Team Mode / Coordinator Mode 如何组织多 Agent
执行后端InProcess / Tmux / iTerm2 如何承载 Worker
并行隔离Git Worktree 如何隔离多路修改
生产支撑SendMessage、权限、Prompt Cache 和记忆系统
01

先看大图：一次复杂请求怎么跑完？

理解 Claude Code，不要从“有哪些 Agent”开始，而要从“用户一句话怎么变成一组安全可控的工程动作”开始。

用户提出任务例如：修一个跨模块 Bug
→
Leader / Coordinator 拆任务决定谁去读代码、谁去改、谁去验证
→
AgentTool 派 Worker统一入口，选择 Agent 类型与执行后端
Worker 独立执行独立上下文，必要时独立 worktree
→
SendMessage 汇报不是靠终端文本，而是显式消息
→
危险操作找人确认权限最终回到 Leader 终端
一句话模型Claude Code 的核心不是“一个大模型很聪明”，而是“一个 Leader 把任务拆给多个隔离 Worker，并用工具、消息、权限、缓存、Worktree 和记忆机制把它们管起来”。
02

为什么单 Agent 不够用？

单 Agent 最大的问题不是不会做，而是所有东西都挤在同一个上下文窗口里。代码搜索日志、错误输出、历史对话、工具结果越堆越多，模型后面就会被前面的噪音拖累。

🧠

上下文会爆

大型代码库里，文件内容、调用链、报错日志会迅速塞满窗口，中间信息容易被稀释。

⏳

串行会慢

一个 Agent 一次只能沿着一条路径查。多 Agent 可以同时查模块 A、模块 B、测试和文档。

🧰

工具会乱

工具太多时，模型既要理解任务，又要在几十个工具里选对工具，路由错误概率上升。

所以多 Agent 的本质不是“角色扮演”，而是把一个大上下文问题拆成多个小上下文问题。每个 Worker 只处理一小块，最后把浓缩后的结论交给 Leader。

更好理解的类比单 Agent 像一个人独自排查大型代码库，所有线索都挤在同一个脑子里；多 Agent 则像把 API 调用链、配置环境、测试日志分给不同 Worker 同时排查，Leader 只接收压缩后的结论并做决策。
03

Worker 不是复制人：内置 Agent 的分工

既然有多个 Worker，下一步自然会问：它们是不是都一样？答案是否定的。Claude Code 更像是在内置一组“岗位”，不同 Agent 的模型、工具权限和职责边界都不同。

Agent像什么角色主要用途关键限制
Explore侦察兵快速扫代码、找调用链、确认事实偏只读，可用更轻量模型，高并发探索
Plan架构师制定方案、评估风险、拆解步骤不直接改代码，避免“边想边动手”
verification测试员 / 反方审查检查实现是否可靠，补测试或找反例强调验证，不负责主方案输出
fork分身继承父上下文尝试一个分支方案权限需要沿父链路冒泡，不能悄悄扩大
general-purpose通用工程师兜底处理复杂、边界不明确的任务能力更全，也更需要权限控制
为什么这一节很重要如果 Worker 都一样，多 Agent 只是“多开几个聊天窗口”。有了角色、模型和工具权限差异，多 Agent 才变成可控的工程组织。
04

两种协作模式：固定团队 vs 临时外包

Claude Code 的多 Agent 不止一种形态。理解 Team Mode 和 Coordinator Mode 的区别，很多后面的设计就顺了。

Team Mode：固定团队

像你提前建好一个团队，每个 Worker 有名字、有配置、有邮箱。适合长期协作，比如固定的“测试 Agent”“文档 Agent”“Reviewer Agent”。

关键词：持久化、手动管理、团队配置。

Coordinator Mode：临时外包

像 Leader 临时拉几个人做一次项目。任务来了才 spawn Worker，结束后回收。适合一次复杂任务的自动拆解和并行执行。

关键词：按需创建、自动编排、用完即毁。

维度Team ModeCoordinator Mode
控制方式Leader 手动管理 WorkerCoordinator 自动派发 Worker
Worker 生命周期可以长期存在任务完成后回收
可用工具更完整只保留 Agent、SendMessage、TaskStop 等编排工具
适合场景固定角色协作复杂任务临时拆解
05

Coordinator 如何收束：不是多开 Worker，而是分阶段压缩

如果说 Team Mode 解决的是“固定团队怎么协作”，那么 Coordinator Mode 解决的是“临时复杂任务怎么自动拆解并收束”。它的关键价值不是派出很多 Worker，而是让探索过程留在 Worker 自己的上下文里，只把压缩后的结论带回来。

PHASE 1

Research

多个 Worker 分头读代码、查资料、找调用链、定位风险点。

PHASE 2

Synthesis

Coordinator 收集各 Worker 的关键结论，而不是复制全部中间日志。

PHASE 3

Execution

选择最可信方案，派执行型 Worker 修改代码、补测试或生成文档。

PHASE 4

Stop

任务完成后回收 Worker，避免临时上下文继续污染主对话。

核心收益Coordinator Mode 把“探索噪音”和“决策上下文”分开：Worker 可以大胆试错，Coordinator 只保留能支撑决策的摘要、证据和下一步动作。
06

AgentTool：所有子 Agent 的总入口

如果把 Claude Code 看成一个公司，AgentTool 就像“派工系统”。Leader 不直接去启动某个进程，而是把任务交给 AgentTool，由它判断：用什么 Agent、给什么工具、跑在哪个后端、权限怎么继承。

Agent 定义
每个 Agent 都有类型、使用场景、可用工具、禁用工具、模型、最大轮次等字段。这样 Agent 不是随便起一个对话，而是有边界的执行单元。
工具过滤
Claude Code 不会让所有 Worker 都拥有完整权限。Explore、Plan 这类 Agent 通常只负责读代码和做方案；Coordinator 只负责派任务、收消息和停止任务，不能直接改文件；自定义 Agent 也可能被禁止继续创建新的子 Agent。
代码层限权
这不是靠提示词提醒“不要乱改”，而是在代码层面直接不给它危险工具。没有 Write / Edit，它就不能改文件；没有 AgentTool，它就不能继续套娃。
小型执行循环
Leader 派出 Worker 后，并不是调用一个固定函数等返回值。Worker 自己也会理解目标、选择工具、读取文件、观察结果、继续判断下一步，直到完成任务并汇报结果。所以 Worker 更像一个被限制权限的小型 Claude Code，而不是普通工具函数。
关键理解Claude Code 的多 Agent 不是写死的 if/else 流程，而是把“Agent”抽象成一种可配置、可限权、可独立执行的工作单元。
07

三种执行后端：Worker 运行在哪里？

“执行后端”不是 Agent 类型，而是 Worker 的承载方式。同一套 Agent 逻辑，可以在当前进程内运行，也可以通过外部终端工具启动独立的 Claude Code 实例运行。

后端怎么理解优点代价
InProcessWorker 复用当前 Claude Code 进程，在进程内创建独立的 Agent 运行上下文启动快，通信成本低进程级隔离弱，依赖运行时上下文隔离
Tmux通过 tmux 启动独立 Claude Code 实例来承载 Worker进程隔离更强，便于独立运行和排查依赖 tmux，有额外进程和通信成本
iTerm2通过 iTerm2 启动 / 管理独立 Claude Code 实例来承载 Worker更贴近 macOS 原生终端体验依赖 iTerm2，不通用

这里容易误解的是 InProcess。它不是把多个任务塞回同一个 Agent，而是在同一个进程里创建多个独立的 Agent 运行上下文。InProcess 的隔离依赖类似 AsyncLocalStorage 这样的运行时上下文机制：不同 Worker 的异步调用链会携带自己的 Agent 身份、会话状态和工具执行上下文。

也就是说，Agent 的边界不一定等于操作系统进程；只要任务状态、上下文、消息通道和生命周期是独立管理的，它仍然可以作为一个独立 Worker 运行。

08

Git Worktree：多 Agent 并行改代码的隔离战场

执行后端解决的是“Worker 跑在哪里”，但只要 Worker 会写代码，就会遇到另一个问题：多个 Worker 同时修改同一个仓库，怎么避免互相覆盖？这就是 git worktree 的意义。

没有 Worktree

风险Worker A 和 Worker B 都在同一个工作区修改 src/api.ts。谁先写、谁后写、谁覆盖谁，很难控制。最后 Leader 看到的是混在一起的结果。

有 Worktree

隔离Worker A 在 worktree-a 改方案 A，Worker B 在 worktree-b 改方案 B。Leader 可以对比差异，再决定合并哪一份。

repo-main/
├── 主工作区：保留当前仓库状态，作为对比和最终合并的位置
├── worktree-agent-a/：Worker A 尝试方案 A
├── worktree-agent-b/：Worker B 尝试方案 B
└── worktree-agent-v/：verification Worker 跑测试 / 查反例

注意，这个目录树不是执行顺序，而是隔离关系。Worker A、Worker B 和 verification Worker 可以在各自 worktree 里并行推进；最后再由 Leader 或用户比较结果，决定采用哪个方案、如何合并。

这也是多 Agent 从“并行思考”走向“并行动手”的关键一步。没有 Worktree，多 Agent 最多适合并行调研；有了 Worktree，多个 Worker 才能在代码层面安全试错。

主线上的位置先有执行后端，保证 Worker 能独立运行；再有 Worktree，保证 Worker 写代码时有独立战场。这两层隔离解决的是不同问题。
09

通信：SendMessage 和文件邮箱

Claude Code 的 Agent 间通信可以分成两层：第一层是 SendMessage，它是 Agent 发送消息的统一入口，负责决定“发给谁、发什么、走哪条通道”；第二层是具体投递通道，例如内存队列、文件邮箱或广播写入。

场景SendMessage 怎么送
目标是运行中的 InProcess Worker优先放进内存队列，速度最快
目标是独立进程 / 外部承载的 Worker写入对应 Agent 的文件邮箱
目标 Agent 已停止但可以恢复先唤醒，再投递消息
广播给所有成员写给多个 Agent 的收件箱

文件邮箱：Agent 的本地收件箱

文件邮箱不是 SendMessage 本身，而是 SendMessage 背后的一种落地通道。每个 Agent 可以有自己的收件箱文件：

~/.claude/teams/{team_name}/inboxes/{agent_name}.json

谁要给这个 Agent 留一条可恢复、可检查的消息，就把消息写进它的 JSON 收件箱。

📁

零依赖

用户不用额外安装 Redis、MQ 或数据库。

🧯

可恢复

消息落在文件里，进程崩溃后还能查。

🔍

可调试

开发者可以直接打开 JSON 文件看消息内容。

为了避免多个 Worker 同时写坏同一个 JSON 文件，写入时会加文件锁，并配合退避重试。

准确关系SendMessage 是统一发送接口；内存队列、文件邮箱、广播写入，是它背后的不同投递方式。
10

权限：防止多 Agent 里的权限漂移

多 Agent 的风险不在于 Worker 会执行任务，而在于 Worker 嵌套之后，危险权限可能被层层传下去，最后变成“谁都能执行 Bash、写文件、删目录”。

Claude Code 用两件事控制这个风险：

机制作用
工具过滤Agent 只拿到自己职责需要的工具，不该用的工具在代码层面不可见。
权限冒泡Worker 触发危险操作时，请求回到 Leader 所在的用户交互链路，由用户最终裁决。

权限检查链路可以简化成：

Worker 请求执行 Bash / Edit / Write
→ 工具自检
→ 配置 allow / deny
→ 风险分类或规则判断
→ 必要时冒泡到 Leader
→ 用户确认后执行
核心原则工具权限先于提示词约束；用户确认高于子 Agent 自行判断。比起在 prompt 里写“不要做危险操作”，更可靠的做法是在代码层面直接不给危险工具，并让危险操作不能绕过最外层确认。
11

成本与速度：少传、少算、按需加载

Claude Code 每次调用模型时，都要带上一大段上下文：系统规则、工具说明、项目状态、Git 信息、用户请求等。如果每次都从头传、从头算，成本高，速度也慢。

所以它做了两类优化。

第一类：Prompt Cache，让稳定内容尽量保持不变

模型身份、安全规则、代码风格、基础工具说明这些内容很少变化。Claude Code 会尽量让它们在 prompt 里保持稳定顺序和稳定文本。这样服务端就更容易复用缓存，而不是每轮都重新处理一遍。

第二类：工具按需加载，不是一开始塞满所有工具

常用工具直接给模型；低频工具先不展开完整说明，只保留搜索入口。等模型真的需要时，再通过 ToolSearch 加载相关工具。这和前端的 Code Splitting 类似：不是打开页面就加载全部代码，而是用到哪块，再加载哪块。

优化解决什么问题
静态段 / 动态段分离稳定内容更容易命中 Prompt Cache，经常变化的内容单独处理。
确定性排序避免只是工具顺序变了，就导致 prompt 前缀不同、缓存失效。
ToolSearch避免一开始塞太多低频工具说明，减少 prompt 体积和工具干扰。
按需加载需要什么工具，再加载什么工具，把成本花在真正用到的地方。
核心收益这类优化看起来细，但对 AI 编程工具很关键。Claude Code 的一次任务可能会调用模型很多轮；每一轮少传一点、少算一点，最终都会变成速度和成本上的收益。
12

上下文压缩：长任务快塞满时，Claude Code 怎么续命？

这里先把两个概念拆开：压缩解决“当前会话太长，怎么继续跑”；记忆解决“跨会话哪些经验要留下”。Claude Code 的上下文降载不是一个动作，而是一条链路：先做便宜的规则清理，再判断是否需要正式压缩，能用已有会话摘要就用已有摘要，最后才让 Fork Agent 现场总结。

环节是否真的压缩是否调用模型作用
Microcompact是不用按规则清理旧工具输出，比如 Read / Bash / Grep 的大块结果。
Auto-Compact否不直接调用判断 token 是否接近阈值，并调度后续压缩路径。
Session Memory Compact是压缩当下不用用会话过程中已经维护好的 Session Memory 作为摘要接力。
Full Compact是使用 Fork Agent临时生成结构化摘要，作为最重的兜底方案。

这条链路可以这样理解：

旧工具输出太多
→ Microcompact 先做规则压缩
→ Auto-Compact 判断上下文是否接近阈值
→ 如果需要正式压缩，优先尝试 Session Memory Compact
→ 如果已有会话摘要不可用或压缩后仍不够，再回退 Full Compact

Microcompact 不用模型也能压缩，因为它不是“理解全文后总结”，而是规则清理。旧的文件读取结果、搜索结果、命令输出很占上下文，系统可以把这类旧工具结果替换成占位文本，先释放 token。它要小心的一点是：不能破坏 tool_use / tool_result 的配对关系，否则 API 消息结构会坏掉。

Auto-Compact 更像容量监控器，而不是摘要算法。它根据 token 估算、模型上下文窗口、摘要预留和安全缓冲判断是否该压缩；同时还要避免压缩流程自己递归触发压缩，所以来源是 session_memory 或 compact 的请求会被排除。

Session Memory Compact 的摘要不是现场凭空生成的。Session Memory 是会话过程中逐步维护的当前任务摘要，记录当前状态、任务要求、相关文件、错误修正、关键结果和工作日志。等上下文快满时，系统优先拿这份已有摘要来接力，而不是立刻重新让模型总结整段历史。

Full Compact 是最后兜底：创建一个 Fork Agent，让它在不能调用工具的约束下，把长历史压成结构化摘要。它最贵，但信息保留能力最强，通常会保留当前目标、关键决策、重要文件、已修复错误、未完成事项和下一步动作。

核心理解Compact 不是长期记忆库，也不是向量数据库。它更像长任务里的“接力棒”：按成本排序，先清旧工具输出，再用已有摘要，最后才让模型重新总结。
13

记忆系统：Session Memory、Persistent Memory、Team Memory

压缩处理的是当前会话的上下文压力；记忆处理的是信息如何跨轮次、跨会话，甚至跨团队留下来。根据这份逆向分析，Claude Code 的记忆可以分成三层。

层级范围主要用途存储形态
Session Memory当前会话服务于上下文压缩，记录当前状态、任务规格、文件函数、错误修正、工作日志等。会话目录下的单个文件，固定章节结构。
Persistent Memory跨会话、按项目保存用户偏好、项目事实、反馈、外部引用等可复用信息。~/.claude/projects/<项目>/memory/ 下的 Markdown 文件。
Team Memory跨用户、按仓库把适合团队共享的项目记忆同步给同仓库成员。本地 team/ 子目录 + 服务端同步。

Session Memory：不是长期记忆，而是压缩的素材

Session Memory 只服务当前会话。它会随着会话推进逐步更新，记录当前状态、任务要求、关键文件、工作流、错误修正、重要结果等。等 Auto-Compact 触发时，系统可以优先拿这份会话记忆做摘要，而不是临时再把整段历史交给 LLM 重新总结。

Persistent Memory：MEMORY.md 是索引，不是全部记忆

持久记忆更像本地知识库。每条记忆是一个独立 Markdown 文件，带 name、description、type 等 frontmatter；MEMORY.md 只负责做索引，告诉系统有哪些记忆文件、每个文件大概讲什么。

memory/
├── MEMORY.md              # 索引，不是记忆本体
├── feedback_concise.md     # 用户反馈 / 工作偏好
├── project_deadline.md     # 项目信息
└── reference_linear.md     # 外部系统引用

自动提取通常发生在一轮任务结束后：主 Agent 完成响应、Stop Hook 触发，后台 Fork Agent 再判断哪些内容值得写入记忆。它不是把当前对话完整保存，而是提炼成 user、feedback、project、reference 等类型的文件。

Team Memory：团队共享，但要更谨慎

Team Memory 面向多人协作，会把适合共享的项目记忆同步到团队范围。因为它跨用户，所以需要额外处理同步冲突、路径安全和秘密扫描。文章主线只需要知道：这是 Persistent Memory 的团队化扩展，不是每个场景都必须启用。

工程观点Claude Code 的记忆不是“记得越多越好”，而是把信息分层：当前会话用 Session Memory 支撑压缩；跨会话用文件化 Persistent Memory 留下可审查的经验；团队协作再扩展到 Team Memory。

如果你要做自己的 Agent 系统，真正值得抄什么？

先做清楚角色边界不要一开始就追求“很多 Agent”。先定义谁负责规划、谁负责执行、谁负责验证、谁负责和用户确认。
工具权限要写在代码里只读 Agent 就真的只给 Read/Grep；规划 Agent 就不要给 Bash/Edit。不要只靠 prompt 约束。
并行写代码必须有隔离战场如果 Worker 会写文件，就要考虑 worktree、分支、沙箱或临时目录，否则并行很快变成互相覆盖。
通信可以先从文件开始本地 Agent 场景里，JSON 文件 + 文件锁比 Redis/MQ 更容易部署、更容易排查。
把探索过程和最终结论分开Worker 可以产生很多中间噪音，但回传给 Leader 的应该是压缩后的结论、证据和建议。
缓存优化不是锦上添花系统 prompt、工具描述、配置顺序越稳定，Prompt Cache 越容易命中，成本和响应速度都会改善。
记忆要可读、可审计、可修改对本地开发工具来说，文件化记忆往往比黑盒向量库更容易获得用户信任。
