# 大模型基础-01

## 1. Transformer 中 Attention 的本质是什么？

**问题：** Transformer 中 Attention 的本质是什么？

**答案：**

Attention 的本质是让模型在处理当前 token 时，动态决定应该关注输入序列里的哪些 token，并按相关性对它们的信息做加权聚合。

更直白地说，Attention 不是固定看前一个词或固定看某个窗口，而是让每个 token 都可以根据当前语义，从整段上下文里“查找对自己有用的信息”。

在 Transformer 里，Self-Attention 通常用 Q、K、V 来理解：

```text
Q：Query，当前 token 想找什么信息
K：Key，每个 token 能提供什么索引特征
V：Value，每个 token 真正携带的信息内容
```

计算过程可以简化成：

```text
当前 token 的 Q
  -> 和所有 token 的 K 计算相似度
  -> 得到 attention score
  -> softmax 变成权重
  -> 用权重加权所有 token 的 V
  -> 得到当前 token 的上下文表示
```

所以 Attention 的核心不是“注意力”这个名字，而是一个可学习的动态信息路由机制：模型根据当前 token 和其他 token 的关系，决定信息从哪里流向哪里。

它解决了 RNN/CNN 里的一些限制：

- **长距离依赖：** 任意两个 token 可以直接建立联系。
- **并行计算：** 不需要像 RNN 一样严格按时间步递推。
- **动态权重：** 不同输入里，同一个位置关注的内容可以不同。
- **上下文建模：** 每个 token 的表示都能融合全局上下文。

Multi-Head Attention 则是在多个子空间里同时做 attention。不同 head 可以学习不同关系，比如语法依赖、指代关系、实体关系、位置关系、局部搭配等。最后把多个 head 的结果拼接起来，让表示更丰富。

不过 Attention 本身不等于理解。它只是提供了一种信息选择和聚合机制，真正的能力来自大规模参数、训练数据、层叠结构、位置编码、FFN 和训练目标共同作用。

**面试可以这样说：**

Transformer 里 Attention 的本质是动态信息路由。每个 token 会生成 Query，和所有 token 的 Key 计算相关性，再用 softmax 得到权重，对对应的 Value 做加权求和，形成当前 token 的上下文表示。它让模型不再固定按顺序或固定窗口取信息，而是根据语义关系动态决定关注谁。Self-Attention 解决了长距离依赖和并行计算问题，Multi-Head Attention 则让模型在不同子空间里学习不同关系。简单说，Attention 做的事情就是：当前 token 根据需要，从上下文中选择并聚合最有用的信息。

## 2. LoRA 微调的原理是什么？

**问题：** LoRA 微调的原理是什么？

**答案：**

LoRA 的核心思想是：不直接更新大模型原始权重，而是在某些线性层旁边增加一个低秩增量矩阵，只训练这个小的增量部分。

普通全量微调会直接更新原始权重：

```text
W -> W'
```

LoRA 则把更新写成：

```text
W' = W + ΔW
ΔW = B A
```

其中：

- `W` 是冻结的原始权重。
- `ΔW` 是训练出来的权重增量。
- `A` 和 `B` 是两个低秩矩阵。
- rank `r` 通常远小于原始矩阵维度。

如果原始权重 `W` 是一个很大的矩阵，直接训练它参数量很大。LoRA 假设模型适配一个新任务时，不需要在完整高维空间里更新所有参数，只需要一个低秩的变化方向就够了。所以它用两个小矩阵 `A`、`B` 近似表示权重变化。

这样做的好处：

- **训练参数少：** 只训练 LoRA adapter，不训练整个模型。
- **显存占用低：** 优化器状态和梯度都少很多。
- **训练成本低：** 比全量微调更便宜。
- **方便多任务切换：** 底座模型不变，不同任务加载不同 LoRA adapter。
- **部署灵活：** LoRA 权重可以单独保存，也可以 merge 回原模型权重。

LoRA 通常加在 Transformer 的线性层上，比如 attention 里的 `q_proj`、`k_proj`、`v_proj`、`o_proj`，或者 FFN 里的 projection 层。实际加哪些层，会影响效果、成本和训练稳定性。

需要注意的是，LoRA 不是让模型“学新知识”的万能方案。它更适合让模型适配特定任务格式、表达风格、领域模式或工具调用习惯。如果是大量事实知识频繁更新，通常 RAG 更合适；如果要彻底改变基础能力，全量微调或继续预训练可能更合适。

**面试可以这样说：**

LoRA 是一种参数高效微调方法。它不直接更新大模型原始权重，而是冻结原模型，在部分线性层上加一个低秩增量 `ΔW = BA`，训练时只更新这两个小矩阵。因为 rank 很小，所以训练参数、显存和优化器状态都大幅减少。推理时可以把 LoRA adapter 挂在原模型上，也可以 merge 回原权重。它适合做任务适配、风格适配、领域表达和格式对齐，不适合把频繁变化的大量事实知识硬训进模型；那类问题通常优先用 RAG。

## 3. 了解 RLHF 吗？DPO 和 PPO 有什么区别？Loss 是怎么样的？各自的优缺点是什么？

**问题：** 了解 RLHF 吗？DPO 和 PPO 有什么区别？Loss 是怎么样的？各自的优缺点是什么？

**答案：**

RLHF 是 Reinforcement Learning from Human Feedback，用人类偏好来对齐模型输出。典型流程是：

```text
预训练模型
  -> SFT：用高质量指令数据做监督微调
  -> Reward Model：用人类偏好数据训练奖励模型
  -> RL 优化：用 PPO 等算法优化策略模型
```

PPO 和 DPO 都是让模型更符合偏好的方法，但思路不同。

**1. PPO 是显式强化学习**

PPO 会先训练一个 Reward Model。然后当前策略模型生成回答，Reward Model 给奖励，再用强化学习更新模型，同时加 KL 约束，避免模型偏离参考模型太远。

PPO 优化目标可以简化理解为：

```text
maximize:
reward(x, y) - β * KL(πθ(y|x) || πref(y|x))
```

更标准的 PPO 会用 clipped objective：

```text
L_PPO = E[min(r_t(θ) A_t, clip(r_t(θ), 1-ε, 1+ε) A_t)]
```

其中：

- `r_t(θ)` 是新旧策略概率比。
- `A_t` 是 advantage，表示这个动作比平均水平好多少。
- `clip` 用来限制更新幅度，避免策略一步更新太大。
- 实际训练还会加 value loss、entropy bonus、KL penalty 等项。

PPO 的优点是灵活，可以直接优化奖励模型，也适合多轮交互、复杂 reward、在线采样。缺点是训练复杂、成本高、稳定性差，对 reward model、KL 系数、采样策略和超参数很敏感。

**2. DPO 是直接偏好优化**

DPO 不再单独训练 Reward Model，也不跑强化学习采样循环，而是直接用偏好数据训练模型。偏好数据通常长这样：

```text
prompt x
chosen y_w：人类更喜欢的回答
rejected y_l：人类不喜欢的回答
```

DPO 的核心 loss 是让模型相对参考模型，更倾向于 chosen，而不是 rejected：

```text
L_DPO = - log σ(
  β * [
    log πθ(y_w|x) - log πθ(y_l|x)
    - log πref(y_w|x) + log πref(y_l|x)
  ]
)
```

直观理解：

- 如果当前模型比参考模型更偏向 chosen，loss 就小。
- 如果当前模型仍然偏向 rejected，loss 就大。
- `β` 控制偏离参考模型的强度。

DPO 的优点是简单、稳定、成本低，不需要训练 Reward Model，也不需要 PPO 的在线采样和复杂 RL pipeline。缺点是它依赖离线偏好数据，优化形式没有 PPO 灵活，对偏好数据质量很敏感，也不如 PPO 适合复杂、多步、在线环境反馈。

**3. PPO 和 DPO 的核心区别**

| 对比点 | PPO | DPO |
|---|---|---|
| 是否需要 Reward Model | 需要 | 不需要显式 RM |
| 是否是强化学习 | 是 | 更像监督式偏好优化 |
| 数据形式 | prompt + 采样回答 + reward | prompt + chosen/rejected |
| 训练复杂度 | 高 | 低 |
| 稳定性 | 较难调 | 更稳定 |
| 成本 | 高 | 低 |
| 灵活性 | 强，可接复杂 reward | 相对弱，依赖离线偏好对 |
| 适用场景 | 复杂 RLHF、在线反馈、多步任务 | 指令对齐、风格偏好、离线偏好优化 |

**4. 怎么选**

如果只是做模型回答风格、格式、安全偏好、拒答边界、通用对齐，DPO 通常更简单有效。  
如果要优化复杂奖励、多轮行为、工具使用策略、在线反馈或者需要显式 reward shaping，PPO 更有表达能力，但工程成本高很多。

**面试可以这样说：**

RLHF 是用人类偏好对齐模型，传统流程是 SFT、训练 Reward Model，再用 PPO 优化策略模型。PPO 是显式强化学习，目标大致是最大化 reward，同时用 KL 约束不要偏离 reference model 太远，实际会用 clipped objective、advantage、value loss 等，所以能力强但训练复杂、成本高、稳定性差。DPO 则把偏好优化改成一个更简单的监督学习问题，直接用 chosen/rejected 数据训练模型，loss 本质上是让当前模型相对 reference model 更偏向 chosen 而不是 rejected。DPO 不需要 Reward Model 和在线 RL 采样，简单稳定、成本低；但它依赖高质量离线偏好数据，灵活性不如 PPO。简单说：PPO 更强但更重，DPO 更简单稳定，工程里很多对齐场景会优先用 DPO。

## 4. 常用的向量索引算法有哪些？

**问题：** 常用的向量索引算法有哪些？

**答案：**

向量索引的目标是做最近邻检索，也就是在大量 embedding 里快速找到和 query 向量最相似的 TopK。小规模数据可以暴力扫全量向量，但数据量大后通常要用 ANN，也就是 Approximate Nearest Neighbor，牺牲一点精确率换检索速度和成本。

常见算法可以分几类：

**1. Flat / Brute Force**

Flat 就是全量扫描，逐个计算 query 和所有向量的相似度。

- 优点：结果最准，召回率最高。
- 缺点：数据量大时慢，成本高。
- 适合：小数据集、评测基线、需要精确召回的场景。

**2. IVF：倒排文件索引**

IVF 会先用聚类把向量空间分成多个簇。查询时先找到 query 最接近的几个簇，只在这些簇里搜索。

```text
向量 -> 聚类中心
查询 -> 找最近的 nprobe 个簇 -> 在簇内搜索
```

- 优点：速度快，适合大规模数据。
- 缺点：如果簇选错，相关向量可能召不回来。
- 关键参数：`nlist`、`nprobe`。

**3. PQ / OPQ：乘积量化**

PQ 会把高维向量切成多个子向量，每个子向量用码本近似表示，从而压缩存储和加速距离计算。OPQ 是在 PQ 前做旋转变换，让量化误差更小。

- 优点：极大降低内存占用。
- 缺点：量化会损失精度。
- 适合：超大规模向量、内存敏感场景。

**4. HNSW：图索引**

HNSW 会构建一个多层近邻图。查询时从高层快速定位大致区域，再逐层向下搜索更精确的近邻。

- 优点：召回高、速度快，工程中很常用。
- 缺点：建索引和内存成本较高。
- 关键参数：`M`、`efConstruction`、`efSearch`。

**5. LSH：局部敏感哈希**

LSH 用哈希函数把相似向量映射到相同或相近桶里，查询时只看相关桶。

- 优点：理论简单，适合某些近似检索。
- 缺点：实际效果和调参不如 HNSW/IVF 常用。

**6. Annoy / ScaNN / Faiss 等工程实现**

这些更像向量检索库或实现：

- **Faiss：** 支持 Flat、IVF、PQ、HNSW、GPU 检索等。
- **Annoy：** 基于随机投影树，适合静态索引。
- **ScaNN：** Google 的向量检索方案，强调速度和压缩。
- **Milvus、Qdrant、Weaviate、pgvector：** 更偏向量数据库或系统实现。

**怎么选：**

- 数据量小、要精确：Flat。
- 数据量大、希望速度快：HNSW 或 IVF。
- 内存压力大：IVF + PQ / OPQ。
- 召回率要求高、内存够：HNSW。
- 需要 GPU、大规模实验：Faiss。
- 需要业务系统能力：向量数据库 + metadata filter。

**面试可以这样说：**

常用向量索引可以分成几类。Flat 是暴力全量扫描，最准但慢，适合小规模或评测基线。IVF 是倒排文件索引，先把向量聚类，查询时只搜部分簇，速度快但可能漏召回。PQ/OPQ 是量化压缩，用更小存储近似表示向量，适合超大规模和内存敏感场景。HNSW 是图索引，通过多层近邻图快速搜索，召回和速度都很好，是工程里很常用的方案。LSH 是哈希近似检索，但实际工程里不如 HNSW、IVF 常见。选型主要看数据规模、召回要求、延迟、内存、更新频率和是否需要 metadata filter。

## 5. Prompt 怎么优化？

**问题：** Prompt 怎么优化？

**答案：**

Prompt 优化不是单纯把提示词写得更长，而是让模型更清楚任务目标、输入边界、输出格式、判断标准和失败时该怎么处理。核心目标是提升稳定性、可控性和可评估性。

常见优化思路：

**1. 明确任务目标**

不要只写“帮我分析一下”，而要写清楚模型要完成什么：

```text
你需要判断用户问题是否属于售后退款，并输出结构化分类结果。
```

**2. 明确角色和边界**

角色不是越花哨越好，关键是边界清楚：

- 能做什么。
- 不能做什么。
- 遇到不确定时怎么办。
- 是否允许编造。
- 是否必须基于证据回答。

**3. 给出输入结构**

把不同来源的信息分区：

```text
用户问题：
...

检索证据：
...

工具结果：
...

历史摘要：
...
```

这样可以减少模型把用户输入、系统规则、检索内容和工具结果混在一起。

**4. 明确输出格式**

如果需要稳定接系统，最好用 JSON schema 或固定字段：

```json
{
  "intent": "",
  "confidence": 0.0,
  "need_clarification": false,
  "answer": ""
}
```

**5. 增加少量高质量示例**

Few-shot 示例要覆盖：

- 正常样本。
- 边界样本。
- 反例。
- 不确定时的处理。

示例不需要很多，但要和线上真实问题相似。

**6. 加约束和兜底**

比如：

- 证据不足时不要编造。
- 缺关键字段时追问。
- 多来源冲突时说明冲突。
- 高风险操作需要确认。
- 输出必须只包含指定格式。

**7. 控制上下文长度**

Prompt 不是越长越好。太长会导致：

- 成本和延迟上升。
- 关键信息被埋掉。
- 多个规则互相冲突。
- 模型注意力分散。

所以要做 token 预算、去重、摘要、证据筛选和优先级排序。

**8. 用评测集迭代，而不是凭感觉改**

Prompt 优化一定要有测试集。每次改 prompt，要看：

- 准确率是否提升。
- 幻觉率是否下降。
- 格式错误率是否下降。
- 追问是否合理。
- 对边界 case 是否更稳定。
- 是否引入新的回归问题。

**面试可以这样说：**

我优化 prompt 不会只靠感觉加几句话，而是先明确任务目标、输入边界、输出格式和失败兜底。结构上会把 system 规则、用户问题、检索证据、工具结果、历史摘要分区，避免信息混淆；输出尽量用固定字段或 JSON schema，方便系统校验。对于不稳定场景，会加少量高质量 few-shot，覆盖正例、反例和边界 case。同时控制上下文长度，避免无关信息太多导致注意力分散。最后一定用评测集迭代，看准确率、格式错误率、幻觉率、拒答/追问是否合理，而不是每次线上出错就凭感觉改 prompt。

## 6. 简述 vLLM 推理框架的核心原理，它是怎么解决高并发显存瓶颈的？

**问题：** 简述 vLLM 推理框架的核心原理，它是怎么解决高并发显存瓶颈的？

**答案：**

vLLM 是一个面向大模型推理服务的高吞吐框架。它的核心目标是提高 GPU 利用率，降低高并发场景下 KV cache 带来的显存浪费。

大模型推理时，主要有两个阶段：

```text
prefill：处理输入 prompt，生成第一批 KV cache
decode：逐 token 生成，每生成一个 token 都要复用历史 KV cache
```

高并发下真正容易卡住的不是模型权重，而是 **KV cache 显存**。每个请求都要保存自己的历史 key/value，而且不同请求长度不同、生成长度不确定。如果传统方式为每个请求预留连续显存，容易出现：

- 预分配过多，短请求浪费显存。
- 请求长度动态增长，显存不好管理。
- 连续内存碎片多，明明总显存够但分配不出来。
- batch size 被 KV cache 限制，吞吐上不去。

vLLM 的核心创新是 **PagedAttention**。它借鉴操作系统虚拟内存分页的思想，把每个请求的 KV cache 切成固定大小的 block，不要求物理显存连续。

可以理解成：

```text
传统方式：
一个请求的 KV cache 必须占一大段连续显存

PagedAttention：
一个请求的 KV cache 被切成多个 block
逻辑上连续，物理上可以分散存放
通过 block table 找到每个 token 对应的 KV block
```

这样带来的好处是：

- **按需分配：** 请求生成到哪里，就分配到哪里，不用按最大长度预留。
- **减少碎片：** block 可以复用和回收，不依赖大块连续显存。
- **提升并发：** 同样显存下能容纳更多请求的 KV cache。
- **支持共享：** 多个请求共享相同 prefix 时，可以复用部分 KV block。
- **更适合动态 batching：** 不同长度请求可以更高效地混在一起执行。

除了 PagedAttention，vLLM 还依赖 **continuous batching**。普通 batching 往往一批请求一起开始、一起结束，慢请求会拖住整批。Continuous batching 会在每个 decode step 动态调度：有请求结束就移出，有新请求就加入，让 GPU 尽量一直有活干。

```text
请求 A 正在 decode
请求 B 结束 -> 释放 KV block
请求 C 进来 -> 复用空闲 block，加入 batch
```

所以 vLLM 解决高并发显存瓶颈，主要不是靠“减少模型权重”，而是靠更高效地管理 KV cache：

- PagedAttention 管 KV cache 显存。
- Block table 管逻辑 token 到物理 block 的映射。
- Continuous batching 提高 GPU 计算利用率。
- Prefix cache / KV block 复用减少重复计算。
- 调度器根据 token budget、sequence 数和 KV cache 空间安排请求。

**面试可以这样说：**

vLLM 的核心是把 LLM serving 里最容易浪费的 KV cache 管起来。传统推理框架通常给每个请求分配连续 KV cache，长短请求混在一起时会有大量预分配和碎片，高并发下 batch size 很快被显存卡住。vLLM 用 PagedAttention，把 KV cache 切成固定大小的 block，逻辑上连续、物理上可以不连续，通过 block table 做映射，按需分配和回收。这样短请求不会浪费大块显存，长请求也不需要连续显存，多个请求还可以共享 prefix 的 KV block。同时 vLLM 用 continuous batching，在每个 decode step 动态加入和移除请求，提高 GPU 利用率。简单说，vLLM 通过分页式 KV cache 管理 + 连续批处理，解决高并发下 KV cache 显存碎片和利用率低的问题。

## 8. 描述 Transformer 的基本结构，并解释自注意力机制

**问题：** 描述 Transformer 的基本结构，并解释自注意力机制。

**答案：**

Transformer 的核心结构可以理解成：用多层堆叠的 Attention 和前馈网络，对序列里的每个 token 做上下文建模。它不依赖 RNN 那种逐步递归，而是通过自注意力让序列中任意位置的 token 直接建立关系。

**1. Transformer 的基本结构**

经典 Transformer 包括 Encoder 和 Decoder 两部分：

```text
Input Embedding
  + Positional Encoding
  -> Encoder Blocks
  -> Decoder Blocks
  -> Linear + Softmax
```

Encoder Block 通常包括：

```text
Multi-Head Self-Attention
  -> Add & Norm
  -> Feed Forward Network
  -> Add & Norm
```

Decoder Block 通常包括：

```text
Masked Multi-Head Self-Attention
  -> Add & Norm
  -> Cross-Attention
  -> Add & Norm
  -> Feed Forward Network
  -> Add & Norm
```

现在很多大语言模型是 decoder-only 结构，比如 GPT 类模型，主要由多层 masked self-attention + FFN 堆叠组成，用来做自回归生成。

**2. 为什么需要位置编码**

Self-Attention 本身不天然知道 token 的顺序。如果只看 attention，输入 `[我, 喜欢, 你]` 和 `[你, 喜欢, 我]` 的 token 集合很像，所以需要 positional encoding 或 position embedding 把位置信息加入 token 表示里。

**3. 自注意力机制怎么做**

Self-Attention 的核心是让每个 token 根据当前上下文，决定应该关注序列里的哪些 token。

对每个 token，模型会从它的 hidden state 映射出三组向量：

```text
Q = Query：我想找什么信息
K = Key：我能提供什么索引
V = Value：我真正携带的信息内容
```

然后用当前 token 的 Q 和所有 token 的 K 做相似度计算：

```text
score = QK^T / sqrt(d_k)
weight = softmax(score)
output = weight * V
```

含义是：当前 token 先和所有 token 算相关性，再把相关性变成权重，最后按权重对所有 token 的 Value 做加权求和，得到融合上下文后的新表示。

**4. Multi-Head Attention 的作用**

单个 attention head 只能在一个表示子空间里看关系。Multi-Head Attention 会并行做多组 Q/K/V，让不同 head 学不同关系：

- 有的 head 关注相邻词。
- 有的 head 关注主谓宾关系。
- 有的 head 关注指代关系。
- 有的 head 关注长距离依赖。

最后把多个 head 的结果拼接，再经过线性层融合。

**5. Masked Self-Attention**

在生成式模型里，预测下一个 token 时不能提前看到未来 token，所以 decoder-only 模型会用 causal mask：

```text
第 t 个 token 只能看 <= t 的位置
不能看 t 之后的位置
```

这样模型才能按从左到右的方式自回归生成。

**6. FFN、残差和归一化的作用**

Attention 负责 token 之间的信息交互，FFN 负责对每个位置的表示做非线性变换。残差连接让深层网络更容易训练，LayerNorm 让训练更稳定。

所以一个 Transformer block 不是只有 Attention，而是：

```text
信息交互：Attention
非线性变换：FFN
训练稳定：Residual + LayerNorm
顺序信息：Position Encoding
```

**面试可以这样说：**

Transformer 的基本结构是多层 block 堆叠，每个 block 主要由 self-attention、feed forward network、残差连接和 LayerNorm 组成，输入 token 会先经过 embedding，再加上位置编码。经典 Transformer 有 encoder 和 decoder，encoder 做双向上下文编码，decoder 用 masked self-attention 做自回归生成；现在很多大模型是 decoder-only。自注意力机制的核心是每个 token 生成 Q、K、V，用 Q 和所有 token 的 K 计算相关性，经过 softmax 得到权重，再对 V 做加权求和，得到融合上下文的信息。Multi-head attention 则是在多个子空间并行学习不同关系，比如局部搭配、语法依赖、指代和长距离依赖。简单说，Self-Attention 让每个 token 能动态选择并聚合序列中对自己最有用的信息。

## 9. Transformer 输入向量维度是多少？为什么 Attention 要除以 sqrt(d_k)？LayerNorm 对哪个维度做？

**问题：** 输入向量的维度是多少？为什么在计算注意力时要除以 `sqrt(d_k)`？LayerNorm 是对哪个维度做？

**答案：**

这三个点都和 Transformer 的张量形状有关。最常见的输入形状可以写成：

```text
X: [batch_size, seq_len, d_model]
```

其中 `d_model` 是每个 token 的隐藏表示维度，也就是 embedding 后进入 Transformer block 的向量维度。

**1. 输入向量维度是多少**

每个 token 先被映射成一个 embedding 向量，维度通常是 `d_model`。

例如：

```text
batch_size = 2
seq_len = 128
d_model = 768

输入 X 的形状就是 [2, 128, 768]
每个 token 的向量维度是 768
```

不同模型的 `d_model` 不一样：

- BERT-base：`d_model = 768`
- GPT-2 small：`d_model = 768`
- LLaMA 7B：`d_model = 4096`

注意：token id 本身只是一个整数，真正进入 Transformer 的是查 embedding table 后得到的 dense vector。

**2. Q、K、V 的维度关系**

Self-Attention 会把输入 `X` 线性映射成 Q、K、V：

```text
Q = X W_Q
K = X W_K
V = X W_V
```

在多头注意力里，通常有：

```text
d_k = d_model / num_heads
```

例如：

```text
d_model = 768
num_heads = 12
d_k = 64
```

每个 head 用 64 维的 Q/K/V 做注意力，多个 head 的结果再拼回 `d_model` 维。

**3. 为什么要除以 sqrt(d_k)**

Attention 的打分是点积：

```text
score = QK^T
```

如果 `d_k` 比较大，Q 和 K 的点积方差会随维度增大而变大，score 的数值可能变得很大。进入 softmax 后会出现分布过尖的问题：

```text
softmax([20, 1, 0]) 约等于 [接近 1, 接近 0, 接近 0]
```

这样梯度会变小，训练不稳定，模型也容易过早把注意力集中到少数位置。

所以要做缩放：

```text
score = QK^T / sqrt(d_k)
```

除以 `sqrt(d_k)` 的作用是把点积分数的尺度拉回比较稳定的范围，让 softmax 不至于过度饱和。

**4. LayerNorm 是对哪个维度做**

在 Transformer 里，LayerNorm 通常是对每个 token 的 hidden dimension 做归一化，也就是对最后一维 `d_model` 做。

如果输入是：

```text
X: [batch_size, seq_len, d_model]
```

那么 LayerNorm 对每个样本、每个位置的 `d_model` 维向量单独算均值和方差：

```text
对 X[b, t, :] 做归一化
```

也就是：

- 不跨 batch 做归一化。
- 不跨 seq_len 做归一化。
- 只在每个 token 自己的 hidden 维度上做归一化。

这和 BatchNorm 不同。BatchNorm 通常依赖 batch 统计量，而 LayerNorm 对单个样本内部做归一化，更适合 NLP 里变长序列和小 batch 场景。

**面试可以这样说：**

Transformer 里输入通常是 `[batch_size, seq_len, d_model]`，每个 token 经过 embedding 后是一个 `d_model` 维向量，比如 768、1024、4096 都是常见 hidden size。多头注意力会把它投影成 Q、K、V，每个 head 的维度一般是 `d_k = d_model / num_heads`，比如 `768 / 12 = 64`。计算注意力时要除以 `sqrt(d_k)`，因为 Q 和 K 的点积会随着维度增大而变大，直接进 softmax 会让分布过尖、梯度变小，缩放后训练更稳定。LayerNorm 在 Transformer 里通常对最后一维 hidden dimension 做，也就是对每个 token 的 `d_model` 维向量单独归一化，不跨 batch，也不跨序列长度。

## 10. 为什么缓存的是 KV？为什么 Q 不缓存？

**问题：** 为什么缓存的是 KV？为什么 Q 不缓存？

**答案：**

在自回归推理里，KV cache 的目的不是缓存所有中间变量，而是避免每生成一个新 token 时，重复计算历史 token 的 Key 和 Value。Q 不缓存，是因为每一步真正需要的是“当前新 token 的 Query”，历史 token 的 Query 后续基本不会再被用到。

**1. 自回归生成每一步在做什么**

生成第 `t` 个 token 时，当前 token 的 Q 要和历史所有 token 的 K 做 attention：

```text
Q_t  x  [K_1, K_2, ..., K_t]
  -> attention weights
  -> 加权 [V_1, V_2, ..., V_t]
  -> 当前 token 的输出表示
```

也就是说，当前步需要：

- 当前 token 的 `Q_t`
- 历史和当前所有 token 的 `K_1 ... K_t`
- 历史和当前所有 token 的 `V_1 ... V_t`

历史 token 的 `Q_1 ... Q_{t-1}` 不再参与当前 token 的计算。

**2. 为什么 K/V 要缓存**

如果不缓存 K/V，每生成一个新 token，都要把整个历史序列重新过一遍 Transformer，重新算所有历史 token 的 K/V。

例如已经有 1000 个历史 token，现在生成第 1001 个 token：

```text
不缓存：
重新计算 1...1001 所有 token 的 K/V

缓存 KV：
只计算新 token 的 K_1001、V_1001
历史 K_1...K_1000、V_1...V_1000 直接复用
```

这样可以大幅减少 decode 阶段的重复计算。

**3. 为什么 Q 不缓存**

Q 的作用是“当前 token 拿什么去查历史信息”。在生成第 `t` 个 token 时，只需要 `Q_t` 去查询历史 K/V。

历史 `Q` 的作用已经在历史 token 生成时用完了：

```text
生成 token 10 时，用 Q_10 查询 K_1...K_10
生成 token 11 时，用 Q_11 查询 K_1...K_11

Q_10 不需要再拿出来参与 token 11 的计算
```

所以缓存历史 Q 没有收益，只会浪费显存。

**4. 从 Attention 公式看**

单步 decode 时可以写成：

```text
Attention(Q_t, K_cache, V_cache)
  = softmax(Q_t K_cache^T / sqrt(d_k)) V_cache
```

这里 `Q_t` 是当前步新算的，`K_cache` 和 `V_cache` 是历史缓存。公式里没有用到历史 `Q_cache`。

**5. 为什么训练时通常不需要 KV cache**

训练阶段通常一次性并行处理完整序列：

```text
Q, K, V = XW_Q, XW_K, XW_V
```

所有 token 的 Q/K/V 可以并行算出来，不是逐 token decode，所以 KV cache 主要是推理优化，不是训练必需结构。

**6. KV cache 的代价**

KV cache 提升 decode 速度，但会占用显存。每层、每个 head、每个历史 token 都要存 K 和 V：

```text
KV cache 大小大致和：
batch_size * seq_len * num_layers * num_heads * head_dim * 2
成正比
```

这里的 `2` 就是 K 和 V 两份缓存。

**面试可以这样说：**

自回归推理里缓存 KV，是因为生成当前 token 时，需要用当前 token 的 Q 去和所有历史 token 的 K 计算注意力权重，再对历史 V 做加权求和。历史 token 的 K/V 每一步都会被后续 token 反复用到，所以缓存它们可以避免重复计算。Q 不缓存，是因为 Q 只代表当前 token 的查询向量，历史 token 的 Q 在当时生成它自己的输出时已经用完了，后续生成新 token 时只需要新的 `Q_t`，不会再用历史 `Q_1...Q_{t-1}`。从公式看，decode 阶段是 `Attention(Q_t, K_cache, V_cache)`，里面根本不需要 `Q_cache`。所以 KV cache 是有收益的，Q cache 只会多占显存。

## 11. 为什么很多场景会优先选 RAG，而不是直接微调大模型？

**问题：** 为什么很多场景会优先选 RAG，而不是直接微调大模型？

**答案：**

很多业务场景优先选 RAG，不是因为微调没用，而是因为两者解决的问题不同。RAG 更适合解决“知识接入、知识更新、事实依据和可追溯”的问题；微调更适合解决“模型行为、任务格式、领域表达和稳定输出”的问题。

**1. 业务知识经常更新**

企业知识库、产品文档、政策制度、价格规则、接口文档、合同条款都可能经常变化。

如果靠微调把这些知识训进模型：

- 每次知识更新都要重新准备数据和训练。
- 训练周期长，更新不及时。
- 模型可能仍然记住旧知识。
- 很难确定模型到底用了哪个版本的知识。

RAG 只需要更新文档、chunk、索引和 metadata，模型回答时检索最新证据，更适合动态知识。

**2. RAG 可引用、可追溯**

很多业务问答不能只给一个看起来合理的答案，还要知道依据来自哪里。

RAG 可以返回：

- 文档标题。
- 页码或章节。
- 版本号。
- 发布时间。
- 具体引用片段。
- 用户是否有权限访问该证据。

微调后的模型即使答对，也很难解释“这句话依据哪份文档”，不适合强审计、强合规、强事实依据的场景。

**3. 成本和迭代速度更友好**

微调需要高质量数据、训练资源、评测集、训练流程和上线流程。即使用 LoRA，仍然要做数据清洗、训练、验证、部署和回滚。

RAG 的迭代通常更快：

- 新文档入库。
- 调整 chunk。
- 优化 query rewrite。
- 调整 embedding / rerank。
- 增加 metadata 过滤。
- 更新检索策略。

这些改动通常比重新训练模型更轻，回滚也更容易。

**4. 私有知识不一定适合训练进模型**

企业内部知识可能包含权限、租户、客户信息、合同、财务、工单、代码、日志等敏感内容。

如果直接训练进模型，会有几个问题：

- 数据合规和隐私风险更高。
- 不同租户、不同权限的数据容易混在一起。
- 用户删除或更新数据后，很难保证模型“忘掉”。
- 模型可能在无权限场景下泄露记忆中的内容。

RAG 可以在检索阶段做租户隔离、资源级权限、版本过滤和脱敏，更适合企业知识管理。

**5. 微调不擅长精确记忆大量事实**

微调可以让模型更会按某种格式回答、更懂某类任务模式，但不适合把大量细碎、变化频繁的事实硬塞进参数里。

比如：

- 某个产品当前价格。
- 某个接口最新字段。
- 某个政策生效日期。
- 某个订单状态。
- 某份文档第几条规则。

这些更适合通过 RAG 或实时 API 提供，而不是靠模型参数记忆。

**6. 什么时候才考虑微调**

如果问题不是知识更新，而是模型行为不稳定，就可以考虑微调。

适合微调的情况：

- 意图分类、信息抽取、结构化输出长期不稳定。
- 需要统一话术风格、语气、格式。
- 有大量稳定、高质量标注数据。
- 任务边界清楚，线上分布稳定。
- RAG 和 prompt 已经解决不了模型行为问题。

实际工程里经常组合使用：

```text
RAG：提供最新知识和可引用证据
微调：提升任务格式、领域表达和工具调用稳定性
规则/Workflow：保证权限、流程和高风险边界
```

**面试可以这样说：**

很多场景优先选 RAG，是因为问题本质是知识更新和事实依据，而不是模型能力不足。企业文档、政策、产品手册、接口说明、合同条款这些知识经常变化，如果靠微调，每次更新都要重新训练、评测和上线，成本高、周期长，还可能让模型记住旧知识。RAG 只需要更新文档和索引，回答时检索最新证据，而且能给出来源、版本、页码和引用，方便审计和排查。另一个原因是权限和合规，企业私有知识不适合全部训进模型参数里，RAG 可以在检索阶段做租户隔离、权限过滤和脱敏。微调更适合解决模型行为问题，比如分类、抽取、格式、话术风格和工具调用稳定性；RAG 更适合解决动态知识、私有知识和可追溯事实。工程里通常不是二选一，而是 RAG 管知识，微调管行为，规则和 Workflow 管权限与业务边界。

## 12. 为什么现在 decoder-only 成为大模型的主流架构？相比 encoder-decoder 好在哪里？

**问题：** 为什么现在 decoder-only 成为大模型的主流架构？相比于 encoder-decoder 的架构好在哪里？

**答案：**

decoder-only 成为大语言模型主流，不是因为 encoder-decoder 不好，而是因为当前大模型的核心任务是“通用文本生成和对话”，decoder-only 的自回归建模目标、训练数据形式、推理方式和工程扩展性都更匹配这个方向。

**1. 训练目标更简单统一**

decoder-only 通常做 next token prediction：

```text
给定前文 token_1 ... token_t
预测下一个 token_{t+1}
```

这个目标非常简单，几乎所有文本都能直接拿来训练，不需要构造输入输出对。

encoder-decoder 更自然适合 seq2seq 任务：

```text
输入序列 -> 输出序列
```

比如翻译、摘要、改写。它当然也能做生成，但大规模通用预训练时，decoder-only 的“续写式”目标和互联网文本、代码、对话数据更天然匹配。

**2. 更适合开放式生成和对话**

现在的大模型主要服务：

- 聊天。
- 续写。
- 代码生成。
- 推理过程生成。
- 工具调用 JSON 生成。
- 多轮上下文下的回答。

这些都可以统一成“把 prompt 当作前缀，然后继续生成”。decoder-only 正好就是这种模式：输入、指令、历史对话、工具结果、示例都拼成一个序列，模型从左到右生成后续 token。

encoder-decoder 需要把输入放 encoder，输出放 decoder，结构上更像明确的“输入到输出转换”。对翻译、摘要这类任务很合适，但对通用 prompt 续写和多轮对话，decoder-only 更直接。

**3. 架构更简单，扩展更容易**

decoder-only 只有一套 decoder block，主要是 masked self-attention + FFN。

encoder-decoder 有：

- encoder self-attention。
- decoder masked self-attention。
- encoder-decoder cross-attention。

cross-attention 会增加结构复杂度、参数、实现成本和推理管理复杂度。大模型扩到几百亿、上千亿参数时，架构越简单，训练、并行、部署和优化越容易。

**4. 推理缓存更直接**

decoder-only 自回归生成时，可以用 KV cache 缓存历史 token 的 K/V。每生成一个新 token，只需要计算新 token，并和历史 KV 做 attention。

encoder-decoder 也可以缓存 decoder 侧 KV，encoder 输出也可以复用，但它多了 encoder 输出和 cross-attention 管理。对长 prompt、多轮对话、长上下文生成来说，decoder-only 的推理路径更统一，工程优化也更集中。

**5. 数据利用率和任务统一性更好**

decoder-only 可以把很多任务都写成同一种格式：

```text
Instruction + Context + Examples + User Input -> Answer
```

分类、抽取、问答、翻译、摘要、代码生成都可以变成“生成目标文本”。这让预训练、SFT、RLHF/DPO、工具调用微调都能沿用同一套自回归框架。

encoder-decoder 对某些任务有天然优势，但不同任务的数据组织更偏输入输出对，通用化时没有 decoder-only 这么顺。

**6. 生态和规模效应**

GPT 系列、LLaMA、Qwen、DeepSeek 等主流生成式大模型都采用 decoder-only 或类似自回归架构。随着训练框架、推理引擎、KV cache、FlashAttention、PagedAttention、量化、并行策略都围绕 decoder-only 优化，生态会进一步强化这个选择。

这也是一个工程规模效应：不是 encoder-decoder 做不了，而是 decoder-only 在大规模通用生成模型上已经形成了更成熟的训练和推理基础设施。

**7. encoder-decoder 仍然有价值**

不能简单说 decoder-only 全面碾压 encoder-decoder。encoder-decoder 在一些场景仍然很合适：

- 翻译。
- 摘要。
- 语音识别里的 encoder-decoder。
- 多模态输入到文本输出。
- 输入和输出边界非常清楚的 seq2seq 任务。

它的优势是 encoder 可以双向理解完整输入，decoder 专注生成输出。但对通用 LLM 来说，decoder-only 用统一自回归目标就能覆盖足够多任务，扩展和部署更简单。

**面试可以这样说：**

decoder-only 成为主流，核心原因是它和现在大模型的主要形态最匹配：把所有任务统一成给定上下文后预测下一个 token。它的训练目标是 next token prediction，简单稳定，几乎所有文本、代码、对话都能直接用于预训练；推理时也很自然，把 system prompt、用户输入、历史对话、工具结果拼成一个前缀，然后自回归生成答案。相比 encoder-decoder，decoder-only 架构更简单，没有 encoder-decoder cross-attention，训练、并行、KV cache、推理部署和大规模扩展都更直接。encoder-decoder 在翻译、摘要、语音、多模态这类输入输出边界清楚的任务上仍然有价值，但通用聊天、代码生成、工具调用和开放式推理更像“续写”，所以 decoder-only 更适合作为通用大模型底座。简单说，encoder-decoder 更像专门的 seq2seq 转换器，decoder-only 更适合统一的通用生成模型。

## 13. RoPE 是什么？常用位置编码有哪些？RoPE 有什么优点，如何做长度外推？

**问题：** 讲一下 RoPE，目前常用的位置编码还有哪些？RoPE 有什么优点，如何进一步外推？

**答案：**

位置编码的作用是让 Transformer 感知 token 顺序。Self-Attention 本身只看 token 之间的相关性，如果不加位置信息，模型很难区分“我喜欢你”和“你喜欢我”。

**1. 常见位置编码**

常见方案包括：

- **绝对位置编码：** 原始 Transformer 的正弦/余弦位置编码，或可学习 position embedding。做法是给每个位置一个向量，加到 token embedding 上。
- **相对位置编码：** Attention 分数里显式加入 token 间相对距离，常见于 T5、Transformer-XL 等思路。
- **RoPE：** Rotary Position Embedding，把位置信息通过旋转矩阵作用到 Q、K 上。
- **ALiBi：** Attention with Linear Bias，在 attention score 上按距离加入线性惩罚，不显式学习位置向量。
- **长度扩展变体：** NTK-aware scaling、linear scaling、YaRN、LongRoPE 等，主要用于扩展 RoPE 模型的上下文长度。

**2. RoPE 的核心思想**

RoPE 不把位置向量直接加到 token embedding 上，而是对 Q、K 做按位置变化的旋转。

直观理解：

```text
位置 m 的 token：Q_m、K_m 旋转一个和 m 相关的角度
位置 n 的 token：Q_n、K_n 旋转一个和 n 相关的角度
Q_m 和 K_n 做点积时，天然包含相对距离 m - n
```

所以 RoPE 的一个关键优点是：它用绝对位置的旋转实现了相对位置信息。

**3. RoPE 的优点**

RoPE 常用于 decoder-only 大模型，主要优点是：

- **天然支持相对位置：** attention score 和 token 间相对距离有关。
- **适合自回归生成：** 对 Q/K 做变换，和 causal attention、KV cache 配合自然。
- **不额外增加大量参数：** 位置变换是确定性的，不像可学习位置 embedding 那样为每个位置存参数。
- **对长文本泛化更好：** 相比固定长度的 learned absolute embedding，更容易做一定长度外推。
- **实现简单高效：** 只是在 Q/K 上做旋转变换，工程上容易集成。

**4. RoPE 的外推问题**

RoPE 虽然比 learned absolute position 更适合长文本，但直接把上下文拉到训练长度之外也会出问题。原因是模型训练时只见过一定范围的位置频率和相对距离，推理时突然出现更大位置，旋转角度分布会超出训练分布，模型可能注意力混乱。

典型现象：

- 长上下文后半段效果下降。
- 中间信息容易被忽略。
- 长距离引用不稳定。
- 困惑度上升，回答开始漂移。

**5. RoPE 如何进一步外推**

常见做法有几类：

- **Position Interpolation / Linear Scaling：** 把推理时更长的位置压缩回训练长度范围内，相当于缩小位置 index，让模型看到的角度变化不要太超分布。
- **NTK-aware scaling：** 调整 RoPE 的 base 或频率分布，让低频维度适合更长距离，高频维度尽量保留局部分辨率。
- **YaRN：** 在插值基础上做更细的频率缩放和温度修正，兼顾长距离外推和短距离能力。
- **LongRoPE 等方法：** 对不同维度或不同位置范围使用非均匀缩放，并结合少量长上下文继续训练。
- **长上下文继续训练：** 只改缩放通常不够稳，工程上经常配合长序列数据继续预训练或 SFT，让模型真正适应长上下文。

**6. 外推的取舍**

做 RoPE 外推时要注意：

- 不是上下文窗口拉长，模型就一定能有效利用所有 token。
- 过度压缩位置会损失局部位置分辨率，影响短文本能力。
- 只做 scaling 可能能跑更长，但长距离检索、推理和引用仍要评测。
- 最好用 needle-in-a-haystack、长文 QA、长代码、长表格和真实业务长上下文评测，而不是只看最大长度。

**面试可以这样说：**

位置编码是为了解决 Self-Attention 不天然感知顺序的问题。常见方案有绝对位置编码、可学习位置 embedding、相对位置编码、RoPE 和 ALiBi。RoPE 的核心是不给 token embedding 直接加位置向量，而是在 Q、K 上按位置做旋转；两个位置的 Q/K 做点积时，会自然体现相对距离，所以它用绝对位置旋转实现了相对位置信息。RoPE 的优点是参数少、适合 decoder-only 自回归生成、和 KV cache 配合自然，并且比 learned absolute position 更容易做长上下文扩展。但 RoPE 直接外推到训练长度之外也会分布漂移，所以常用 linear scaling、NTK-aware scaling、YaRN、LongRoPE 这类方法调整位置频率或位置 index，把更长上下文映射到模型更熟悉的频率范围。真正生产里通常还要配合长上下文继续训练和长文评测，因为能扩窗口不代表模型真的会稳定利用长距离信息。

## 14. 幻觉怎么判断出来，如何解决？

**问题：** 幻觉怎么判断出来，如何解决？

**答案：**

大模型幻觉不是简单指“回答不符合预期”，而是模型生成了没有依据、与事实不符、与上下文矛盾或引用不成立的内容。判断幻觉要结合任务类型：开放创作里不一定严重，但企业知识库、医疗、法律、金融、运维、工具调用这类事实要求高的场景，必须严格判断。

**1. 怎么判断是不是幻觉**

常见判断方法有几类：

- **和权威事实对比：** 与数据库、API、知识库原文、标准答案或人工标注对比。
- **groundedness 检查：** 看答案中的每个关键结论是否能被给定上下文支持。
- **citation 检查：** 如果答案带引用，要检查引用是否来自本次检索、用户是否有权限、引用内容是否真的支持结论。
- **一致性检查：** 同一回答内部是否自相矛盾，是否和工具返回、task state、系统规则冲突。
- **unsupported claim 检测：** 抽取答案里的实体、数字、时间、政策条款、因果结论，看哪些没有证据来源。
- **反事实/多次采样检查：** 同一问题多次生成差异很大，或者换问法后结论不一致，说明不稳定。
- **人工评审和回归集：** 高风险场景要有人审，并把幻觉样本沉淀成测试集。

对 RAG 系统，我会重点看三件事：

```text
正确证据是否被召回？
正确证据是否进入最终上下文？
最终答案是否被上下文证据支持？
```

如果证据没召回，是检索问题；证据在上下文里但模型没用，是生成或上下文组织问题；答案引用不支持结论，是 citation/groundedness 问题。

**2. 幻觉常见来源**

常见原因包括：

- 用户问题本身含糊，模型猜了意图。
- 检索没有召回正确证据。
- 上下文里有噪声、旧版本文档或冲突证据。
- chunk 切分不合理，条件和结论被切开。
- prompt 没有要求基于证据回答。
- 模型为了完整性过度补全。
- 工具返回不完整，模型误读成确定结果。
- 高温采样或多轮上下文过长导致不稳定。

**3. 怎么解决**

解决幻觉要分层，不要只说“换更强模型”。

- **输入侧：** 用户问题不清楚时追问，不让模型猜关键参数。
- **检索侧：** 做 query rewrite、BM25 + 向量混合检索、rerank，提高正确证据进入上下文的概率。
- **上下文侧：** 去重、过滤旧版本、权限过滤、冲突标注、控制 TopN，避免噪声干扰。
- **生成侧：** 要求基于证据回答，关键结论带引用，证据不足时说明不确定。
- **校验侧：** 做 groundedness、citation、unsupported claim、敏感信息和规则校验。
- **兜底侧：** 校验失败时重检索、重生成、拒答、追问或转人工。
- **评测侧：** 把线上幻觉 case 放进回归集，持续跟踪幻觉率、引用准确率、no-answer 准确率。

**4. 高风险场景要更严格**

如果涉及金额、权限、医疗建议、法律条款、生产操作、删除数据等，不能只靠模型自信度。必须用：

- 权威数据源校验。
- 规则或 Workflow 控制。
- 人工确认。
- 审计日志。
- 明确拒答和转人工策略。

**面试可以这样说：**

我判断幻觉不会只看模型语气是否自信，而是看答案里的关键结论有没有事实依据。RAG 场景里会检查正确证据有没有被召回、有没有进入最终上下文、答案是否被上下文支持；如果带引用，还要做 citation 校验，看引用是否来自本次检索、是否有权限、是否真的支持结论。更细一点会抽取答案里的实体、数字、时间、政策条款和因果判断，做 unsupported claim 检测。解决上我会分层处理：输入不清就追问；检索不足就优化 query rewrite、混合检索和 rerank；上下文有噪声就去重、过滤旧版本和冲突证据；生成阶段要求基于证据回答并带引用；生成后做 groundedness 和引用校验。证据不足或校验失败时，宁可说明不确定、重检索、追问或转人工，也不要让模型强行补全。最后把幻觉样本沉淀成回归集，持续看幻觉率、引用准确率和无答案拒答准确率。

## 15. 为什么有些场景会选择 pgvector，而不是直接用 ES 做向量检索？

**问题：** 为什么有些场景会选择 pgvector，而不是直接用 ES 做向量检索？

**答案：**

选择 pgvector 还是 Elasticsearch 做向量检索，本质不是谁绝对更好，而是看数据规模、团队基础设施、事务一致性、过滤条件、混合检索需求和运维成本。有些场景选 pgvector，是因为它可以把业务数据、metadata、权限和向量放在同一个 PostgreSQL 体系里，架构更简单、一致性更好。

**1. pgvector 的优势**

pgvector 是 PostgreSQL 的向量扩展，适合这些场景：

- 数据规模中小，不是十亿级向量。
- 已经大量使用 PostgreSQL。
- 文档、chunk、metadata、权限、租户都在关系库里。
- 需要事务一致性，比如文档更新和向量更新一起提交。
- 需要复杂 SQL 过滤、join、权限条件。
- 团队不想额外维护一套 ES/向量数据库集群。

比如企业 RAG 里，每个 chunk 都有：

```text
doc_id、tenant_id、permission、version、status、updated_at、section、embedding
```

用 pgvector 可以直接在 SQL 里做：

```sql
WHERE tenant_id = ?
  AND permission <= ?
  AND status = 'active'
ORDER BY embedding <-> query_embedding
LIMIT 10
```

这样权限过滤、版本过滤和向量召回在一个系统里完成，简单可控。

**2. 为什么不一定直接用 ES**

ES 很强，尤其擅长全文检索、BM25、倒排索引、日志检索和大规模搜索。但如果只是中小规模 RAG，直接上 ES 可能带来：

- 多维护一套集群。
- 数据同步链路复杂。
- PostgreSQL 和 ES 之间一致性要处理。
- 权限、版本、租户 metadata 需要双写或同步。
- 排查时要同时看数据库和 ES 状态。

如果业务主数据本来就在 PostgreSQL，RAG 规模又不大，pgvector 的工程复杂度更低。

**3. ES 更适合什么场景**

ES 仍然很适合：

- 大规模全文检索。
- BM25 和关键词召回要求强。
- 日志、代码、错误码、商品搜索等搜索场景。
- 需要复杂倒排、分词、排序、聚合。
- 已经有成熟 ES 集群和搜索团队。
- 需要高吞吐、横向扩展的检索服务。

如果 RAG 需要大量关键词检索、复杂 query DSL、中文分词、搜索排序和向量混合召回，ES 会更有优势。

**4. 工程里经常组合使用**

很多生产系统不是二选一：

```text
PostgreSQL / pgvector：存业务数据、metadata、小中规模向量
ES：做 BM25、全文检索、复杂关键词召回
向量库：做更大规模 ANN 检索
Reranker：最终精排
```

比如：

```text
query
  -> pgvector 向量召回
  -> ES BM25 召回
  -> 合并去重
  -> rerank
  -> 权限和版本校验
```

pgvector 可以先满足简单 RAG 和快速迭代；当数据规模、检索复杂度、吞吐压力上来后，再引入 ES 或专门向量数据库。

**5. 选型判断**

可以这样判断：

- **中小规模、强 metadata、强事务一致性、已有 PostgreSQL：** 优先 pgvector。
- **关键词检索强、BM25 权重高、搜索需求复杂：** 优先 ES。
- **超大规模向量、高 QPS、低延迟 ANN：** 考虑 Milvus、Qdrant、Faiss、Weaviate 等专门方案。
- **企业 RAG 初期：** pgvector 往往更快落地。
- **复杂生产搜索：** ES + 向量检索 + rerank 更稳。

**面试可以这样说：**

有些场景选择 pgvector，不是因为它一定比 ES 强，而是因为它能把向量、chunk、metadata、权限、版本和业务数据放在同一个 PostgreSQL 体系里。对于中小规模企业 RAG，这样架构更简单，事务一致性更好，权限和租户过滤可以直接用 SQL 做，也不用维护 PostgreSQL 到 ES 的同步链路。ES 的优势在全文检索、BM25、分词、复杂搜索和大规模横向扩展，如果场景里关键词、错误码、日志、商品搜索这类需求很强，ES 更合适。工程上经常不是二选一：pgvector 做中小规模语义召回和 metadata 过滤，ES 做 BM25/关键词召回，最后合并 rerank。我的选型原则是：数据规模不大、业务数据本来就在 Postgres、权限过滤复杂，优先 pgvector；搜索复杂度高、全文检索强、已有 ES 基建，就用 ES 或混合方案。

核心结论是：纯向量索引擅长语义相似和同义改写，但容易漏掉错误码、编号、专有名词、代码符号、订单号这类精确匹配；BM25 擅长关键词和精确词匹配，但对口语化、同义表达、语义改写不够稳。所以生产 RAG 经常做混合索引，用向量检索覆盖语义召回，用 BM25 覆盖精确匹配，再合并去重、RRF 或加权融合，最后 rerank 精排。

**面试可以这样说：**

我不会只用纯向量索引，因为向量检索解决的是语义相似，但对精确词不一定稳定，比如错误码、接口名、型号、订单号、表名、代码符号这类 query，向量可能召回语义相近但业务不相关的内容。BM25 正好补这个短板，它对关键词、专有名词、编号和短 query 更可靠。但 BM25 也有问题，如果用户问法很口语化，或者和文档表达不一致，它容易漏召回。所以工程上通常做 hybrid search：BM25 和向量两路并行召回，合并去重后用 RRF、加权融合或 reranker 排序。什么时候优先向量？语义问答、FAQ 改写、自然语言描述、同义表达多的场景。什么时候优先 BM25？错误码、编号、专有名词、代码/API、订单号、短关键词这类精确匹配场景。真实系统里可以按 query 类型动态调权重。

## 17. PEFT 是什么？Prefix-tuning 和 P-tuning 有什么区别？

**问题：** 知道 PEFT 吗？Prefix-tuning 和 P-tuning 有何区别？

**答案：**

PEFT 是 Parameter-Efficient Fine-Tuning，参数高效微调。核心思想是冻结大模型主体参数，只训练少量新增参数或少量可训练模块，让模型适配具体任务。

常见 PEFT 方法包括 LoRA、Adapter、Prefix-tuning、Prompt tuning / P-tuning。它们都想降低训练参数量、显存和部署成本，但切入点不同：LoRA 是训练权重增量，Adapter 是插入小模块，Prefix-tuning 和 P-tuning 则是训练连续的软提示参数。

Prefix-tuning 通常是在 Transformer 每一层 attention 里加入一段可训练 prefix，更像给每层 attention 额外加一组虚拟的 key/value：

```text
原始 attention: Q attends to K, V
Prefix-tuning: Q attends to [K_prefix, K], [V_prefix, V]
```

它不是真的在输入文本前拼几个自然语言 token，而是在 attention 计算里加入可训练的前缀状态。因为每一层都能被 prefix 影响，表达能力比较强，常用于生成、摘要、对话、风格和任务适配。

P-tuning 更强调学习连续 prompt embedding，用可训练向量替代人工设计的 prompt token。早期 P-tuning v1 主要是在输入 embedding 层加入 virtual tokens，并可能用 BiLSTM、MLP 等 prompt encoder 生成这些连续 prompt：

```text
输入: [virtual prompt embeddings] + 原始输入 tokens
```

P-tuning v1 主要影响输入层，参数更少，但表达能力相对弱。P-tuning v2 做了 deep prompt tuning，会在多层加入可训练 prompt，表达能力更接近 Prefix-tuning，适用范围也更广。

核心区别可以这样看：

| 对比点 | Prefix-tuning | P-tuning |
|---|---|---|
| 本质 | 给 attention 加可训练 prefix KV | 学习连续 prompt embedding |
| 插入位置 | 通常作用于每层 attention 的 K/V | v1 多在输入层，v2 扩展到多层 |
| 是否改底座参数 | 不改 | 不改 |
| 表达能力 | 较强，直接影响每层 attention | v1 较弱，v2 更强 |
| 典型用途 | 生成、对话、摘要、任务适配 | prompt 优化、分类、理解、生成任务适配 |

工程上现在 LoRA 更常见，因为效果、训练稳定性和生态支持通常更好；Prefix/P-tuning 的优势是参数很少、底座完全冻结、不同任务可以挂不同 prompt 参数。但它们也有局限：prompt/prefix 会占用一定上下文或 attention 预算，对初始化和任务比较敏感；如果要大幅改变模型能力、工具调用习惯或复杂领域行为，LoRA 或全量微调通常更稳。

**面试可以这样说：**

PEFT 是参数高效微调，目标是冻结大模型主体，只训练很少的附加参数来适配任务，比如 LoRA、Adapter、Prefix-tuning、P-tuning。Prefix-tuning 和 P-tuning 都属于不改底座参数的软提示方法，但 Prefix-tuning 通常是在每层 attention 里加入可训练的 prefix KV，让模型每层 attention 都能受影响；P-tuning 则是学习连续 prompt embedding，v1 主要加在输入层，v2 扩展成多层 deep prompt。简单说，Prefix-tuning 更像改 attention 里的前缀状态，P-tuning 更像学习一段软 prompt。工程上现在 LoRA 更常用，因为效果和生态更稳；Prefix/P-tuning 更适合参数极少、任务切换轻量的场景。

## 18. RLHF 的训练流程是什么？为什么大模型微调后还要 RLHF？

**问题：** 知道 RLHF 吗？训练流程是什么？大模型微训练为什么还要 RLHF？

**答案：**

这题和 [[大模型基础-01#3. 了解 RLHF 吗？DPO 和 PPO 有什么区别？Loss 是怎么样的？各自的优缺点是什么？|第 3 题：RLHF、DPO 和 PPO 的区别]] 有重叠，但这里重点是 RLHF 的完整训练流程，以及为什么 SFT/微调之后还需要 RLHF。

RLHF 是 Reinforcement Learning from Human Feedback，用人类偏好信号来对齐模型输出。它解决的不是“模型会不会生成文本”，而是“模型生成的答案是不是更符合人类偏好、安全边界和真实使用需求”。

典型流程是：

```text
预训练模型
  -> SFT 监督微调
  -> 收集偏好数据
  -> 训练 Reward Model
  -> 用 PPO 等算法优化策略模型
  -> 评测、安全测试、上线
```

预训练阶段让模型获得语言能力、知识记忆和通用推理能力，但预训练目标只是 next token prediction，不等于会听指令、会拒答、会按用户偏好回答。

SFT 用高质量指令数据训练模型，让模型学会理解用户指令、按问答/摘要/代码/抽取等格式输出，形成基本助手风格。但 SFT 本质是模仿标注答案。如果同一个问题有多个可接受答案，SFT 很难表达“哪个更好”；如果标注数据覆盖不全，模型也可能学到表面格式，但不一定学到人类偏好。

RLHF 会给同一个 prompt 生成多个回答，让人类标注哪个更好，形成 chosen / rejected 数据：

```text
prompt: 用户问题
chosen: 更好的回答
rejected: 较差的回答
```

然后训练 Reward Model，让它对 chosen 打更高分，对 rejected 打更低分。最后用 PPO 等算法优化策略模型：模型生成回答，Reward Model 打分，训练目标是提高奖励，同时用 KL 约束限制模型不要偏离 SFT/reference model 太远：

```text
maximize: reward - beta * KL(policy || reference)
```

为什么微调后还要 RLHF？因为 SFT/微调解决的是“学会怎么答”，RLHF 解决的是“在多个可能答案里更偏向人类认为好的答案”。开放式生成没有唯一标准答案，很多质量维度也很难写成 hard label，比如更有帮助、更真实、更安全、更简洁、拒答边界更合理。RLHF 把这些人类偏好变成可优化信号。

现在工程里不一定都用传统 PPO-RLHF，也常用 DPO、IPO、KTO 等偏好优化方法替代复杂 RL 流程。但核心目的相同：在 SFT 之后进一步让模型输出更符合人类偏好。

**面试可以这样说：**

RLHF 是用人类反馈对齐大模型。典型流程是先预训练获得通用语言能力，再用 SFT 让模型学会按指令回答，然后收集同一 prompt 下多个回答的人类偏好，训练 Reward Model，最后用 PPO 这类强化学习方法优化策略模型，同时加 KL 约束避免模型偏离 SFT 模型太远。为什么 SFT 后还要 RLHF？因为 SFT 本质是模仿标准答案，它能让模型会答题，但不能很好表达“哪个答案更有帮助、更安全、更符合人类偏好”。开放式生成没有唯一标准答案，很多质量维度也很难写成 hard label，所以需要偏好数据和 RLHF/DPO 这类方法继续对齐。简单说，SFT 解决会不会按指令答，RLHF 解决答得是不是更符合人的偏好和安全边界。

## 19. MHA、MQA、GQA 有什么区别？

**问题：** 知道几种 attention 的区别吗？MHA、MQA、GQA？

**答案：**

MHA、MQA、GQA 都是 Transformer attention 的变体，核心区别在于 Q、K、V 的 head 怎么分配，尤其是 K/V 是否被多个 query head 共享。

**1. MHA：Multi-Head Attention**

MHA 是标准多头注意力。每个 head 都有自己独立的 Q、K、V：

```text
head1: Q1, K1, V1
head2: Q2, K2, V2
...
headH: QH, KH, VH
```

优点是表达能力强，不同 head 可以学习不同语义关系。缺点是推理时 KV cache 很大，因为每一层、每个 token、每个 head 都要缓存 K/V。长上下文和高并发场景下，显存压力明显。

**2. MQA：Multi-Query Attention**

MQA 是多个 query head 共享同一组 K/V：

```text
Q 有 H 个 head
K/V 只有 1 组，被所有 Q head 共享
```

它的主要目标是降低推理阶段 KV cache 占用和内存带宽压力。因为 K/V head 数从 H 变成 1，KV cache 大幅下降，解码速度更快，吞吐更高。

缺点是 K/V 表达能力被压缩，多个 query head 只能看同一组 K/V，效果可能比 MHA 略差，尤其在模型较小或任务较复杂时更明显。

**3. GQA：Grouped-Query Attention**

GQA 是 MHA 和 MQA 的折中。它把 query heads 分成若干组，每组共享一组 K/V：

```text
Q 有 H 个 head
K/V 有 G 组，1 < G < H
每组 Q heads 共享对应的 K/V
```

比如 32 个 Q head、8 个 KV head，就是每 4 个 Q head 共享 1 组 K/V。这样 KV cache 比 MHA 小很多，同时比 MQA 保留更多 K/V 表达能力。

**4. 工程取舍**

| 类型 | Q head | K/V head | 表达能力 | KV cache | 推理速度 |
|---|---:|---:|---|---|---|
| MHA | 多个 | 多个，和 Q 一样多 | 最强 | 最大 | 较慢 |
| MQA | 多个 | 1 组 | 较弱 | 最小 | 最快 |
| GQA | 多个 | 少数组 | 接近 MHA | 中等 | 较快 |

大模型推理时瓶颈不只是算力，还包括 KV cache 显存和内存带宽。MHA 效果强但缓存重；MQA 极致省 KV cache，但可能损失表达能力；GQA 在效果和推理成本之间更平衡，所以很多现代 LLM 会采用 GQA。

**面试可以这样说：**

MHA、MQA、GQA 的区别主要在 K/V head 是否共享。MHA 是标准多头注意力，每个 head 都有自己的 Q/K/V，表达能力强，但 KV cache 最大，长上下文和高并发推理成本高。MQA 是多个 Q head 共享一组 K/V，KV cache 和内存带宽压力大幅下降，解码更快，但因为 K/V 表达被压缩，效果可能有损失。GQA 是折中方案，把 Q heads 分组，每组共享一组 K/V，比如 32 个 Q head 配 8 个 KV head。它比 MHA 省显存、比 MQA 保留更多表达能力，所以现在很多大模型会用 GQA 来平衡效果和推理效率。

## 20. Dense 模型和 MoE 模型有什么区别？

**问题：** 讲一下 dense 模型和 MoE 模型以及二者区别。

**答案：**

Dense 模型和 MoE 模型的核心区别是：每次前向计算时，是不是激活所有参数。

Dense 模型是稠密模型。对每个 token，模型里的主要参数都会参与计算。比如一个 70B dense 模型，理论上每次推理都会走过这 70B 参数对应的层和计算路径。

MoE 是 Mixture of Experts，混合专家模型。它会在某些层里放多个 expert，通常是多个 FFN 专家，然后用 router/gate 根据 token 选择少数几个 expert 激活：

```text
token
  -> router 选择 top-k experts
  -> 只经过被选中的 experts
  -> 合并 expert 输出
```

比如一个 MoE 模型总参数有 8x7B，但每个 token 只激活其中 2 个 expert，那么总参数量很大，但单 token 的激活参数量和计算量远小于总参数量。

**1. Dense 模型特点**

- **所有参数参与计算：** 每个 token 都走完整模型。
- **训练和推理路径简单：** 工程实现更直接。
- **稳定性好：** 没有路由负载均衡、专家塌缩等问题。
- **成本随参数量线性增加：** 模型越大，每次计算越贵。
- **适合中小规模和稳定部署：** 延迟、吞吐和效果更容易预测。

**2. MoE 模型特点**

- **总参数大，激活参数少：** 容量高，但单 token 计算量可控。
- **通过 router 选择专家：** 不同 token 走不同 expert。
- **训练更复杂：** 需要处理负载均衡、专家利用率、通信开销、路由稳定性。
- **推理部署更复杂：** expert 可能分布在不同 GPU，容易受通信和 batch 分布影响。
- **适合扩大模型容量：** 在计算预算不同比例增加的情况下提升模型能力。

**3. 主要区别**

| 对比点 | Dense 模型 | MoE 模型 |
|---|---|---|
| 参数激活 | 每个 token 激活大部分参数 | 每个 token 只激活部分 expert |
| 总参数量 | 通常等于主要计算规模 | 可以很大 |
| 单 token 计算量 | 随总参数增加明显增加 | 主要取决于激活 expert 数 |
| 工程复杂度 | 较低 | 较高 |
| 训练稳定性 | 更稳 | 需要路由和负载均衡 |
| 推理部署 | 简单可预测 | 受 expert 分布、通信、batch 影响 |
| 适用目标 | 稳定、通用、易部署 | 用可控计算扩大容量 |

MoE 的优势不是“免费变强”，而是用稀疏激活扩大模型容量。它能让模型拥有更大的参数存储和知识容量，但每个 token 只用其中一部分，从而控制计算成本。代价是训练和服务复杂度更高，尤其是跨卡通信、expert 负载不均、路由抖动、batch 内 token 分布不均等问题。

**面试可以这样说：**

Dense 模型是稠密激活，每个 token 基本都会经过模型的主要参数，所以结构简单、训练稳定、部署可预测，但参数越大计算越贵。MoE 是稀疏激活，在某些层放多个 expert，通过 router 给每个 token 选择 top-k expert，只激活一部分参数。这样 MoE 可以有很大的总参数量和容量，但单 token 计算量不等于总参数量，适合在计算预算可控的情况下扩大模型能力。代价是工程复杂度更高，要处理路由、负载均衡、专家利用率、跨 GPU 通信和推理抖动。简单说，Dense 胜在简单稳定，MoE 胜在用稀疏激活扩大容量，但训练和部署更难。

## 21. MoE 模型专家负载不均衡怎么解决？

**问题：** MoE 模型专家的负载不均衡问题如何解决？

**答案：**

MoE 的负载不均衡，是指 router 总把 token 分给少数热门 expert，导致这些 expert 过载，而其他 expert 空闲。它会带来几个问题：

- **训练效率低：** 部分 expert 很忙，部分 expert 学不到东西。
- **专家塌缩：** router 越来越偏向少数 expert，模型容量没有真正用起来。
- **跨卡通信不均：** expert 分布在不同 GPU 时，部分 GPU 成为瓶颈。
- **推理延迟抖动：** batch 里 token 分布不均，尾延迟变差。

常见解决办法有几类。

**1. 加负载均衡损失**

训练时给 router 加 auxiliary loss，鼓励 token 分配更均匀。直觉上要同时看两件事：

- 每个 expert 被选中的 token 数是否均衡。
- router 给每个 expert 的概率质量是否均衡。

如果某些 expert 被频繁选中，而其他 expert 几乎不用，loss 就会惩罚这种分布，让 router 不要过早集中到少数 expert。

**2. 设置 expert capacity**

每个 expert 设置容量上限，比如一个 batch 内最多处理多少 token。超过 capacity 的 token 可以被丢弃、走 residual、分配到备选 expert，或者延后处理。

capacity 可以防止单个 expert 被无限塞满，但也有代价：capacity 太小会丢 token 或损失效果，太大又不能缓解负载峰值，所以需要结合 batch size、top-k、并行策略调。

**3. Top-k 路由和随机扰动**

MoE 通常不是只选一个 expert，而是 top-1 或 top-2。Top-2 routing 可以让 token 同时走两个 expert，缓解单 expert 过载，也让训练信号更充分。

训练早期还可以给 router logits 加噪声，或者使用随机路由、温度调节，增加探索，避免 router 过早固定到少数 expert。

**4. 改进路由策略**

除了 token-choice routing，也可以用 expert-choice routing，让 expert 主动选择自己处理哪些 token，从机制上更容易控制每个 expert 的 token 数。

也可以做分组路由、局部路由、层级路由，减少跨设备通信，同时让负载更可控。

**5. 工程侧均衡**

部署时要关注 expert placement，把专家合理放到不同 GPU 或节点上；推理引擎要做 token dispatch、all-to-all 通信优化、micro-batch 合并和动态 batching。

线上还要监控：

- 每个 expert 的 token 占比。
- router entropy。
- capacity overflow/drop rate。
- 各 GPU 负载和通信耗时。
- p95/p99 延迟。

如果发现某些 expert 长期过热，可以调整 capacity factor、top-k、router 温度、负载均衡 loss 权重，或者重新训练/蒸馏。

**面试可以这样说：**

MoE 的负载不均衡本质是 router 总把 token 分给少数 expert，导致热门 expert 过载，其他 expert 空闲，训练时会造成专家塌缩，推理时会造成 GPU 负载不均和尾延迟抖动。解决思路一般是训练和工程两边一起做：训练侧加 load balancing loss，让每个 expert 的 token 数和概率质量更均匀；设置 expert capacity，避免单个 expert 无限过载；用 top-2 routing、router noise、温度调节增加探索，防止早期塌缩；也可以用 expert-choice routing 或分组路由控制分配。工程侧要做好 expert placement、all-to-all 通信优化、动态 batching，并监控每个 expert 的 token 占比、overflow rate、router entropy 和 p99 延迟。简单说，既要让 router 学会均匀用专家，也要让系统能承受不均匀分布。

## 22. 微调时直接用 PEFT 库还是 LLaMA Factory？

**问题：** 如何做微调的？直接用 PEFT 库还是 LLaMA Factory 做的？

**答案：**

这题面试时不要只回答“用某个工具”，要讲清楚你对微调链路的理解。PEFT 库和 LLaMA Factory 不是同一层东西。

PEFT 是 Hugging Face 生态里的参数高效微调库，主要提供 LoRA、Prefix-tuning、P-tuning、Adapter 等 PEFT 方法的底层实现。它更偏代码级组件，适合你自己写训练脚本，精细控制模型加载、dataset、collator、Trainer、loss、保存和 merge。

LLaMA Factory 是更上层的训练框架，封装了模型加载、数据模板、SFT、LoRA、QLoRA、DPO、评测、导出等流程。它底层也会用到 Transformers、PEFT、Accelerate、TRL 这类能力，但使用方式更配置化，更适合快速跑通实验和标准微调任务。

实际微调流程一般是：

```text
明确任务目标
  -> 准备和清洗指令数据
  -> 选择底座模型
  -> 选择 SFT / LoRA / QLoRA / DPO
  -> 配置训练参数
  -> 训练和验证
  -> 人工评测与自动评测
  -> 导出 adapter 或 merge 模型
  -> 部署灰度
```

如果是业务里的指令微调、领域问答格式适配、客服话术、分类抽取、工具调用格式稳定性，我一般优先用 LoRA/QLoRA，而不是全量微调。原因是成本低、迭代快、回滚方便，也能保留底座模型的大部分能力。

PEFT 和 LLaMA Factory 的选择可以这样说：

| 场景 | 更适合 |
|---|---|
| 快速验证 LoRA/SFT/DPO 效果 | LLaMA Factory |
| 数据模板和训练流程比较标准 | LLaMA Factory |
| 需要低成本复现实验和交付训练产物 | LLaMA Factory |
| 需要自定义 loss、采样、collator、特殊模型结构 | PEFT + Transformers 自写脚本 |
| 需要和内部训练平台深度集成 | PEFT/TRL/Accelerate 自定义 |
| 需要细粒度控制 adapter 注入层和保存逻辑 | PEFT 自写更灵活 |

工程上我会先用 LLaMA Factory 快速跑 baseline，比如 Qwen/LLaMA 类模型加 LoRA 或 QLoRA，验证数据是否有效、loss 是否下降、评测集是否提升。等任务确定后，如果需要特殊数据拼接、自定义 loss、多任务采样、复杂评测或接内部平台，就会迁到 PEFT + Transformers/TRL 的自定义训练脚本。

关键不是工具，而是微调质量控制：

- 数据要去重、清洗、统一模板。
- 训练集、验证集、测试集要按场景隔离。
- 评测要覆盖准确性、格式遵循、幻觉、安全和回归。
- LoRA rank、target modules、learning rate、batch size、epoch 要做对比实验。
- 上线时保存 adapter、训练配置、数据版本和评测报告，方便回滚。

**面试可以这样说：**

我做微调时会先判断目标。如果只是标准 SFT、LoRA、QLoRA 或 DPO，我通常会先用 LLaMA Factory 快速跑通 baseline，因为它把模型加载、数据模板、训练参数、评测和导出都封装好了，适合快速验证数据和方案。PEFT 更偏底层库，提供 LoRA、Prefix-tuning、P-tuning 这些参数高效微调能力；如果我要自定义 loss、数据 collator、采样策略、adapter 注入层，或者接内部训练平台，就会用 PEFT + Transformers/TRL 自己写训练脚本。我的理解是 LLaMA Factory 是工程框架，PEFT 是底层微调组件。真正重要的是数据清洗、模板设计、评测集、超参对比、adapter 保存和上线回滚，而不是只会调一个工具命令。

## 23. SFT 用多少张卡、训练多久怎么回答？

**问题：** SFT 使用的数据集使用了多少张卡？SFT 训练多久？

**答案：**

这类问题面试官通常不是只想听一个数字，而是想判断你是否真的做过训练，以及你是否理解训练成本和数据规模、模型大小、序列长度、batch size、epoch、精度、并行策略之间的关系。

回答时不要编一个孤立数字，最好按下面结构说：

```text
模型规模
数据规模和平均长度
训练方式：全参 / LoRA / QLoRA
硬件：GPU 型号和卡数
关键超参：epoch、global batch size、max length、lr
训练耗时
评测和上线结果
```

SFT 训练时长主要受这些因素影响：

- **模型规模：** 7B、14B、32B、70B 的成本差别很大。
- **训练方式：** LoRA/QLoRA 远低于全参微调。
- **数据 token 数：** 样本条数不够准确，平均长度和总 token 数更关键。
- **max sequence length：** 2K、4K、8K 显存和计算差异明显。
- **global batch size：** 影响吞吐、收敛和显存。
- **GPU 型号：** A10、A100、H100 的吞吐差距很大。
- **训练轮数：** 常见 SFT 可能 1 到 3 个 epoch，具体看验证集。
- **是否开 gradient checkpointing、FlashAttention、DeepSpeed/FSDP：** 会影响显存和速度。

如果没有真实项目数字，可以用保守口径表达，不要冒充大规模训练。例如：

```text
我们当时不是做全参训练，而是基于 7B/14B 底座做 LoRA SFT。
数据规模是几万到十几万条指令样本，清洗后按场景拆了训练集、验证集和回归集。
训练资源用的是 4/8 张 A100 级别 GPU，max length 设在 2K 或 4K，训练 1 到 3 个 epoch。
单次实验大概几小时到十几个小时，最终不是只看 loss，而是看验证集、人工评测和线上灰度效果。
```

如果是更小规模实验，也可以这样说：

```text
如果只是验证 LoRA SFT baseline，7B 模型在单张 24G/48G 卡上也可以跑，通常会配 QLoRA、gradient checkpointing 和较小 batch。
这种实验更多是验证数据和任务方向，不代表最终生产训练配置。
```

注意面试中要主动说明：训练多久不是越久越好。SFT 过训会导致模型记模板、泛化变差、回答变窄，甚至遗忘底座能力。所以会看 train loss、eval loss、任务指标、人工 case、拒答边界和回归集。如果验证集不再提升，或者通用能力开始下降，就不继续堆 epoch。

**面试可以这样说：**

我回答这类问题不会只报一个卡数和时间，因为 SFT 成本和模型规模、数据 token 数、max length、batch size、训练方式、GPU 型号都有关系。比如我们做标准业务 SFT 时，一般不会直接全参训，而是先用 LoRA/QLoRA 在 7B 或 14B 底座上跑 baseline。数据通常先清洗成几万到十几万条指令样本，再按场景拆训练集、验证集和回归集。资源上可以用 4 到 8 张 A100 级别卡，max length 设 2K 或 4K，训练 1 到 3 个 epoch，单次实验大概几小时到十几个小时。最终是否停止不是只看训练跑完，而是看 eval loss、任务指标、人工评测、格式遵循、幻觉和回归集。如果只是小规模验证，7B + QLoRA 单卡也能跑，但那更多是验证数据和方向，不代表生产配置。

## 24. 如何设计一个 Prompt？Prompt engineering 有哪些技术？

**问题：** 如何设计一个 prompt？Prompt engineering 有哪些技术？

**答案：**

这题和 [[大模型基础-01#5. Prompt 怎么优化？|第 5 题：Prompt 怎么优化？]] 有重叠，但这里重点是系统化说明 Prompt 设计方法和常见 Prompt engineering 技术。

设计 Prompt 时，我一般先不急着写提示词，而是先明确任务边界：

```text
目标：希望模型完成什么任务
输入：用户问题、上下文、工具结果、检索证据分别是什么
约束：哪些不能做，哪些必须遵守
输出：返回自然语言、JSON、表格还是结构化字段
兜底：信息不足、冲突、低置信、高风险时怎么处理
评测：怎么判断 prompt 是否真的变好
```

一个比较稳定的 Prompt 通常包含几层：

```text
角色和任务目标
全局规则和安全边界
输入上下文分区
推理或处理步骤
输出格式
少量示例
失败兜底策略
```

常见 Prompt engineering 技术包括：

**1. Instruction prompting**

把任务要求写清楚，包括要做什么、不要做什么、输出什么格式。适合分类、抽取、总结、问答等基础任务。

**2. Role prompting**

给模型一个角色，比如“你是客服质检助手”“你是代码审查助手”。角色不是为了好看，而是为了限定回答视角、专业术语和判断标准。

**3. Zero-shot / Few-shot**

Zero-shot 是不给示例，直接让模型按指令完成。Few-shot 是给少量高质量示例，帮助模型稳定格式、边界和风格。Few-shot 示例要覆盖正例、反例、边界 case，不能只放简单样本。

**4. Chain-of-Thought / 分步推理**

复杂推理任务可以要求模型先分解问题、逐步分析，再给结论。工程上不一定把完整思考过程暴露给用户，可以让模型内部分析，最终只输出结论和必要依据。

**5. ReAct**

ReAct 把 reasoning 和 action 结合起来，适合 Agent 或工具调用场景：

```text
思考当前需要什么信息
选择工具
观察工具结果
再决定下一步
```

生产里不能只靠 prompt 写 Thought/Action，还要有工具 schema、权限校验、状态管理和执行日志。

**6. Structured output**

要求模型输出 JSON、固定字段或符合 schema 的结果，方便系统解析和校验。例如：

```json
{
  "intent": "",
  "slots": {},
  "confidence": 0.0,
  "need_clarification": false
}
```

如果用于生产，最好配合 JSON schema、function calling 或后端校验。

**7. Context engineering**

Prompt 不只是提示词，还包括上下文组织。要把系统规则、用户输入、RAG 证据、工具结果、历史摘要分区，按可信度和相关性排序，避免把无关内容全塞进去。

**8. Constraint prompting**

明确约束和兜底，比如“只能基于证据回答”“证据不足时说明不知道”“缺字段时追问”“高风险操作必须确认”。这能减少幻觉和越权行为，但不能替代系统侧校验。

**9. Self-check / Critique**

让模型在输出前检查是否满足格式、是否基于证据、是否遗漏关键字段。复杂系统里也可以用单独 verifier 或 LLM-as-judge 做二次检查。

**10. Prompt 版本化和评测**

Prompt engineering 不能靠感觉。每次改 Prompt，都要固定模型、检索、工具和测试集，看准确率、格式错误率、幻觉率、拒答/追问是否合理、是否引入回归问题。

**面试可以这样说：**

我设计 Prompt 时不会只写一句“请认真回答”，而是先明确任务目标、输入边界、输出格式和失败兜底。结构上会把角色、任务、规则、上下文、处理步骤、输出 schema、示例和约束分开写，尤其在 RAG 或 Agent 场景里，要把用户输入、检索证据、工具结果和历史摘要分区，避免模型混淆指令和数据。常用技术包括 instruction prompting、role prompting、zero-shot/few-shot、分步推理、ReAct、结构化输出、上下文工程、约束提示和 self-check。Prompt 不是越长越好，关键是信息优先级清楚、格式稳定、边界明确。最后一定要用评测集迭代，比较准确率、幻觉率、格式错误率和回归 case，而不是凭感觉不断加规则。

## 25. 大模型如何调用、本地部署和对外提供服务？

**问题：** 大模型的调用方式是什么？本地部署大模型会用到哪些框架，大模型服务是如何部署的？提供哪些接口？是否支持流式输出？

**答案：**

大模型调用方式可以分成两类：调用云厂商 API，或者私有化/本地部署模型服务。

**1. 云 API 调用**

应用侧直接通过 HTTP API 调模型，常见接口形态包括：

- Chat Completions：多轮对话生成。
- Completions：传统文本补全。
- Embeddings：文本向量化。
- Rerank：检索结果重排。
- Tool / Function Calling：模型输出结构化工具调用参数。
- Moderation：内容安全审核。

优点是接入快、弹性好、不需要自己维护 GPU；缺点是成本、数据合规、网络稳定性和可控性受外部平台影响。

**2. 本地部署常用框架**

本地或私有化部署时，常见推理框架有：

| 框架 | 适合场景 |
|---|---|
| vLLM | 高吞吐服务化推理，支持 continuous batching、PagedAttention、OpenAI 兼容接口 |
| TGI | Hugging Face 生态常用服务框架，适合生产推理 |
| SGLang | 适合复杂结构化生成、Agent、多轮和高性能推理 |
| TensorRT-LLM | NVIDIA 生态，追求极致性能和深度优化 |
| llama.cpp | CPU/边缘设备/量化模型，本地轻量运行 |
| Ollama | 本地开发和原型验证，上手快 |
| Triton Inference Server | 多模型统一服务、企业推理平台集成 |

如果是生产服务，常见选择是 vLLM、TGI、SGLang 或 TensorRT-LLM；如果是个人本地验证，可以用 Ollama 或 llama.cpp。

**3. 服务部署链路**

一个常见的大模型服务部署链路是：

```text
模型权重 / tokenizer
  -> 推理框架加载模型
  -> GPU 资源和并行配置
  -> 暴露 HTTP/gRPC API
  -> API Gateway / 鉴权 / 限流
  -> 应用服务调用
  -> 日志、监控、告警、灰度
```

部署时要考虑：

- GPU 型号、显存、张量并行、流水并行。
- 模型量化，比如 FP16、BF16、INT8、INT4。
- max context length、max batch token、并发数。
- KV cache 显存管理。
- 动态 batching 和请求调度。
- 多副本负载均衡。
- 超时、重试、熔断和降级。
- 模型版本、Prompt 版本和灰度发布。

**4. 对外提供哪些接口**

生产里通常会提供 OpenAI-compatible API，方便 LangChain、LlamaIndex、业务系统直接接入。常见接口包括：

```text
POST /v1/chat/completions
POST /v1/completions
POST /v1/embeddings
GET  /v1/models
```

有些系统还会扩展：

```text
POST /v1/rerank
POST /v1/tokenize
POST /v1/detokenize
POST /v1/moderations
POST /v1/responses
```

如果是内部模型网关，还会统一封装 model、temperature、top_p、max_tokens、stream、tools、response_format、trace_id、tenant_id 等参数，并做鉴权、计费、限流和审计。

**5. 是否支持流式输出**

一般支持。大模型生成是逐 token 解码，天然适合流式返回。常见方式是 SSE，也可以用 WebSocket。

SSE 返回时，服务端会不断推送增量 token 或增量消息：

```text
Content-Type: text/event-stream

data: {"delta": "你"}
data: {"delta": "好"}
data: {"delta": "，"}
data: [DONE]
```

流式输出的价值是：

- 降低首字延迟，用户更快看到响应。
- 长回答体验更好。
- 前端可以展示生成中状态。
- Agent 场景可以同时展示工具调用、检索进度和模型 token。

但生产里要处理断线重连、超时、取消生成、心跳、错误事件、输出审核和最终状态落库。对于敏感场景，如果需要输出前完整审核，也可能不直接流式吐给用户，而是先缓冲再返回。

**面试可以这样说：**

大模型调用方式一般有两种：一种是直接调云厂商 API，另一种是私有化部署成内部模型服务。云 API 接入快，本地部署更适合数据合规、成本可控和模型可控。私有化部署常用 vLLM、TGI、SGLang、TensorRT-LLM，轻量本地验证可以用 Ollama 或 llama.cpp。生产部署时通常由推理框架加载模型权重和 tokenizer，配置 GPU、并行策略、量化、KV cache、动态 batching，然后通过 HTTP 或 gRPC 暴露服务，前面再接 API Gateway 做鉴权、限流、审计、监控和灰度。接口上通常提供 OpenAI 兼容的 `/v1/chat/completions`、`/v1/completions`、`/v1/embeddings`、`/v1/models`，也可能扩展 rerank、tokenize、moderation。流式输出一般支持，常用 SSE 返回增量 token，也可以用 WebSocket；生产里还要处理心跳、断线、取消、错误事件和安全审核。

## 26. Token 和字符有什么区别？

**问题：** Token 和字符的区别是什么？

**答案：**

字符是人类看到的最小文字单位，比如一个汉字、一个英文字母、一个数字、一个标点。Token 是模型处理文本时的基本单位，由 tokenizer 按规则切出来，不一定等于字符，也不一定等于单词。

比如：

```text
字符：我 / 爱 / A / I
Token：可能是 "我"、"爱"、"AI"，也可能把一个英文单词拆成多个子词
```

不同模型的 tokenizer 不一样，同一句话在不同模型里可能会被切成不同数量的 token。

**1. 字符是什么**

字符更接近文本显示层面的单位：

- 中文里一个汉字通常是一个字符。
- 英文里一个字母是一个字符。
- 标点、空格、换行也可以算字符。
- emoji 或一些特殊符号在底层编码里可能更复杂，但用户感知上通常看成一个字符。

字符主要用于前端显示、字符串长度、文本清洗和普通业务规则。

**2. Token 是什么**

Token 是模型输入输出的计费、上下文长度和推理计算单位。大模型不会直接按“人类理解的字数”处理文本，而是先用 tokenizer 把文本转成 token id。

常见 tokenizer 会使用 BPE、WordPiece、SentencePiece 等子词切分方式。它会把高频片段合成一个 token，把低频词拆成多个 token。

例如英文：

```text
unbelievable
```

可能被拆成：

```text
un / believable
```

或者：

```text
un / believ / able
```

这取决于 tokenizer 词表。

**3. Token、字符和词的关系**

它们不是一一对应关系：

| 类型 | 含义 | 是否等于 token |
|---|---|---|
| 字符 | 显示层面的文字单位 | 不一定 |
| 单词 | 语言学或空格分隔单位 | 不一定 |
| token | tokenizer 切分后的模型单位 | 模型真正处理的单位 |

中文里，一个汉字有时接近一个 token，但不是绝对。常见词、短语、标点组合可能被合并，生僻字或特殊符号也可能被拆分。

英文里，一个常见单词可能是一个 token，不常见单词、专有名词、代码变量名、URL 往往会被拆成多个 token。

**4. 为什么工程里更关心 token**

大模型工程里，token 很重要，因为：

- 上下文窗口按 token 限制，不是按字符限制。
- API 计费通常按输入 token 和输出 token。
- 推理耗时和显存消耗与 token 数强相关。
- RAG chunk 大小一般按 token 控制。
- Prompt、历史对话、工具 schema、检索内容都会占 token。
- 流式输出也是逐 token 或近似 token 增量返回。

所以做 prompt 拼接、上下文压缩、RAG 切分、成本估算时，不能只看字符数。

**5. 举例说明**

同样是 10 个字符，token 数可能差很多：

```text
你好世界       -> token 数可能较少
OpenAI API    -> 可能按常见片段切
abc_xyz_123   -> 可能拆成多个 token
https://...   -> URL 通常 token 很多
```

代码、JSON、表格、URL、UUID、日志、错误堆栈通常 token 密度很高，虽然字符不一定特别多，但会吃掉大量上下文。

**6. 面试里常见追问**

如果面试官问“一个 token 大概等于多少字”，可以谨慎回答：

- 中文场景可以粗略估算为 1 个汉字接近 1 个 token，但不精确。
- 英文场景常见经验是 1 个 token 大约 3 到 4 个字符，或者一个英文单词约 1 到 2 个 token。
- 真实项目里应该用对应模型的 tokenizer 计算，而不是靠经验估算。

**面试可以这样说：**

字符是文本显示层面的单位，比如一个汉字、字母或标点；token 是 tokenizer 切分后给模型处理的单位。两者不是一一对应的，同一句话在不同模型 tokenizer 下 token 数也可能不同。中文里一个汉字有时接近一个 token，但不是绝对；英文常见单词可能是一个 token，不常见词、代码变量、URL、JSON、日志可能会被拆成很多 token。工程上更关心 token，因为上下文窗口、API 计费、推理耗时、KV cache 显存、RAG chunk 大小和 prompt 拼接都按 token 计算。所以实际项目里不能只按字符数截断或估算成本，要用目标模型的 tokenizer 计算 token 数。
