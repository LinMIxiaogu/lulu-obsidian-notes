# 酒店比价助手-面试模拟

## 1. 项目整体介绍

**面试官提问：**

我看到你简历里写了「GUI Agent 酒店比价助手」，说是面向移动端用户的 GUI Agent 系统，通过 AI 编排规划任务、理解 APP 页面，再用 Android 辅助功能自动完成酒店比价。

你先用 1-2 分钟介绍一下这个项目。重点讲清楚三件事：

- 这个项目解决的真实业务问题是什么？
- 用户从输入需求到拿到比价结果，完整链路怎么走？
- 你本人主要负责了哪些模块？

**推荐回答：**

这个项目是一个移动端酒店比价助手，主要解决用户在多个 OTA 平台之间反复搜索、填写入住信息、切换 APP、对比价格很麻烦的问题。用户在我们的 APP 里输入酒店名、入住时间等需求后，系统会先做意图理解和关键信息抽取；如果信息不完整，会先追问补齐。

执行时，我们的 AI 编排服务会把任务拆成多个平台的查询流程，Android 端通过 AccessibilityService 去真实操作携程、美团、去哪儿这类 APP，包括输入、点击、滑动、截图和页面信息采集。最后后端把各平台查到的价格汇总成一个比价结果返回给用户。

我主要负责 AI 编排服务的一部分、Android 端和后端的任务流转协议，以及无障碍服务侧的前端操作实现。项目是从 0 到 1 做第一版，所以我也参与了多平台流程调试和联调。

**回答注意点：**

- 第一问不要讲太细，重点是说清楚业务背景、执行链路和个人职责。
- 不要说“所有模块都参与了”，要明确自己的主责边界。
- 可以有意识地留下后续追问点，比如 AI 编排、任务状态、端云协议、AccessibilityService、页面识别、多平台适配。

## 2. Agent 和固定脚本的区别

**面试官提问：**

你刚才说这个项目会自动打开携程、美团、去哪儿这些 APP，执行输入、点击、滑动、截图和采集价格。

那这个流程听起来也可以用固定脚本或者 RPA 来做。你们为什么要做成 Agent？在你的项目里，哪些部分是模型动态决策的，哪些部分是固定 Workflow 或规则控制的？

**推荐回答：**

酒店比价这个场景的核心难点之一是页面不稳定。比如同一个 App，不同酒店、不同日期、不同活动状态下，页面结构可能不一样；中间还可能出现登录弹窗、优惠券弹窗、广告弹窗，甚至按钮位置也会变。如果完全靠固定脚本，前期能跑，但后面维护成本会很高。

所以我们做的不是纯 Agent，而是 Workflow 加 Agent。固定 Workflow 负责控制大方向，比如先抽取用户需求，再补齐酒店和日期，再查酒店候选，再进入各个平台采集价格，最后汇总结果。这些步骤是确定的，我们不会让模型自由发挥。

模型动态决策主要放在两个地方。一个是用户输入理解，比如从一句话里提取酒店名、城市、入住离店日期，缺了什么信息就追问什么。另一个是页面操作阶段，端侧把当前截图传给后端，模型主要根据截图判断现在是在搜索页、详情页、房型页，还是遇到了弹窗，然后决定下一步是点击、输入、滑动，还是结束当前平台采集。

规则控制主要是兜底和约束，比如平台执行顺序、当前执行到哪个 App、节点之间怎么流转、连续滑动几次就熔断、截图变化太小就认为可能卡住，还有最终价格汇总这些，都是规则或固定流程控制。

所以我们做 Agent 的原因不是为了替代所有规则，而是因为页面理解和动作选择这部分变化太大，适合交给模型；但主流程和安全边界还是用 Workflow 和规则来控制。

**回答注意点：**

- 先解释为什么固定脚本不够，再解释 Workflow + Agent 的分工。
- 不要把 Agent 说成完全替代规则，重点强调模型只处理不确定节点。
- “主要根据截图判断”这个说法比“只靠截图判断”更稳，方便后续补充其他信号。
- 要说出规则兜底手段，比如超时、熔断、重复操作限制、截图变化检测。

## 3. 页面状态和点击位置怎么判断

**面试官提问：**

你刚才说，端侧会把当前截图传给后端，模型根据截图判断现在是在搜索页、详情页、房型页，或者遇到了弹窗，然后决定下一步动作。

那我想具体问一下：你们传给模型的 observation 里具体有什么？是只有截图吗？如果只靠截图，怎么保证模型稳定判断页面状态和可点击位置？

**推荐回答：**

不是只有截图。截图是主要输入，因为动态页面里的状态判断和点击位置，主要还是靠多模态模型看图来做。但我们会把截图和任务上下文一起组成 observation，比如当前 App、任务目标、酒店名、入住离店日期、当前阶段、上一轮动作这些信息。这样模型知道自己是在美团还是携程，要找哪家酒店，要完成哪一步。

点击位置这块，主链路上模型会输出坐标类动作，比如 `click(start_box=...)`。它输出的是一个区域框，不是一个单点，端侧会取这个区域中心去点击。所以只要模型框到的是按钮或输入框的大致区域，通常就能点中。

我们也专门测过多模态模型的坐标能力。最后选的模型在手机截图上输出坐标比较稳定，在我们测试的常见按钮、输入框、列表项这些元素上，偏差基本能控制在可点击区域内。之前测过一些模型，因为图片尺寸限制或者缩放问题，坐标会有偏差，所以我们也做过图片缩放比例和坐标还原的测试。

当然，也不是所有操作都交给模型坐标。在一些非常固定的流程里，比如能明确拿到输入框、按钮文本，或者固定权限弹窗，我们会用无障碍服务直接获取页面节点信息并操作。这样固定场景就不用每次都让模型判断，稳定性和效率都会更好。

**回答注意点：**

- 不要说只有截图，要强调截图 + 任务上下文共同组成 observation。
- `click(start_box=...)` 要解释成区域框，不是单点坐标。
- 坐标稳定性要结合模型选型、图片缩放比例、坐标还原测试来说。
- 要补充固定场景下会用 AccessibilityService 节点信息操作，避免显得完全依赖视觉坐标。

## 4. 模型动作输出和端侧执行协议

**面试官提问：**

你刚才提到，模型会输出 `click(start_box=...)` 这类坐标动作，也可能决定输入、滑动、返回或者结束当前平台采集。

那我想问得更具体一点：模型输出的动作格式是怎么设计的？后端和 Android 端之间的执行协议大概是什么样的？你们怎么保证模型输出的动作是可执行、可校验的，而不是一段自然语言？

**推荐回答：**

模型输出不是一整段自由文本，而是我们约束过的结构化结果。里面会有一个状态描述，用来说明它判断当前是什么页面、准备做什么；同时也会有一个可执行的 action 字段，真正给端侧执行的是 action。

action 是提前约束好的动作名加参数，比如点击会带区域坐标，输入会带文本，滑动会带起止位置。Android 端收到后不会直接执行，会先校验动作名是否合法、参数是否完整、坐标是否在屏幕范围内，以及当前任务阶段允不允许执行这个动作。

校验通过后才映射到无障碍服务执行；如果校验失败，就把错误回传给后端编排层，让它重新规划或进入异常处理。

**回答注意点：**

- 不要说“结构化 action”导致听起来只有 action，要说“结构化结果，包含状态描述和 action”。
- 重点讲清楚模型只是生成候选动作，端侧会校验后再执行。
- 口述时不用枚举太多动作名，点到点击、输入、滑动即可。

## 5. 任务状态怎么维护

**面试官提问：**

你刚才说端侧会校验“当前任务阶段允不允许执行这个动作”。那我想问一下，你们后端是怎么维护 task state 的？

一次酒店比价任务里，状态会记录哪些东西？比如当前操作到哪个 App、哪个阶段、已采集结果、上一轮动作。如果某个平台执行失败，或者用户中途修改入住日期，状态怎么更新？

**推荐回答：**

因为这个任务不是一次请求就能完成的，而是多轮的“执行-观察-再决策”。端侧每执行一步，都会带着截图和执行结果再次请求后端，所以我们会用一个会话 ID 串起整个比价任务流程。

状态大概分三层。第一层是 LangGraph 的 state，它是一次后端请求内部所有节点共享的上下文，比如当前节点、下一个节点路由、当前正在操作的 App、模型输出的 action、端侧回传的执行结果。

第二层是 Redis，用来存跨轮请求需要复用的任务状态。比如酒店名、城市、入住离店日期、酒店 ID，当前执行到哪个平台，以及各个平台已经采集到的价格、房型、失败标记、完成标记这些。

第三层是 Java 后端的数据持久化和日志记录，主要存用户消息、模型调用日志、节点流转日志、任务状态标记，用于问题追踪和链路回放。

每一轮请求回来时，后端会根据会话 ID 读取 Redis 里的任务状态，再结合前端这次带回来的截图和执行结果，初始化这一轮 LangGraph state，跑完当前节点流转后，再把新的进度、结果和日志写回 Redis 或数据库。模型主要负责页面判断和动作建议，真正的任务推进还是由状态和节点流转控制。

**回答注意点：**

- 先说明为什么需要状态：任务是多轮“执行-观察-再决策”，不是一次请求完成。
- 三层状态要讲清楚：LangGraph state 管单轮节点共享上下文，Redis 管跨轮任务状态，Java 数据层管持久化日志和追踪。
- 要强调会话 ID 串起整个任务流程。
- 最后点出模型只给页面判断和动作建议，任务推进由状态和节点流转控制。

## 6. 重复回调和状态一致性

**面试官提问：**

你刚才说端侧每执行一步都会再次请求后端，后端根据会话 ID 读取 Redis 状态，再推进下一轮 LangGraph。

那我想追一个真实线上问题：如果 Android 端因为网络重试，或者用户重复点击，导致同一个执行结果回调了两次，你们怎么避免后端重复推进状态？比如重复记录价格、重复切换到下一个 App、或者重复下发下一步动作。

**推荐回答：**

这个场景确实可能出现，但在我们这里主要不是用户重复点击导致的。任务开始后手机基本是被自动执行链路接管的，重复更多来自端侧网络重试，或者同一次动作结果被重复回传。

我们的核心是不能让重复回调重复推进任务。后端每次下发动作时，都会带一个 `action_id`，端侧执行完再回调时也会把这个 `action_id` 带回来。后端会用 `session_id + action_id` 做去重判断，如果这个动作结果在当前会话下已经处理过，就不会再更新状态，也不会再次推进到下一个节点。

另外我们还会做阶段校验。因为平台执行是按任务状态顺序推进的，比如当前已经从美团切到携程了，如果又收到一个美团旧动作的回调，就会认为它是过期回调，只记录日志，不再推进主状态。

所以整体是两层保护：一层是 `session_id + action_id` 做幂等去重，防止同一个动作结果重复处理；另一层是当前 App 和节点阶段校验，防止旧回调把任务状态往错误方向推进。

**回答注意点：**

- 先纠正真实来源：重复更多来自端侧网络重试或自动执行链路重复回传，不一定是用户重复点击。
- 核心方案是 `session_id + action_id` 做幂等去重。
- 除了动作级去重，还要做当前 App 和节点阶段校验，防止旧回调污染主状态。

## 7. 失败重试和卡住检测

**面试官提问：**

如果某一步模型判断错了，比如连续点不到按钮，或者滑动了几次页面都没有变化，你们怎么判断任务卡住了？重试几次？什么时候切换策略、跳过当前平台，或者返回失败给用户？

**推荐回答：**

我们判断任务是否卡住，主要看动作执行后页面有没有有效推进。端侧每执行一步都会重新截图回传，后端会计算前后截图相似度；如果连续几轮相似度都很高，比如连续 3 次页面几乎没变化，就认为当前动作没有推进页面，可能卡住了。

卡住的原因可能是模型点错了，也可能是无障碍操作被系统拦截没有生效，或者是业务上这个平台没有这家酒店，导致一直在列表页滑动找不到结果。

处理上，我们会做当前平台的失败阈值控制，比如连续截图高相似、连续滑动次数超过上限、单个平台执行步数超过上限，就停止继续在这个平台尝试，标记失败原因，然后切到下一个平台。因为比价是多平台任务，一个平台失败不应该阻塞整个结果。

**回答注意点：**

- 要保留截图相似度判断，这是技术面试里的关键抓手。
- 不要只说“熔断”，可以说“当前平台的失败阈值控制”或“停止继续在当前平台重试”。
- 要讲清楚一个平台失败不影响其他平台继续采集。

## 8. 截图相似度怎么计算

**面试官提问：**

你刚才提到后端会计算前后截图相似度，连续几轮相似度很高就认为页面没有推进。

那我具体问一下：这个截图相似度你们是怎么计算的？是简单像素对比、感知哈希，还是用模型/特征？如果页面里有加载动画、价格局部变化，或者广告轮播，怎么避免误判？

**推荐回答：**

我们这里用的是传统图像相似度里的 SSIM，也就是结构相似度。做法是把前后两张截图转成灰度图，统一 resize 到相同尺寸，然后计算结构相似度分数。相比直接像素差，SSIM 更关注亮度、对比度和结构信息，对一些局部像素变化没那么敏感。

实际判断时不是只看一组截图，而是看连续几轮。比如连续 3 次动作后，前后截图的 SSIM 都很高，才认为页面主体没有有效变化。这样可以减少一次偶然加载、动画或者广告轮播带来的误判。

对于连续滑动这种场景，我们还会结合 action 类型和次数判断。比如连续执行滑动，但截图结构一直高度相似，就说明可能列表没有新增内容，或者已经滑到底了，这时就停止继续滑当前平台，标记当前平台采集失败或无结果。

**回答注意点：**

- 术语要说 SSIM，不要说成 SSRM。
- 强调不是单次相似度判断，而是连续多轮高相似才认为卡住。
- 对滑动场景要结合 action 类型和次数，避免只靠图片相似度下结论。

## 9. 可观测性和问题排查

**面试官提问：**

你简历里写到接入了 Langfuse，并且结合 AOP 切面做全链路与 LLM 主动触发的 Human-in-the-loop 机制，保证 Agent 可控。

我想先问可观测性这块：这个酒店比价 Agent 线上如果失败了，比如用户说“查不到价格”或者“点错页面了”，你们怎么排查是哪一环出了问题？

具体来说，你们会记录哪些日志或 trace？比如模型输入输出、截图、action、端侧执行结果、LangGraph 节点流转、Redis 状态这些，哪些会进 Langfuse，哪些会进你们自己的业务日志？

**推荐回答：**

我们排查时基本是按 `session_id` 串起整条链路。第一步先看后端的节点流转日志，确认任务卡在哪个阶段，比如是用户信息补齐、某个平台采集、页面判断，还是结果汇总。节点日志里会记录 LangGraph 的节点跳转关系，以及影响路由的关键字段。

确定具体节点后，再去 Langfuse 看这个节点里的模型调用，包括 prompt、输入的任务上下文、截图相关信息、模型输出的状态判断和 action、模型名、耗时这些。这样可以判断是模型看错页面、输出动作不合理，还是模型输出本身没问题。

如果模型输出没问题，就继续看端侧执行日志，比如 action 有没有真正执行成功、无障碍服务有没有被系统拦截、执行后截图有没有变化、有没有异常上报。最后再结合 Java 业务库里的会话信息、调用日志、子任务状态、价格采集结果这些，确认状态有没有正确落库。

简单说，Langfuse 主要看模型调用和 LLM 链路；我们自己的业务日志和数据库主要看 LangGraph 节点流转、端侧执行结果、Redis/任务状态和最终业务数据。这样可以定位到底是模型判断问题、端侧执行问题，还是状态流转问题。

**回答注意点：**

- 排查主线要按 `session_id` 串起来。
- Langfuse 主要讲模型调用链路：prompt、输入上下文、模型输出、模型名、耗时。
- 业务日志主要讲节点流转、端侧执行、Redis/任务状态、业务结果落库。
- 要能区分模型判断问题、端侧执行问题、状态流转问题。

## 10. Human-in-the-loop 机制

**面试官提问：**

你简历里写到“通过 SSIM 截图相似度检测识别 Agent 死循环，并结合 AOP 切面任务拦截与 LLM 主动触发的 Human-in-the-loop 机制，保障 Agent 可控性”。

我想具体问一下：你们这个 Human-in-the-loop 是在什么情况下触发的？是模型主动判断不确定时触发，还是规则检测到风险后触发？触发后用户或人工要做什么？系统怎么从人工反馈继续执行？

**推荐回答：**

这里的 Human-in-the-loop 有两种触发方式。

第一种是模型主动触发。比如模型从截图里识别到当前页面是登录页，就不会让 Agent 自动处理，而是返回一个暂停动作，提示用户先完成登录。前端收到这个动作后，会暂停任务并展示用户操作提示。

第二种是用户主动触发。因为 Agent 执行过程中会接管手机，而且整个比价流程比较长，用户如果临时要接电话或者想暂停，可以通过触碰任务控制浮层来暂停任务。

暂停后，前端会保存当前会话 ID 和当前执行的 trace。这个 trace 里包含当前 App、当前阶段、上一轮动作等执行上下文。用户点击继续后，前端带着这些信息再次请求后端，后端根据 session_id 和 trace 恢复任务状态，从暂停点继续执行。

**回答注意点：**

- 不要泛泛说“人工审核”，这个项目里的 HITL 主要是登录页用户处理和用户主动暂停。
- 可以说 trace，但要解释 trace 里包含当前 App、阶段、上一轮动作等上下文。
- 恢复时强调根据 `session_id` 和 trace 从暂停点继续，而不是重新开始。

## 11. AOP 切面任务拦截

**面试官提问：**

你简历里写到“结合 AOP 切面任务拦截与 LLM 主动触发的 Human-in-the-loop 机制”。

我想问 AOP 这块：为什么这里要用 AOP 切面做任务拦截？它具体拦截的是哪些操作或节点？比如暂停、取消、超时、重复执行、异常状态这些，是怎么在切面里统一处理的？如果不用 AOP，直接写在每个节点里会有什么问题？

**推荐回答：**

因为这是一个接管手机的全自动流程，执行大概 20 秒到 1 分钟，用户中途可能要接电话或者有急事，所以必须支持随时暂停。

这里我们用 AOP 是因为暂停属于横切逻辑，用户可能在任意节点暂停，不适合每个节点都写一遍判断。我们通过自定义注解标记关键执行方法，切面在方法执行前拦截；如果当前会话已经被置为暂停，就直接中断后续执行，不再继续调用模型或下发操作。

这样暂停逻辑和具体业务节点解耦，也避免漏掉某个执行入口。

**回答注意点：**

- AOP 的理由要讲“暂停是横切逻辑”，不要讲成普通业务判断。
- 提到自定义注解即可，不需要展开太多实现细节。
- 强调中断后不再继续调用模型或下发端侧操作。

## 12. LangGraph 编排设计和 Plan-React

**面试官提问：**

你简历里写到“基于 LangGraph 实现 Plan-React 多 Agent 编排，支持按业务场景动态构建不同拓扑的工作流 DAG”。

我想具体问：在酒店比价助手里，LangGraph 的图大概是怎么设计的？有哪些核心节点？边的跳转条件是什么？你们说的 Plan-React 是怎么体现在这个流程里的？

**推荐回答：**

酒店比价这个 LangGraph 图里，核心节点主要有参数校验、酒店确认、GUI 操作和结果汇总。

参数校验节点负责从用户输入里抽取城市、酒店名、入住离店日期这些信息，信息不全就追问。酒店确认节点会把用户输入的酒店名和业务库里的酒店 ID 做映射；如果匹配不唯一，就返回候选列表让用户确认具体是哪一家。

用户确认后进入 GUI 操作节点。这里的 Plan-React 主要体现在这个节点里：Plan 不是每轮让模型临时生成的，而是我们为 GUI 操作节点预先定义好的，比如在 OTA 平台里要按“搜索酒店、进入详情页、找到房型和价格、满足终止条件后结束采集”这个大方向执行。

React 体现在每一步真实操作后，端侧会把截图和执行结果回传给后端，模型根据新的 observation 判断当前页面状态，再决定下一步 action，比如点击、输入、滑动、返回或结束当前平台。执行完后再观察、再决策，形成循环。

最后结果汇总节点会把各个平台采集到的房型、价格、失败状态整理成统一格式返回给用户。

节点跳转上，如果是后端内部可以连续执行的节点，就用 LangGraph 的路由继续往下走；如果到了需要端侧真实操作的节点，本轮请求会先返回 action 或 next_node 给端侧，端侧执行完再带着 session_id、截图和执行结果回来，后端从对应节点继续推进。

**回答注意点：**

- 要正面回答 Plan 和 React 如何体现，不能只讲节点列表。
- Plan 可以说是为 GUI 操作节点预先定义好的，不要说成模型每轮自由规划。
- React 要讲“执行后回传截图和结果，再观察、再决策”的循环。
- 节点跳转要区分后端内部路由和端侧执行后再回调继续推进。
