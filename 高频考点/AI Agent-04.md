# AI Agent-04

## 1. 如何设计 Agent 的 Tool registry？

**问题：** 如何设计 Agent 的 Tool registry？

**答案：**

Tool registry 可以理解成 Agent 的工具目录和治理中心。它不只是保存工具名和参数 schema，而是负责工具发现、工具路由、权限控制、风险分级、版本管理、执行策略和可观测。

一个生产级 Tool registry 通常要保存这些信息：

```json
{
  "name": "refund_order",
  "description": "对符合条件的订单发起退款",
  "input_schema": {},
  "output_schema": {},
  "tags": ["order", "refund"],
  "when_to_use": "用户明确要求退款，且订单号已确认",
  "when_not_to_use": "用户只是咨询退款规则，或订单号缺失",
  "risk_level": "high",
  "permission": ["order:refund"],
  "tenant_scope": "current_tenant",
  "read_write_type": "write",
  "need_confirmation": true,
  "timeout_ms": 5000,
  "retry_policy": "no_retry_for_write",
  "idempotency_required": true,
  "version": "v2",
  "owner": "order_team"
}
```

**核心设计点：**

- **工具元数据：** name、description、tags、输入输出 schema、owner、version。
- **路由信息：** when_to_use、when_not_to_use、正例、反例、适用任务类型。
- **权限信息：** 用户角色、租户、资源范围、工具白名单。
- **风险控制：** read/write、高风险等级、是否需要二次确认、是否允许自动执行。
- **执行策略：** timeout、retry、fallback、幂等键、限流、熔断。
- **结果治理：** output schema、脱敏规则、结果摘要、错误码解释。
- **观测信息：** tool_call_id、trace_id、调用耗时、成功率、错误率、版本记录。

Tool registry 的关键原则是：**模型只能看到当前任务可用的少量候选工具，而不是看到所有工具。**

一般流程是：

```text
用户请求
  -> 意图识别 / task state
  -> 从 registry 中筛选可用工具
  -> 权限和风险过滤
  -> TopK 候选工具暴露给模型
  -> 模型生成 tool call
  -> 系统再次做 schema / 权限 / 业务规则校验
  -> 执行工具
  -> 结果写回 tool state 和 run trace
```

这样设计可以避免工具太多导致模型误选，也能避免敏感工具被模型看到或误调用。

**面试可以这样说：**

我设计 Tool registry 时，不会只把它当成一个函数列表，而是把它做成工具治理中心。每个工具除了 name、description、input_schema、output_schema，还要有 when_to_use、when_not_to_use、tags、risk_level、permission、read/write 类型、是否需要确认、timeout、retry、幂等策略、owner 和 version。每轮请求进来后，系统根据 intent、task state、用户权限和风险等级，从 registry 里筛出少量候选工具给模型；模型生成 tool call 后，后端还要再做 schema、权限和业务规则校验。这样可以减少工具误选，限制敏感工具暴露，并且保证工具调用可审计、可回放、可灰度。

**答案：**

这个问题已有答案可以直接使用：

- [[AI Agent-01#4. Agent 比传统 Workflow 好吗？|AI Agent-01 第 4 题：Agent 比传统 Workflow 好吗？]]

第 4 题已经覆盖 Agent 和 Workflow 的核心区别：Workflow 流程固定、可控、可测试，适合确定性业务流程；Agent 路径动态、能根据中间结果调整动作，适合目标明确但路径不确定的开放式任务。工程上通常不是二选一，而是 Agentic Workflow：Workflow 管主流程，Agent 处理需要理解、检索、推理和生成的节点。

**面试可以这样说：**

Agent 和 Workflow 的本质区别在于控制方式。Workflow 是人提前定义好 A -> B -> C，流程、分支和异常处理都比较确定，所以适合支付、审批、订单、工单、退款这类高可靠业务。Agent 是用户给目标，模型根据上下文和工具结果动态规划下一步，适合调研分析、复杂问答、多工具组合、报告生成这类路径不固定的任务。我的选择原则是：流程清楚、风险高、可测试性要求强，用 Workflow；目标清楚但路径不确定、需要模型理解和动态决策，用 Agent。生产里更常见的是组合：Workflow 管确定性主链路，Agent 只嵌入到需要智能判断的节点，并受权限、状态机和人工确认约束。

智能体开发范式我一般按控制方式来分。第一类是 ReAct，边思考边调用工具，适合路径不确定、多轮工具调用的任务；第二类是 Plan-and-Execute，先规划再执行，适合调研、报告、代码修改这类可拆解任务；第三类是 Tool-Calling Agent，核心是模型选工具和生成参数，适合 API、数据库、搜索、代码执行等工具型任务；第四类是 RAG Agent，适合企业知识库、文档分析、客服问答；第五类是 Agentic Workflow 或 State Machine Agent，用工作流和状态机管主流程，适合订单、审批、支付、工单等高可靠业务；第六类是 Reflection，用于代码、推理、报告这类需要自检修正的任务；第七类是 Multi-Agent 或 Hierarchical Agent，适合复杂任务分工、并行执行和交叉审核。工程选型看任务开放程度、风险等级、工具复杂度、状态管理要求和成本延迟。

## 4. 如果让你设计一个 Agent 规划器，怎么避免它每一步都重新规划，导致路径震荡？

**问题：** 如果让你设计一个 Agent 规划器，怎么避免它每一步都重新规划，导致路径震荡？

**答案：**

避免路径震荡的核心是：规划和执行要分层，计划要有稳定性，re-plan 要有触发条件，不能每一步都让模型重新从零规划。

我会这样设计：

**1. 计划要结构化保存**

第一次规划后，把计划写入 task state，而不是只放在上下文里：

```json
{
  "goal": "生成竞品分析报告",
  "plan": [
    {"step_id": 1, "name": "收集资料", "status": "done"},
    {"step_id": 2, "name": "提取对比维度", "status": "running"},
    {"step_id": 3, "name": "生成报告", "status": "pending"}
  ],
  "current_step": 2,
  "replan_count": 0
}
```

后续每轮不是重新规划全局路径，而是基于当前 `current_step` 执行和更新。

**2. 区分 plan 和 next action**

Planner 负责生成高层计划，Executor 只负责执行当前步骤。每一步只让模型决定当前 step 的 next action，而不是改完整计划。

```text
Planner：生成/修订计划
Executor：执行当前步骤
Controller：判断是否允许 re-plan
```

**3. re-plan 必须有触发条件**

只有这些情况才允许重新规划：

- 当前步骤失败且重试无效。
- 工具返回结果改变了关键假设。
- 用户修改目标。
- 发现缺少关键步骤。
- 计划依赖不成立。
- 安全或权限规则阻断当前路径。

普通中间结果不理想，不应该立刻全局 re-plan。

**4. 限制 re-plan 范围**

能局部改就不要全局推翻：

- 优先修改当前步骤。
- 其次修改后续未执行步骤。
- 已完成步骤默认冻结。
- 高风险已执行步骤不能被模型随意覆盖。

**5. 做进展检测和震荡检测**

系统要记录最近几步动作，检测是否出现：

- 反复切换计划。
- 反复调用同一个工具。
- 同样参数得到同样结果还继续尝试。
- re-plan 后又回到原路径。
- 多次没有新增信息。

命中后要停止、降级、追问或转人工。

**6. 给规划器加预算**

比如：

```text
max_steps = 10
max_replan = 2
max_same_tool_retry = 2
max_no_progress_steps = 3
```

预算用完后不能继续自由推理，要返回部分结果、追问用户或失败退出。

**面试可以这样说：**

我不会让 Agent 每一步都重新规划全局路径，否则很容易路径震荡。我的做法是把计划结构化写入 task state，区分 Planner 和 Executor：Planner 负责生成高层计划，Executor 只执行当前 step，Controller 判断是否允许 re-plan。re-plan 必须有明确触发条件，比如当前步骤失败、用户修改目标、关键假设变化、权限阻断或依赖不成立。即使 re-plan，也优先局部修改当前步骤或后续未执行步骤，已完成步骤默认冻结。同时记录最近动作做震荡检测，比如反复换计划、重复调用同一工具、没有新增信息，就触发停止、追问或转人工。核心是让计划稳定推进，而不是让模型每轮从零想一遍。

## 5. 如果一个 Agent 需要同时读知识库、调外部 API，再结合用户历史偏好回答，你怎么处理这三类上下文的优先级？

**问题：** 如果一个 Agent 需要同时读知识库、调外部 API，再结合用户历史偏好回答，你怎么处理这三类上下文的优先级？

**答案：**

我不会把三类上下文平铺进 prompt，而是按“可信度、时效性、权限和任务相关性”分层处理。一般来说，系统规则和权限最高；外部 API 的实时事实优先于知识库；知识库证据优先于用户历史偏好；历史偏好主要用于个性化表达和默认选项，不能覆盖事实证据。

一个比较稳的优先级可以是：

```text
系统规则 / 安全策略 / 权限
> 外部 API 返回的实时业务事实
> 高可信知识库证据
> 当前用户明确输入
> 任务状态和已确认槽位
> 用户历史偏好 / 长期记忆
> 模型自身推断
```

**1. 外部 API 负责实时事实**

API 适合回答订单状态、库存、价格、账户权限、审批进度、最新配置这类动态信息。只要 API 返回可信且权限校验通过，就应该以 API 为准。

例如：

- 知识库说“退款通常 3 天到账”，但 API 返回该订单已退款失败，要以 API 为准。
- 用户历史偏好说“喜欢走普通配送”，但库存和物流 API 显示普通配送不可用，就不能按历史偏好推荐。

**2. 知识库负责规则、解释和背景**

知识库更适合提供政策、产品说明、操作手册、FAQ、合同条款、流程解释等相对稳定的信息。

它的作用是：

- 给 API 结果补解释。
- 提供规则依据。
- 支持回答可追溯引用。
- 在没有实时 API 的情况下提供默认知识。

但知识库要看版本、发布时间、权限和来源权威性，不能拿过期文档覆盖实时系统状态。

**3. 用户历史偏好负责个性化，不负责改事实**

用户历史偏好可以影响：

- 回答语言和语气。
- 展示粒度。
- 默认排序。
- 推荐偏好。
- 常用配置。

但它不能覆盖事实和规则。比如用户偏好“简短回答”，系统仍然要在高风险场景给足必要说明；用户偏好“低价优先”，也不能推荐无库存、无权限或不合规的选项。

**4. 拼接上下文时要分区标注来源**

最终给模型的上下文要明确分区，避免模型混淆：

```text
[System Policy]
安全规则、权限边界、回答约束

[User Query]
用户当前问题

[Task State]
当前任务目标、已确认参数、缺失参数

[API Facts]
实时接口结果、时间戳、trace_id、状态码

[Knowledge Evidence]
知识库片段、文档版本、来源、更新时间、引用位置

[User Preferences]
历史偏好、置信度、更新时间、是否用户确认
```

这样模型知道哪些是事实，哪些是证据，哪些只是偏好。

**5. 冲突时按规则处理，不让模型自己猜**

常见冲突处理：

- API 和知识库冲突：优先 API，同时提示知识库可能过期或只作规则解释。
- 当前用户输入和历史偏好冲突：优先当前输入，并更新或暂时覆盖偏好。
- 用户偏好和权限规则冲突：优先权限规则。
- 多个知识库文档冲突：按版本、发布时间、权威来源和适用范围排序；无法判断就说明不确定或转人工。
- API 失败或结果不完整：降级到知识库和历史偏好，但要说明“当前实时状态无法确认”。

**6. 工程上要做上下文预算控制**

三类上下文都可能很长，不能全部塞进去。我会做：

- API 结果结构化摘要，只保留和问题相关字段。
- 知识库只放 rerank 后的少量证据块。
- 历史偏好只取当前任务相关偏好，不加载完整记忆。
- 每段上下文带 source、timestamp、confidence。
- 高风险回答必须引用事实来源或触发确认。

**面试可以这样说：**

我会把这三类上下文分层，而不是简单拼在一起。优先级上，系统规则和权限最高，其次是外部 API 返回的实时业务事实，再是知识库里的规则和文档证据，然后才是用户当前输入、任务状态和历史偏好。用户历史偏好主要用于个性化表达、默认选项和排序，不能覆盖 API 事实、知识库规则和权限边界。工程上我会把上下文分成 API Facts、Knowledge Evidence、User Preferences 等区块，并给每段带来源、时间戳、置信度和权限信息。冲突时不让模型自己猜，比如 API 和知识库冲突以 API 为准，当前输入和历史偏好冲突以当前输入为准，偏好和权限冲突以权限为准。如果实时 API 失败，可以降级用知识库回答，但要明确说明实时状态无法确认。

## 6. LangChain 和 LangGraph 如何选择？

**问题：** LangChain、LangGraph 如何选择？

**答案：**

LangChain 和 LangGraph 不是完全互斥的关系。简单理解：LangChain 更偏上层开发框架，提供模型、Prompt、Tool、Retriever、Agent 等封装和大量集成；LangGraph 更偏底层编排运行时，用 graph、state、node、edge 来管理有状态、可恢复、可观测的 Agent 执行流程。

**1. 什么时候选 LangChain**

如果项目链路比较简单，优先用 LangChain：

- 简单 Chatbot。
- 单轮或轻量多轮问答。
- 普通 RAG：query -> retrieve -> rerank -> generate。
- 简单 Tool Calling。
- 快速验证模型、工具、向量库、检索器接入。
- 需要大量生态集成，比如模型 provider、数据库、向量库、document loader。

LangChain 的优势是上手快、封装多、生态广，适合快速搭原型和中低复杂度应用。

**2. 什么时候选 LangGraph**

如果 Agent 开始有复杂控制流，就更适合 LangGraph：

- 多步骤任务规划和执行。
- 分支、循环、条件跳转。
- 多工具调用和失败重试。
- human-in-the-loop，人审或用户确认。
- 中断恢复、长任务续跑。
- checkpoint、状态持久化、time travel debug。
- 多 Agent 协作。
- 需要精细记录每个节点输入输出和状态变化。

LangGraph 的价值是把 Agent 执行显式建模成有状态的图，而不是一条隐式 chain。生产级 Agent 经常需要可控、可恢复、可回放，这些更适合用 LangGraph 表达。

**3. 一个简单判断标准**

可以用这几个问题判断：

```text
是否只有一条固定链路？
是否需要保存任务状态？
是否需要中断后恢复？
是否有循环、分支、并行、人审？
是否需要追踪每个节点为什么执行？
是否需要长期运行或失败重试？
```

如果大部分答案是否，LangChain 就够了；如果大部分答案是，应该考虑 LangGraph。

**4. 工程上常见组合方式**

实际项目里经常不是二选一，而是组合使用：

```text
LangGraph：负责流程编排、状态、checkpoint、分支、恢复
LangChain：负责模型封装、prompt、tool、retriever、document loader 等组件
LangSmith：负责 trace、评测、调试和观测
```

也就是说，LangGraph 管“任务怎么流转”，LangChain 管“每个节点里怎么调用模型、工具和检索能力”。

**5. 不建议为了复杂而复杂**

如果只是一个固定 RAG 链路或简单工具调用，直接上 LangGraph 可能会增加开发和维护成本。反过来，如果已经出现状态散落、异常难恢复、用户确认流程混乱、工具调用难回放、链路分支越来越多，这时继续用简单 chain 会越来越难维护。

**面试可以这样说：**

我不会把 LangChain 和 LangGraph 当成互斥选择。LangChain 更像上层 Agent 开发框架和组件生态，适合快速接模型、Prompt、Tool、Retriever、向量库和普通 RAG；LangGraph 更像有状态 Agent 的编排运行时，适合多步骤、分支循环、工具重试、人审、中断恢复、checkpoint 和可回放的生产级 Agent。我的选择原则是：链路固定、状态少、只是普通 RAG 或简单 tool calling，用 LangChain 更快；如果任务有明确状态流转、复杂控制流、长任务、人审和恢复需求，就用 LangGraph。工程里也可以组合：LangGraph 负责流程和状态，LangChain 负责节点里的模型、工具和检索组件。

## 7. 如何解决 MCP 膨胀？

**问题：** 如何解决 MCP 膨胀？

**答案：**

MCP 膨胀通常指 MCP server、tool、resource、prompt 模板越来越多，最后导致工具列表过大、schema 占满上下文、模型误选工具、权限边界变模糊、调用链路难观测。解决思路不是让模型看到更多工具，而是做分层治理和按需暴露。

**1. 不把所有 MCP 工具直接暴露给模型**

MCP 负责标准化接入，但不等于 `tools/list` 拿到什么就全部塞给模型。工程上应该先进入本地 tool registry，再根据当前请求筛选候选工具。

```text
MCP tools/list
  -> 本地 tool registry
  -> 补充业务 metadata
  -> intent / task state / permission 过滤
  -> TopK 候选工具暴露给模型
```

模型每轮只看到当前任务相关的少量工具，而不是全量 MCP 能力。

**2. 按领域拆 MCP server**

不要把所有能力塞进一个超级 MCP server。更合理的是按业务域拆分：

- `crm-mcp`：客户、商机、跟进记录。
- `order-mcp`：订单、物流、售后。
- `doc-mcp`：知识库、文档、搜索。
- `devops-mcp`：部署、日志、监控。
- `finance-mcp`：账单、付款、发票。

这样可以降低工具命名冲突，也方便权限、限流、审计和版本管理。

**3. 做两阶段工具路由**

第一阶段只让模型或路由器看短描述，判断需要哪个 server 或工具组；第二阶段才展开少量工具 schema。

```text
用户问题
  -> 选择 domain / MCP server
  -> 召回候选 tool group
  -> 展开 TopK tool schema
  -> 模型生成 tool call
```

这和 Skill 的渐进式披露类似：先看摘要，命中后再加载细节。

**4. 工具粒度要合适**

MCP 膨胀很多时候来自工具粒度失控：

- 太细：`get_user_name`、`get_user_phone`、`get_user_email` 会导致工具数量爆炸。
- 太粗：`execute_any_sql`、`call_any_api` 会导致权限和安全不可控。

更合理的是按业务动作设计工具，比如 `get_customer_profile`、`search_orders`、`create_refund_request`，输入输出稳定，权限边界清晰。

**5. 给工具加治理 metadata**

每个 MCP 工具进入 registry 后，要补充业务侧 metadata：

- domain / tags。
- when_to_use / when_not_to_use。
- read/write 类型。
- risk_level。
- permission scope。
- owner 和 version。
- timeout、retry、rate limit。
- 是否需要用户确认。
- 是否可并行、是否幂等。

这些信息不一定全部给模型看，但必须给系统路由、权限校验和执行治理使用。

**6. 控制 schema 和返回结果长度**

MCP 工具膨胀不只发生在工具数量，也发生在 schema 和 observation 上。

处理方式：

- schema 只保留必要字段，不写长篇说明。
- 复杂参数用枚举、对象结构和示例约束。
- 大结果分页、摘要、字段裁剪。
- 原始结果不直接塞给模型，先经过 observation adapter。
- 对返回结果做脱敏、压缩和引用标记。

**7. 做淘汰、合并和版本治理**

MCP 工具要像 API 一样治理：

- 低频工具下线或隐藏。
- 重复工具合并。
- 相似工具明确边界。
- 旧版本设置 deprecated。
- 线上错选工具进入回归集。
- 统计工具曝光率、调用率、成功率、误选率。

否则工具只增不减，系统会越来越不可控。

**面试可以这样说：**

MCP 膨胀的核心问题不是 MCP 本身，而是把 MCP 当成工具大杂烩，导致工具数量、schema、权限和返回结果都失控。我会先把 MCP 暴露出来的 tools/list 接入本地 tool registry，而不是直接全量给模型；然后按业务域拆 MCP server，比如订单、知识库、CRM、DevOps 分开；每轮请求根据 intent、task state、用户权限和风险等级做两阶段路由，只展开 TopK 候选工具 schema。工具设计上要控制粒度，不能太细导致数量爆炸，也不能太粗变成万能接口。每个工具还要补充 metadata、权限、风险等级、owner、version、限流、重试和是否需要确认。最后要持续做工具合并、下线、版本治理和误选率观测。核心原则是：MCP 负责标准化接入，Agent Runtime 负责筛选、治理和安全边界。

## 8. Few-shot 在 Agent 评测中的作用是提升能力还是降低方差？在评测 pipeline 的哪个阶段注入？如何防止 few-shot 过拟合？

**问题：** Few-shot 在 Agent 评测中的作用是提升能力还是降低方差？在评测 pipeline 的哪个阶段注入？如何防止 few-shot 过拟合？

**答案：**

Few-shot 在 Agent 评测里主要不是用来“提升被测模型能力”，而是用来稳定任务格式、评判标准和执行策略，降低模型输出方差。它可以让模型更清楚该怎么规划、怎么调用工具、怎么输出结构化结果，但如果把 few-shot 放得太贴近测试集，也会让评测失真，变成记样例而不是测泛化能力。

**1. Few-shot 的作用：更偏降低方差**

在评测场景里，few-shot 常见作用是：

- 固定输出格式。
- 固定 tool call 格式。
- 说明什么算成功、什么算失败。
- 展示边界 case 的处理方式。
- 降低同一输入多次运行的随机波动。
- 让 LLM-as-judge 的评分口径更一致。

所以它确实可能提升某些任务表现，但评测里更应该把它理解为“控制变量和稳定评测口径”，不是偷偷给模型补能力。

**2. 在 pipeline 哪个阶段注入**

要看 few-shot 服务于谁。

如果是评测 Agent 本身，few-shot 通常注入到被测 Agent 的 prompt 或 policy 层：

```text
test case
  -> 构造 Agent 输入
  -> 注入固定 system prompt / few-shot policy examples
  -> Agent 执行：规划、检索、工具调用、生成
  -> 记录 run trace
  -> evaluator 评分
```

这里的 few-shot 不能根据每条测试样本动态挑太相似的例子，否则会泄漏测试集。

如果是 LLM-as-judge，few-shot 应该注入到 evaluator prompt：

```text
Agent 输出 + trace
  -> evaluator prompt
  -> 注入评分 rubric + judge few-shot
  -> 输出 score / reason / error_type
```

这类 few-shot 的作用是校准评分标准，比如什么叫工具误选、什么叫证据不足、什么叫任务完成。

**3. 不同 few-shot 要分开**

工程上最好分成两类：

- **Agent few-shot：** 教被测 Agent 如何执行任务。
- **Judge few-shot：** 教评测器如何评分。

这两类不要混在一起。Agent few-shot 会影响被测系统能力；Judge few-shot 影响评分稳定性。如果不分开，就很难判断指标变化是 Agent 真的变好了，还是评测器评分口径变了。

**4. 如何防止 few-shot 过拟合**

防过拟合的关键是把 few-shot 当成通用规则示例，而不是测试题答案。

具体做法：

- few-shot 和 test set 严格隔离。
- few-shot 不使用测试集同源改写样本。
- few-shot 覆盖任务类型，不覆盖具体答案。
- 控制 few-shot 数量，不堆大量相似例子。
- 固定 few-shot 版本，评测前后不随意改。
- 单独保留 hidden test set。
- 做多 seed、多模型或多批次稳定性测试。
- 看分类型指标，不只看总分。

如果线上错例要回流，应该先进入 dev set 或 prompt 调试集，确认改法后再用独立 test set 评估，不能把线上错例直接塞进 few-shot 后再拿同一批错例报提升。

**5. 如何判断是不是过拟合**

几个典型信号：

- few-shot 相似题提升明显，不相似题没有提升。
- dev set 提升，hidden test set 不提升。
- 换一批测试集后指标掉得很厉害。
- 输出越来越像 few-shot 模板，但任务完成率没提升。
- judge few-shot 改动后分数提升，但人工复核不认同。

这说明 few-shot 可能只是在适配评测集，而不是提升真实 Agent 能力。

**6. 推荐实践**

我会把评测集拆成：

```text
few-shot examples：少量通用示例，用于稳定格式和口径
dev set：调 prompt、调工具路由、调评测器
test set：固定回归评测
hidden set：防止过拟合和刷榜
online sample：线上抽样人工复核
```

同时记录每次评测使用的 prompt 版本、few-shot 版本、工具 mock 版本、模型版本和数据版本，保证可回放。

**面试可以这样说：**

Few-shot 在 Agent 评测里主要作用不是单纯提升能力，而是降低方差和稳定评测口径。对被测 Agent 来说，它可以固定任务执行方式、tool call 格式和边界 case 处理；对 LLM-as-judge 来说，它可以校准评分标准。注入位置要分清：如果是指导 Agent 执行，就放在 Agent prompt 或 policy 层；如果是指导评测器评分，就放在 evaluator prompt 里，两者要隔离。防止 few-shot 过拟合的核心是 few-shot、dev set、test set 和 hidden set 分离，few-shot 只放通用示例，不放测试题同源样本；版本固定，不根据 test case 动态召回相似例子；最后用 hidden set、人工复核、多 seed 和分类型指标验证，避免只是把评测集刷高。

## 9. 讲一下你做过的一个 Agent 项目，重点说业务背景、流程和你负责的部分

**问题：** 讲一下你做过的一个 Agent 的项目，重点说业务背景、流程和你负责的部分。

**答案：**

这类题不要一上来就说用了 LangChain、向量库、Function Calling，而是要先讲业务为什么需要 Agent，再讲用户请求怎么从入口流到结果，最后讲自己负责了哪些关键模块。

可以用“企业知识库 + 工单辅助 Agent”来回答：

**1. 业务背景**

项目背景是内部客服和运营同学每天要处理大量咨询、工单和制度查询，比如订单状态、退款规则、物流异常、活动政策、SOP 操作说明等。原来主要靠人工查文档和后台系统，问题是：

- 知识分散在文档、FAQ、工单记录和业务系统里。
- 一线同学查询成本高，回答口径不一致。
- 有些问题只靠知识库不够，还要查订单、物流、用户历史记录等实时数据。
- 高风险动作，比如退款、改地址、关闭工单，不能让模型直接自由执行。

所以我们做的不是普通问答机器人，而是一个面向客服场景的 Agent：它既能检索知识库，也能调用内部 API，还能根据工单状态给出处理建议，但写操作必须受权限和确认流程约束。

**2. 用户侧流程**

用户使用时大致是：

```text
客服输入用户问题
  -> Agent 判断问题类型
  -> 如果是制度/政策问题，检索知识库并给出带来源的答案
  -> 如果涉及订单/物流/账户，调用内部只读 API 查询实时状态
  -> 如果需要处理动作，生成建议方案并触发人工确认
  -> 最后输出回答话术、处理依据和下一步操作
```

比如用户问“这个订单为什么不能退款”，Agent 会先识别这是售后类问题，然后查订单状态、支付时间、商品类型，再检索退款政策，最后综合判断原因，给客服一段可直接回复用户的话术，并标出依据来自哪个政策条款和哪个订单字段。

**3. 后端技术流程**

后端流程不是简单把所有上下文塞给模型，而是分层编排：

```text
请求入口
  -> 鉴权、租户识别、输入风控
  -> 意图识别和任务路由
  -> 读取 session state / task state
  -> 选择 RAG、工具调用、追问或直接回答
  -> RAG 做 query rewrite、混合召回、rerank、权限过滤
  -> 工具调用做 schema 校验、权限校验、业务规则校验
  -> 结果汇总、引用校验、安全校验
  -> 输出答案并写回状态、trace 和评估日志
```

这里 Agent 负责理解用户目标、选择能力、组织中间结果；系统侧负责权限、参数、状态、审计和兜底。尤其是工具调用，我们不会让模型直接调用真实接口，而是先通过 tool registry 筛选候选工具，模型只生成 tool call，后端再做强校验后执行。

**4. 我负责的部分**

我主要负责三块：

第一是 Agent 编排链路。包括意图识别、任务状态设计、RAG 和工具调用的路由逻辑，以及多轮对话里缺参数时如何追问、工具失败时如何重试或降级。

第二是工具调用治理。包括设计 tool schema、工具白名单、参数校验、权限校验、风险等级、二次确认和幂等控制。只读接口可以自动执行，高风险写操作必须返回确认卡片，由人工确认后再执行。

第三是评测和观测。我们按意图识别准确率、检索命中率、工具选择准确率、参数准确率、答案 groundedness、任务完成率、转人工率、P95 延迟和单次成本做指标。线上每次运行都会记录 run trace，方便定位到底是检索没召回、模型选错工具，还是业务 API 返回异常。

**5. 项目难点**

这个项目里比较难的点不是把模型接进来，而是把 Agent 做得可控。

- 知识库和实时 API 有冲突时，以实时 API 为准，知识库只解释规则。
- 文档命中不足时，不能编答案，要追问、换 query 或提示证据不足。
- 工具调用必须做权限和参数校验，不能只靠 prompt 限制模型。
- 多轮场景要维护 task state，不能每轮都从历史对话里重新猜。
- 高风险动作要有人审、幂等、审计和回滚预案。

**6. 结果和复盘**

落地后，Agent 主要提升的是一线处理效率和回答一致性。简单政策类问题可以直接生成标准话术，涉及订单的问题可以自动聚合订单字段、物流状态和政策依据，客服不需要在多个系统之间来回查。

复盘来看，Agent 项目最重要的不是模型多强，而是业务边界是否清楚、工具和知识是否治理好、评测闭环是否能持续发现问题。我们后续优化也主要围绕召回质量、工具误选率、复杂工单转人工策略和线上 trace 分析来做。

**面试可以这样说：**

我做过一个偏客服和运营场景的 Agent 项目，目标不是做普通问答，而是帮助一线同学把知识库、订单系统、物流系统和工单系统串起来。业务背景是知识分散、人工查询成本高、回答口径不一致，而且很多问题既需要查政策，也需要查实时订单数据。整体流程是用户输入问题后，先做鉴权、输入风控和意图识别，再读取会话状态和任务状态，判断走 RAG、工具调用、追问还是直接回答。RAG 链路会做 query rewrite、混合召回、rerank 和权限过滤；工具链路由模型生成 tool call，但后端负责 schema 校验、权限校验、业务规则校验和执行治理。我的主要工作是 Agent 编排、tool registry 和工具调用治理，以及评测观测体系，包括意图准确率、工具选择准确率、参数准确率、检索命中率、groundedness、任务完成率、转人工率和 P95 延迟。这个项目最大的难点不是接模型，而是让 Agent 在业务边界内稳定工作：实时 API 和知识库冲突时以实时数据为准，高风险写操作必须二次确认，证据不足不能硬答，所有执行过程都要有 trace 和审计。

## 10. 如果 Agent 系统里有高并发场景，怎么设计限流、降级和幂等？

**问题：** 如果你的 Agent 系统里也有高并发场景，你会怎么设计限流、降级和幂等？

**答案：**

Agent 高并发不能只看接口 QPS，因为一次用户请求可能触发多次模型调用、RAG 检索、rerank、工具调用和状态写回。设计时要按“入口限流、链路分级、资源隔离、降级策略、幂等控制、观测闭环”来讲。

**1. 先识别高并发压力点**

Agent 系统里的压力通常来自几类：

- 用户入口请求突然增加。
- LLM 推理排队，首 token 或 P95/P99 变高。
- RAG 检索、rerank 或 embedding 服务被打满。
- 下游业务工具被 Agent 放大调用。
- 用户重试、前端重复点击、上游超时重试造成流量放大。
- 多轮任务或长任务占用 worker、队列和状态存储。

所以不能只在网关层做一个 QPS 限制，还要控制模型调用次数、工具调用次数、并发任务数、token 预算和租户配额。

**2. 限流设计**

限流要分层做：

- **入口限流：** 按用户、租户、IP、应用、接口做 QPS 和并发数限制。
- **任务限流：** 限制单个用户同时运行的 Agent task 数，避免一个用户开很多长任务。
- **模型限流：** 控制模型调用并发、token/min、请求队列长度和最大输出 token。
- **工具限流：** 不同工具按风险和下游容量设置单独限流，避免 Agent 把业务系统打穿。
- **租户配额：** 企业场景要按租户做 quota，防止大客户或异常租户影响其他租户。

实现上可以用网关限流、Redis 计数器/滑动窗口、令牌桶、漏桶、队列削峰和 worker pool。核心是入口先挡住明显超限请求，内部再按资源类型做细粒度保护。

**3. 降级设计**

降级要按业务重要性和风险分级，不是所有失败都返回系统繁忙。

常见降级策略：

- **模型降级：** 强模型超时或排队过长时，低风险任务切到小模型；复杂任务提示排队或转异步。
- **RAG 降级：** rerank 服务不可用时，退回 BM25 + 向量召回的粗排结果，但降低置信度并限制生成。
- **工具降级：** 只读 API 超时时，可以返回“实时状态暂时无法确认”，再用知识库回答规则；写操作不能降级成猜测执行。
- **功能降级：** 高峰期关闭低优先级能力，比如深度总结、长文生成、多轮自动规划、批量任务。
- **结果降级：** 返回部分结果、引用证据、建议人工处理，而不是让模型硬编完整答案。
- **异步降级：** 对长任务进入队列，前端通过 SSE 或轮询看进度。

降级的原则是：低风险、可解释的能力可以降级；涉及权限、资金、删除、生产变更等高风险动作只能暂停、确认或转人工，不能自动绕过。

**4. 幂等设计**

Agent 里幂等很关键，因为模型调用、工具调用和用户重试都可能导致重复执行。

幂等要覆盖几层：

- **请求幂等：** 前端每次提交带 request_id，后端对同一个 request_id 返回同一结果或同一任务状态。
- **任务幂等：** 每个 Agent run 有 run_id / task_id，重复触发时先查任务状态，而不是新建重复任务。
- **工具幂等：** 写工具必须带 idempotency_key，比如 `tenant_id + user_id + tool_name + business_id + action_type`。
- **状态幂等：** task state 按版本号或 CAS 更新，避免并发节点互相覆盖。
- **消息幂等：** 队列消费要有去重表或消费日志，保证 at-least-once 投递下不会重复产生副作用。

只读工具一般天然幂等，但也要防止重复查询打爆下游；写操作必须先查外部系统真实状态，再决定跳过、重试、补偿还是人工介入。

**5. 重试、熔断和幂等要一起设计**

高并发下最怕“超时 -> 上游重试 -> 下游更慢 -> 更多重试”的放大效应。

所以重试要有边界：

- 只对网络抖动、限流、临时 5xx 做有限重试。
- 使用指数退避和 jitter，避免同一时间集体重试。
- 写操作重试前必须确认幂等键和外部状态。
- 对持续失败的模型、检索或工具服务做熔断。
- 熔断后走降级、排队、转人工或直接失败。

不能把所有失败都交给 Agent re-plan，否则高并发时模型可能反复换工具、重复调用，进一步放大故障。

**6. 观测和压测**

这类设计最后要靠指标验证：

- 入口 QPS、并发数、拒绝率。
- 模型队列长度、首 token 延迟、P95/P99、token/min。
- RAG 检索耗时、rerank 耗时、召回失败率。
- 工具调用成功率、超时率、限流率、熔断次数。
- 重试率、重复请求命中率、幂等冲突数。
- 降级触发次数、转人工率、任务成功率和用户重试率。

上线前要做压测和故障演练，比如模型服务变慢、rerank 挂掉、下游工具 5xx、Redis 抖动、队列积压，验证系统会限流和降级，而不是把整个链路拖垮。

**面试可以这样说：**

如果 Agent 系统有高并发，我不会只在网关加一个 QPS 限制，因为一次 Agent 请求可能放大成多次模型调用、检索、rerank 和工具调用。我会分层设计：入口按用户、租户、IP 做限流，任务层限制并发 Agent run，模型层控制并发、token/min、队列长度和最大输出，工具层按下游容量和风险等级单独限流。降级上，低风险任务可以从强模型降到小模型，RAG 可以在 rerank 不可用时退回粗排结果，只读 API 失败可以返回部分结果并说明实时状态无法确认；但写操作、资金、删除、生产变更这类高风险动作不能降级绕过，必须暂停、确认或转人工。幂等上，每次请求有 request_id，每个任务有 run_id，写工具必须带 idempotency_key，状态更新用版本号或 CAS，队列消费要去重。重试必须有限次、指数退避，并且和熔断、降级一起设计，避免高并发下重试把故障放大。最后通过 P95/P99、模型队列长度、工具超时率、限流率、降级次数、幂等命中率和任务成功率来验证设计是否有效。

## 11. 怎么理解 Agent 项目的数据？和传统模型训练数据有什么不一样？

**问题：** 怎么理解 Agent 项目的数据，和传统模型训练数据有什么不一样？

**答案：**

Agent 项目的数据不能只理解成“prompt 和 answer”。传统模型训练数据更关注输入输出样本，而 Agent 项目的数据更像一条可回放的任务轨迹，包含用户目标、状态变化、检索证据、工具调用、模型决策、外部环境结果、安全校验和最终反馈。

**1. 传统模型训练数据更偏静态样本**

传统训练或微调数据通常是：

```text
input -> output
prompt -> response
query -> label
chosen / rejected
```

它主要解决模型本身的能力问题，比如分类、抽取、问答风格、指令遵循、偏好对齐。数据质量重点看标注是否正确、分布是否覆盖、答案是否一致、噪声是否低。

**2. Agent 数据更偏任务过程和环境交互**

Agent 数据至少包括几类：

- **用户请求数据：** 原始 query、多轮上下文、用户目标、租户、权限。
- **任务状态数据：** task state、slots、current step、plan、checkpoint。
- **RAG 数据：** query rewrite、召回结果、rerank 排序、引用证据、groundedness。
- **工具调用数据：** 候选工具、实际 tool call、参数、返回结果、错误码、耗时。
- **决策轨迹数据：** 为什么追问、为什么调用工具、为什么停止、为什么转人工。
- **安全治理数据：** 权限校验、风控命中、prompt injection 拦截、脱敏记录。
- **结果反馈数据：** 任务是否完成、人工是否采纳、用户是否追问、线上指标。

所以 Agent 数据不是单点答案，而是“目标 -> 计划 -> 行动 -> 观察 -> 状态更新 -> 结果”的完整链路。

**3. 最大区别：Agent 数据有动作和副作用**

传统模型输出错了，通常是答案错；Agent 决策错了，可能会选错工具、查错数据、重复执行、越权访问，甚至触发真实业务副作用。

因此 Agent 数据里必须记录：

- 工具调用前后的状态。
- 权限和业务规则校验结果。
- 写操作的幂等键和确认状态。
- 外部系统真实返回。
- 是否产生副作用以及是否需要补偿。

这也是为什么 Agent 数据要可审计、可回放，而不是只保存最终回答。

**4. Agent 数据不一定都适合拿去训练**

线上 trace 很有价值，但不能直接全部变成训练数据。因为里面可能包含：

- 用户隐私和企业敏感信息。
- 错误工具调用和错误推理路径。
- 过期知识、过期接口返回和临时业务状态。
- 权限信息、内部系统字段和审计数据。
- 多条合理路径，难以用单一标准答案标注。

更合理的做法是先把 trace 用于排障、评测、回归和策略优化；只有经过清洗、脱敏、人工审核，并确认是模型能力问题的数据，才进入微调或偏好训练。

**5. Agent 数据的主要用途**

Agent 数据在工程里通常有几种用途：

- **排障：** 通过 run trace 判断是检索错、工具错、模型错还是状态错。
- **评测：** 构建端到端任务集、工具调用评测集、RAG 评测集和安全评测集。
- **回归：** 把线上错例沉淀成固定 case，防止 prompt 或工具 schema 改坏。
- **优化路由：** 分析工具误选率、参数错误率、追问率和转人工率。
- **数据闭环：** 从高质量成功轨迹里沉淀 SOP、few-shot、规则或训练样本。
- **审计合规：** 追踪谁在什么权限下查了什么数据、执行了什么动作。

**6. 和训练数据的关系**

Agent 数据可以转化成训练数据，但要分层处理：

- 用户 query + 正确 intent，可以做意图分类数据。
- query + gold chunk，可以做 RAG 召回评测或 embedding/reranker 训练数据。
- 工具选择 + 参数，可以做 tool calling 监督数据。
- 成功轨迹和失败轨迹，可以做偏好数据或策略评测数据。
- 最终答案和人工修改，可以做回答质量优化数据。

但不能把所有轨迹都直接喂给模型。比如权限校验、幂等、审批流这些应该由系统规则保证，不应该训练模型“学会遵守”；业务事实更新也应该靠 RAG 或 API，不应该靠训练记住。

**面试可以这样说：**

我理解 Agent 项目的数据和传统模型训练数据最大的区别是：传统训练数据更像静态的 input-output 样本，而 Agent 数据是一条任务执行轨迹。它不只包含用户问题和最终回答，还包含 task state、plan、RAG 召回和 rerank、工具候选、tool call 参数、工具返回、权限校验、安全拦截、状态写回、run trace 和用户反馈。传统训练数据主要用于提升模型本身能力，比如分类、抽取、生成和偏好对齐；Agent 数据首先用于排障、回放、评测、审计和工程优化。它里面有外部环境、有动作、有权限、有副作用，所以不能直接全部拿去训练。正确做法是先脱敏、清洗、标注和分层：意图数据用于路由，query-gold chunk 用于检索评测，工具调用轨迹用于 tool calling 评测或微调，高质量成功轨迹可以沉淀成 few-shot、SOP 或偏好数据。但权限、幂等、审批、业务规则这类边界必须由系统保证，不能指望模型通过训练自己学会。

## 12. 如果用户输入含糊不清，会让 Agent 追问还是自己猜？

**问题：** 如果用户输入含糊不清，你会让 Agent 追问还是自己猜？

**答案：**

这题可以直接复用：

- [[AI Agent-03#25. 一个 Agent 系统里，什么时候应该追问用户，什么时候应该自己继续推理？|AI Agent-03 第 25 题：一个 Agent 系统里，什么时候应该追问用户，什么时候应该自己继续推理？]]

核心判断是：含糊信息是否影响执行结果或带来业务风险。关键槽位缺失、多解释且会影响结果、高风险动作、权限确认、证据不足时要追问；低风险任务、非关键细节、可以从状态/上下文/只读工具/RAG 可靠补齐的信息，可以让 Agent 自己继续推理或查询。

**面试可以这样说：**

我不会简单说一律追问或一律让 Agent 猜，而是看含糊点是否关键、是否高风险、是否会改变结果。如果缺的是订单号、日期、金额、目标对象、权限确认，或者用户一句话有多个可能意图，就应该追问；涉及删除、退款、支付、发消息、生产变更这类高风险动作，也必须确认。如果只是低风险解释、摘要、格式化，或者信息能从 task state、上下文、RAG、只读工具里可靠补齐，就可以自己继续推理。原则是：低风险可推理，高风险要确认；能可靠查到就自己查，不能可靠判断就追问。

## 13. 如果让你优化一个 Agent 系统，通常先从哪里下手？

**问题：** 如果让你优化一个 Agent 的系统，你通常先从哪里下手？

**答案：**

优化 Agent 系统不能一上来就换模型或改 prompt。Agent 是模型、RAG、工具、状态、权限、上下文和业务系统的组合，先要知道问题发生在哪一层，再决定优化手段。

**1. 第一件事：先补齐可观测和可回放**

如果只能先做一件事，我会先看有没有完整 run trace。

至少要能看到：

```text
用户输入
intent / route 结果
task state / missing slots
query rewrite
检索召回和 rerank 结果
最终上下文
模型输入输出
tool call 和参数
工具返回和错误
权限校验结果
最终答案
用户反馈、耗时、成本、版本信息
```

没有这些数据，优化就很容易变成凭感觉改 prompt。先有 trace，才能判断是理解错、检索错、工具错、上下文错、模型错，还是业务规则缺失。

**2. 第二步：按业务目标定义指标**

不同 Agent 优化目标不一样：

- 客服 Agent 看解决率、转人工率、回答一致性、权限安全。
- RAG Agent 看 Recall@K、groundedness、引用准确率、幻觉率。
- 工具型 Agent 看工具选择准确率、参数准确率、调用成功率。
- 数据分析 Agent 看 SQL 正确率、指标口径一致性、越权查询率。
- 运维 Agent 看变更安全、误操作率、恢复时间。

如果没有明确指标，只说“效果不好”，就不知道该优化准确率、延迟、成本、稳定性还是安全。

**3. 第三步：先抓高频失败和高风险失败**

优化优先级不是按技术复杂度排，而是按业务影响排：

- 高频问题：每天大量出现，优化收益最大。
- 高风险问题：可能越权、误操作、错退款、泄露数据，优先级最高。
- 高成本问题：模型调用次数多、长上下文、重复工具调用。
- 高延迟问题：P95/P99 差、排队严重、工具超时。
- 高不确定问题：低置信、证据不足、用户反复纠正。

一般先从线上错例、用户点踩、人工接管、重试率高的 case 里抽样，做错误分类。

**4. 第四步：分层定位再优化**

定位可以按这条链路拆：

```text
输入理解
  -> 路由 / 规划
  -> RAG / 工具
  -> 上下文组装
  -> 模型生成
  -> 输出校验
  -> 状态写回
```

常见优化方向：

- **意图和路由错：** 优化 intent schema、工具 description、路由样本、低置信追问。
- **RAG 召回错：** 优化 chunk、query rewrite、混合检索、rerank、metadata 过滤。
- **工具调用错：** 优化 tool registry、schema、when_to_use、参数校验、候选 TopK。
- **上下文太乱：** 做上下文分区、去重、压缩、证据排序和 token 预算。
- **模型生成错：** 改 prompt、换模型、加格式约束、加 groundedness 校验。
- **状态管理错：** 补 task state、checkpoint、幂等、状态机和恢复机制。
- **安全问题：** 强化权限、脱敏、二次确认、prompt injection 防护和审计。

这个顺序的核心是：先定位瓶颈，再改对应层，不要所有问题都归因给模型。

**5. 第五步：建立回归集和灰度机制**

每次优化都要能验证有没有真的变好：

- 把线上错例沉淀成回归集。
- 按错误类型分桶看指标，而不是只看总分。
- 固定模型版本、prompt 版本、tool schema 版本和索引版本。
- 重要改动先离线评测，再小流量灰度。
- 同时看效果、延迟、成本和安全指标。

否则很容易出现一个 prompt 改动解决了 10 个 case，又破坏了 20 个长尾 case。

**6. 实际优先级**

我通常会按这个顺序下手：

```text
可观测和 trace
  -> 指标和错例分类
  -> 高风险护栏
  -> 高频链路优化
  -> RAG / 工具 / 上下文分层优化
  -> 模型和 prompt 优化
  -> 成本、延迟和并发优化
  -> 回归集和持续评测闭环
```

其中高风险护栏要尽早做，因为安全和权限问题不能等效果优化完再补。

**面试可以这样说：**

如果让我优化一个 Agent 系统，我不会第一步就换模型或改 prompt，而是先补齐可观测和可回放，拿到完整 run trace，包括用户输入、intent、task state、检索、rerank、最终上下文、tool call、工具返回、权限校验、模型输出、耗时、成本和版本信息。然后按业务目标定义指标，比如任务成功率、工具选择准确率、参数准确率、RAG Recall、groundedness、转人工率、P95 延迟和成本。接着从线上高频失败和高风险失败入手，做错例分类，判断问题发生在输入理解、路由规划、RAG、工具、上下文、模型生成还是状态写回。定位后再分层优化：检索问题优化 chunk、query rewrite 和 rerank；工具问题优化 tool registry、schema 和执行前校验；上下文问题做去重、压缩和证据排序；模型问题再改 prompt 或换模型。最后把错例沉淀成回归集，离线评测后灰度上线。核心原则是先可观测、再定位、再优化，不把所有问题都归因给模型。

## 14. 怎么防止 Agent 在复杂任务里越跑越偏？

**问题：** 怎么防止 Agent 在复杂任务里越跑越偏？

**答案：**

Agent 在复杂任务里越跑越偏，本质上是目标、计划、状态和证据没有被稳定约束。模型每一步都根据当前上下文临时决策，如果没有明确任务边界、计划冻结、进展检测和结果校验，就容易被中间结果、噪声上下文、错误工具返回或用户插话带偏。

**1. 先把目标结构化**

不能只把用户原话放在 prompt 里，要把任务目标写进 task state：

```json
{
  "goal": "生成某业务问题的排查报告",
  "scope": ["订单状态", "退款规则", "物流异常"],
  "out_of_scope": ["营销活动复盘", "用户画像分析"],
  "success_criteria": ["给出结论", "列出证据", "给出下一步建议"],
  "constraints": ["只能使用有权限数据", "证据不足要说明"]
}
```

每一步执行前都检查 next action 是否仍然服务于原始目标。偏离 scope 的动作要拦截、降级或追问用户确认。

**2. 计划要稳定，不要每轮从零规划**

复杂任务适合先生成高层计划，再按步骤执行：

```text
Planner：生成高层计划
Executor：只执行当前 step
Controller：判断是否允许 re-plan
Verifier：检查结果是否满足目标
```

计划写入 state，已完成步骤默认冻结。只有用户改目标、关键假设变化、当前步骤失败、权限阻断、发现缺少关键步骤时，才允许 re-plan，而且优先局部修改后续步骤，不要全局推翻。

**3. 上下文要分层，避免噪声带偏**

复杂任务上下文会越来越长，不能把所有历史和工具结果都塞给模型。

我会把上下文分成：

- 系统规则和安全边界。
- 当前任务目标和成功标准。
- 当前 step 和待解决问题。
- 已确认事实。
- 检索证据和工具结果。
- 历史摘要和低优先级参考信息。

拼 prompt 时只放当前 step 需要的信息，历史内容做摘要，工具结果做结构化 observation。用户临时插话、低置信记忆、过期文档和无关检索结果不能和高可信证据平铺。

**4. 做进展检测和偏航检测**

每一步执行后检查有没有真实进展：

- 是否完成了当前 step。
- 是否获得新证据。
- 是否减少了 missing slots。
- 是否离 success criteria 更近。
- 是否重复调用同一工具和同一参数。
- 是否开始处理 out_of_scope 内容。
- 是否连续多步没有新增信息。

如果发现重复调用、反复 re-plan、目标关键词漂移、工具结果没有被使用、上下文越来越偏，就要停止、回到上一个 checkpoint、追问用户或转人工。

**5. 每个阶段加验证节点**

不要等最终答案才发现跑偏。可以在关键节点加 verifier：

- plan verifier：计划是否覆盖目标，是否越界。
- tool verifier：工具是否该调用，参数是否正确。
- evidence verifier：证据是否足够、是否冲突、是否过期。
- answer verifier：结论是否被证据支持。
- safety verifier：是否越权或触发高风险动作。

Verifier 可以是规则、小模型、强模型或人工审核，关键是把“是否继续”交给系统控制，而不是让主 Agent 自己一路跑到底。

**6. 设置预算和终止条件**

要有硬约束：

- 最大步骤数。
- 最大 re-plan 次数。
- 最大工具调用次数。
- 最大连续无进展次数。
- 最大 token 和时间成本。

预算用完后，Agent 不能继续自由发挥，要输出当前进展、已确认事实、未解决问题和下一步建议。

**面试可以这样说：**

我防止 Agent 在复杂任务里越跑越偏，核心不是只靠 prompt 提醒，而是把目标、计划和状态显式管理起来。第一步会把用户目标结构化到 task state，记录 goal、scope、out_of_scope、success criteria、constraints 和当前 step；每一步执行前检查 next action 是否还服务于目标。第二是计划稳定性，Planner 生成高层计划，Executor 只执行当前步骤，只有用户改目标、关键假设变化、步骤失败或权限阻断时才允许局部 re-plan。第三是上下文治理，只给模型当前步骤需要的信息，把系统规则、任务目标、已确认事实、工具结果和历史摘要分区，避免噪声上下文带偏。第四是进展检测和偏航检测，如果连续几步没有新信息、重复调用工具、反复改计划、开始处理 scope 外内容，就停止、回滚到 checkpoint、追问或转人工。最后还要有 verifier 和预算约束，检查计划、工具、证据、答案和安全边界。核心原则是：目标写进状态，计划稳定推进，过程持续校验，发现偏航及时刹车。

## 15. 知识库原始数据不是 Markdown，而是 PDF、PPT、图片或网页，怎么处理进 RAG 系统？

**问题：** 如果知识库原始数据不是 Markdown，而是 PDF、PPT、图片或者网页，你会怎么处理进 RAG 系统？

**答案：**

这类数据不能直接“转成一大段文本再向量化”。非 Markdown 数据的问题是版式复杂、结构容易丢、图片和表格需要特殊解析、网页有噪声和安全风险。所以我会先做文档解析和结构化建模，再做 chunk、索引、权限、版本和引用。

**1. 先统一成 document/block/chunk 模型**

不管来源是 PDF、PPT、图片还是网页，入库后都统一抽象成：

```text
document：原始文档整体
block：标题、段落、表格、图片、列表、代码块、页/幻灯片等结构单元
chunk：用于检索和放入上下文的语义片段
```

每个 block/chunk 都要带 metadata：

```json
{
  "doc_id": "doc_001",
  "source_type": "pdf",
  "block_type": "table",
  "page": 12,
  "section_path": "退款规则/特殊场景",
  "version": "v3",
  "updated_at": "2026-05-08",
  "permission": "customer_service"
}
```

这样检索命中后才能回溯到原文、页码、幻灯片、图片区域或网页 URL。

**2. 不同类型分别解析**

不同数据源不能用同一套简单 text splitter。

- **PDF：** 解析标题、段落、页码、目录、页眉页脚、表格和图片；扫描版 PDF 要 OCR；页眉页脚、页码、水印要清洗。
- **PPT：** 按 slide 解析标题、正文、备注、图表、图片文字和层级关系；保留 slide_no，避免把不同页内容混在一起。
- **图片：** 先 OCR，再根据场景做图像理解，比如图表、流程图、截图、表单；结果要保留 bbox 或区域位置。
- **网页：** 抽正文、标题、发布时间、作者、URL、正文区块，去掉导航栏、广告、推荐、评论和脚本；动态网页要用爬虫渲染或接口抓取。
- **表格/图表：** 保留结构化表格，同时生成可检索的文本摘要和行级文本。

核心是保留结构，而不是只拿纯文本。

**3. 清洗和安全处理**

入库前要做清洗：

- 去掉重复页眉页脚、目录噪声、广告、导航、版权页。
- 过滤乱码、OCR 低置信文本、重复段落。
- 对敏感字段脱敏或打标签。
- 检测 prompt injection，把外部文档里的指令性内容标成不可信数据。
- 给来源打可信度、时效性和权限标签。

网页、用户上传 PDF、邮件附件这类外部内容尤其不能当成系统指令，只能作为被检索的数据。

**4. 按结构切 chunk**

切分时优先按语义和结构：

- 标题层级。
- 章节和段落。
- PPT 单页或页内主题块。
- 表格按表级、行级或业务字段切。
- 图片 OCR 按区域或说明文字切。
- 网页按正文 section 切。

每个 chunk 要带标题路径、页码/slide_no、URL、表格 ID、图片区域等来源信息。必要时做 parent-child chunk：小 chunk 用于召回，大 section 用于补充上下文。

**5. 建多路索引**

非 Markdown 数据只靠向量索引不够。一般要建：

```text
BM25：标题、正文、OCR、网页正文、表格文本
向量索引：语义 chunk、图片说明、表格摘要、PPT 页摘要
结构化索引：表格字段、日期、编号、状态、权限、版本
元数据索引：doc_id、page、slide、url、source_type、updated_at
原文存储：PDF/PPT/图片/网页快照和解析结果
```

检索时做混合召回 + rerank + 权限过滤 + 上下文扩展，而不是只取向量 TopK。

**6. 引用和可追溯必须做好**

RAG 最终回答要能引用到具体来源：

- PDF：文档名 + 页码。
- PPT：文档名 + slide_no。
- 图片：图片名 + OCR 区域或图表说明。
- 网页：URL + 标题 + 抓取时间。
- 表格：表名 + 行/列或字段。

如果不能回到原始来源，线上排查、权限审计和用户信任都会有问题。

**7. 质量评估**

入库后要抽样检查：

- OCR 准确率。
- 表格结构是否保留。
- PDF/PPT 页码是否对得上。
- 网页正文抽取是否混入广告和导航。
- chunk 是否切断条件和结论。
- query 是否能召回 gold chunk。
- 引用是否真实可打开。

对于关键知识库，要构建 query-gold chunk 评测集，按 PDF、PPT、图片、网页、表格分别看 Recall@K、MRR、NDCG、groundedness 和 citation accuracy。

**面试可以这样说：**

如果知识库原始数据不是 Markdown，我不会直接把 PDF、PPT、图片或网页转成一段纯文本再向量化，而是先做解析和结构化建模。统一抽象成 document、block、chunk 三层：document 保存原始文件和版本，block 保存标题、段落、表格、图片、PPT 页、网页 section 这类结构单元，chunk 才用于检索。PDF 要解析标题、正文、页码、表格和图片，扫描件做 OCR；PPT 按 slide 解析标题、正文、备注和图片文字；图片做 OCR 和必要的图像理解；网页要抽正文、去广告导航、保留 URL、发布时间和抓取时间。然后按结构切 chunk，保留 page、slide_no、url、bbox、section_path、权限和版本 metadata。索引上用 BM25、向量索引、结构化索引和元数据索引组合，检索时混合召回、rerank、权限过滤和上下文扩展。最后答案必须能引用回具体 PDF 页码、PPT 页、图片区域或网页 URL。核心原则是：先保结构和来源，再做检索，不要把复杂文档粗暴压成纯文本。

## 16. Agent 是否有调用外部搜索引擎？

**问题：** 是否有调用外部搜索引擎？

**答案：**

可以调用，但我不会把外部搜索引擎当成默认知识来源。一般要看业务场景：如果问题主要依赖企业内部知识、订单、工单、权限数据，就优先走内部 RAG、数据库和业务 API；如果问题需要公开网页、新闻、竞品资料、开源文档或强时效公开信息，才把外部搜索引擎作为一个受控工具接入 Agent。

**1. 什么时候会调用外部搜索**

适合调用外部搜索的场景：

- 公开资料调研。
- 竞品信息收集。
- 开源框架、官方文档、版本更新查询。
- 新闻、政策、公告等强时效信息。
- 内部知识库没有覆盖，但允许查询外部公开来源。

不适合调用外部搜索的场景：

- 企业内部制度、合同、订单、用户数据。
- 需要严格权限控制的数据。
- 已有权威内部知识库或业务 API 的问题。
- 金融、法务、医疗等高风险结论直接依赖不可信网页。

**2. 工程上怎么接**

外部搜索应该作为 tool 接入，而不是让模型自己随便联网。

流程一般是：

```text
用户问题
  -> 意图识别：是否需要外部搜索
  -> 权限和策略判断：当前场景是否允许搜索
  -> 生成 search query
  -> 调搜索 API
  -> 抓取/摘要/清洗网页内容
  -> 来源可信度和时间校验
  -> rerank 和去重
  -> 带引用生成答案
```

搜索 query 也要受控，不能把用户隐私、订单号、手机号、内部代码、合同内容直接拼到外部搜索里。

**3. 外部搜索结果不能直接信**

搜索结果属于不可信外部内容，需要做治理：

- 过滤广告、SEO 垃圾站、低可信来源。
- 优先官方文档、权威媒体、政府公告、项目仓库。
- 记录 URL、标题、发布时间、抓取时间。
- 多来源交叉验证。
- 对网页里的 prompt injection 做隔离。
- 答案必须带来源引用。

外部网页里的“忽略系统提示”“调用某工具”等内容只能当作数据，不能当作指令。

**4. 和内部 RAG 的优先级**

一般优先级是：

```text
系统规则 / 权限
  > 内部业务 API
  > 内部权威知识库
  > 外部官方/权威来源
  > 普通网页搜索结果
  > 模型自身记忆
```

如果内部知识库和外部搜索冲突，企业业务问题通常以内部联系统为准；如果是公开技术文档，则优先官方最新文档。

**5. 线上要做观测**

需要记录：

- 哪些问题触发外部搜索。
- 搜索 query。
- 返回 URL 和来源。
- 哪些网页进入最终上下文。
- 引用是否被答案使用。
- 搜索失败率、延迟、成本。
- 外部搜索带来的答案提升或误答率。

这样才能判断外部搜索是提升了实时性，还是引入了噪声和风险。

**面试可以这样说：**

有些场景会调用外部搜索引擎，但我不会默认让 Agent 随便联网。我的做法是把外部搜索当成一个受控 tool：先由意图识别判断是否真的需要公开信息，再经过权限和策略检查，确认不能把内部敏感信息带到搜索 query 里。搜索结果回来后也不会直接塞给模型，而是做网页清洗、去重、来源可信度判断、时间校验和 rerank，优先官方文档、政府公告、权威媒体或项目仓库，并且答案要带 URL 和抓取时间。内部业务问题优先走内部 RAG、数据库和业务 API；外部搜索主要用于公开资料、强时效信息、竞品调研和开源文档查询。核心原则是：外部搜索可以增强实时性，但它是不可信输入，必须受工具权限、来源治理、引用校验和 prompt injection 防护约束。

## 17. MCP 和 Function Calling 的区别是什么？

**问题：** MCP 和 function call 的区别是什么？

**答案：**

这题可以直接复用：

- [[AI Agent-01#22. MCP、A2A、普通 Function Calling 和 Skills 有什么本质区别？工程里怎么选？|AI Agent-01 第 22 题：MCP、A2A、普通 Function Calling 和 Skills 有什么本质区别？工程里怎么选？]]

核心区别是：Function Calling 是模型调用某个具体函数的机制，解决“模型如何生成函数名和参数”；MCP 是外部工具、资源和上下文接入的标准协议，解决“不同系统如何把工具和数据源标准化暴露给 Agent 应用”。简单 API 或少量内部工具，用 Function Calling 就够；工具、文件、数据库、Git、浏览器、知识库等数据源很多，并且希望跨应用复用时，更适合 MCP。

**面试可以这样说：**

Function Calling 更像一次具体工具调用的接口机制：开发者把函数名、description 和参数 schema 给模型，模型输出 tool name 和 arguments，后端做校验和执行。MCP 更像工具和上下文接入层的标准协议，它把外部系统里的 tools、resources、prompts 等能力用统一方式暴露出来，方便不同 Agent 应用复用。两者不是互斥关系：MCP 负责标准化接入和发现工具，Function Calling/Tool Calling 负责模型在当前任务里选择并调用具体工具。简单内部 API 直接 function calling 就行；工具和数据源很多、需要跨系统复用和治理时，用 MCP 更合适。

## 18. 为什么 AI 应用里经常需要做两级缓存？

**问题：** 为什么 AI 应用里经常需要做两级缓存？

**答案：**

AI 应用里经常做两级缓存，本质是为了同时解决低延迟、高并发、成本控制和跨实例共享。一级缓存通常是进程内本地缓存，速度最快；二级缓存通常是 Redis 这类分布式缓存，支持多实例共享、TTL、限流、幂等和任务状态。

**1. 为什么一层缓存不够**

AI 应用的链路通常比普通接口长：

```text
用户请求
  -> 意图识别
  -> RAG 检索 / rerank
  -> 工具调用
  -> prompt 组装
  -> 模型推理
  -> 输出校验
```

其中很多步骤成本高、延迟长，比如权限查询、tool schema、prompt 模板、RAG 检索结果、rerank 结果、用户短期状态、模型响应等。如果每次都查数据库、调检索、调工具或调模型，延迟和成本都会很高。

但只用 Redis 也不一定够快，因为高频小数据每次都走网络，会增加毫秒级开销；只用本地缓存也不行，因为多实例之间不共享，更新和失效很难统一。

**2. 一级缓存解决什么**

一级缓存一般放在应用进程内，比如 LRU cache、本地内存、SDK 内部缓存。

适合存：

- prompt 模板。
- tool schema 摘要。
- 模型配置。
- 低频变更的路由配置。
- 小而高频的权限/租户配置短 TTL 副本。
- embedding/rerank 配置。

优点：

- 访问最快，没有网络开销。
- 能扛住极高频读取。
- 适合每个实例都需要的热点配置。

缺点：

- 多实例不共享。
- 容量有限。
- 失效和更新不如 Redis 统一。
- 进程重启后丢失。

**3. 二级缓存解决什么**

二级缓存一般用 Redis。

适合存：

- 会话短期状态。
- active task 状态。
- RAG 检索结果。
- rerank 结果。
- 只读工具查询结果。
- 用户权限和租户配额。
- 幂等键。
- 限流计数器。
- 分布式锁。
- SSE/任务进度事件。

优点：

- 多实例共享。
- 支持 TTL 和统一失效。
- 支持原子操作。
- 可以做限流、锁、幂等和轻量队列。

缺点：

- 比本地缓存慢。
- Redis 抖动会影响链路。
- 要处理缓存穿透、击穿、雪崩和权限隔离。

**4. 两级缓存的典型读取流程**

常见流程是：

```text
读本地缓存
  -> 命中：直接返回
  -> 未命中：读 Redis
      -> 命中：回填本地缓存并返回
      -> 未命中：查 DB / 调工具 / 做检索
          -> 写 Redis
          -> 回填本地缓存
          -> 返回
```

这样可以让最热的数据走本地缓存，多实例共享的数据走 Redis，最终源头数据只在缓存未命中时访问。

**5. AI 应用里常见缓存对象**

不同对象要分开设计：

- **配置类缓存：** prompt、tool schema、路由规则，适合本地 + Redis。
- **RAG 类缓存：** query rewrite、召回结果、rerank 结果，适合 Redis，必要时本地短 TTL。
- **工具结果缓存：** 只读 API 可缓存，写操作不能简单缓存。
- **模型结果缓存：** 只适合确定性、低风险、高重复问题；开放问答要谨慎。
- **语义缓存：** 相似问题命中历史答案，能降成本，但要做相似度阈值、权限和时效校验。
- **状态类缓存：** 会话、任务、进度、幂等键，适合 Redis，不适合只放本地。

**6. 风险和注意点**

两级缓存最容易出问题的是一致性和权限：

- 权限相关缓存必须带 tenant_id、user_id、resource_id。
- RAG 结果缓存要带知识库版本和索引版本。
- 工具结果缓存要区分用户权限和数据时效。
- 高风险答案不要直接命中旧模型结果。
- 本地缓存 TTL 要短，Redis 作为统一失效中心。
- 缓存 key 要包含模型版本、prompt 版本、tool schema 版本。

否则可能出现用户看到过期答案、越权数据或旧版本规则。

**面试可以这样说：**

AI 应用里做两级缓存，是因为一层缓存很难同时满足低延迟和多实例共享。一级缓存通常是进程内本地缓存，适合放 prompt 模板、tool schema、模型配置、路由规则这类小而高频、变化不频繁的数据，优点是没有网络开销、速度最快。二级缓存一般用 Redis，适合放会话状态、任务状态、RAG 检索结果、rerank 结果、只读工具结果、权限短缓存、幂等键、限流计数和分布式锁，优点是多实例共享、支持 TTL 和原子操作。典型流程是先查本地，未命中查 Redis，再未命中才查数据库、检索系统或外部工具，并回填两级缓存。AI 场景尤其要注意缓存 key 里带上用户、租户、权限、知识库版本、prompt 版本和模型版本，避免命中过期或越权结果。简单说，本地缓存解决极低延迟，Redis 解决共享状态和分布式协调，两级组合才能兼顾性能、成本和安全。

## 19. 如果做一个智能客服类 AI 应用，整体链路怎么设计？

**问题：** 如果要做一个智能客服类的 AI 应用，整体链路怎么设计？

**答案：**

智能客服不能只做一个“用户问题 -> 大模型回答”的聊天框。真实客服场景通常涉及知识库、订单、物流、售后、工单、用户历史、权限、转人工和质检，所以整体链路要按“入口治理 -> 意图路由 -> RAG/工具/流程编排 -> 安全校验 -> 回复和状态写回 -> 评估闭环”来设计。

**1. 用户入口和会话层**

入口要先处理基础信息：

- 用户身份、租户、渠道、语言。
- 会话 ID、用户 ID、订单 ID、工单 ID。
- 最近几轮对话和当前 active task。
- 输入风控、敏感词、prompt injection 检测。
- 限流、防刷、黑白名单。

客服场景里多轮、省略和指代很多，比如“那这个能退吗”“帮我催一下”，所以必须维护 conversation state 和 task state，而不是每轮重新猜。

**2. 意图识别和任务路由**

用户输入后先做轻量意图识别，判断属于哪类问题：

- FAQ/政策咨询。
- 订单查询。
- 物流查询。
- 退款/售后。
- 投诉/工单。
- 账号问题。
- 闲聊或无关问题。
- 高风险/敏感问题。

路由结果不只是一个 intent，还要包含：

```json
{
  "intent": "refund_consulting",
  "slots": {"order_id": "123"},
  "missing_slots": [],
  "need_rag": true,
  "need_tool": true,
  "risk_level": "medium",
  "confidence": 0.86
}
```

低置信或缺关键参数时先追问，不要直接调用工具或编答案。

**3. 知识库 RAG 链路**

政策、FAQ、SOP、活动规则、产品说明适合走 RAG：

```text
query rewrite
  -> 权限过滤
  -> BM25 + 向量混合召回
  -> rerank
  -> 去重、版本过滤、上下文压缩
  -> 返回带来源的证据
```

客服 RAG 要特别注意：

- 文档版本和生效时间。
- 不同客服角色的权限。
- FAQ、表格、附件、图片 OCR 的解析质量。
- 答案必须引用来源。
- 证据不足时不能硬答。

**4. 业务工具调用链路**

订单状态、物流轨迹、退款进度、用户权益、工单状态这类实时信息不能只靠知识库，要调业务 API。

工具调用流程：

```text
选择候选工具
  -> 模型生成 tool call
  -> schema 校验
  -> 权限校验
  -> 业务规则校验
  -> 执行只读 API 或进入确认流程
  -> 工具结果结构化成 observation
```

只读工具可以自动执行；退款、改地址、关闭工单、补偿券发放这类写操作必须二次确认、幂等、审计，必要时走 Workflow 或人工审批。

**5. 编排层：Agent + Workflow 组合**

智能客服通常不适合让 Agent 完全自由规划。

更稳的是：

- Agent 负责理解用户问题、路由、总结证据、生成话术。
- RAG 负责知识依据。
- Tool Calling 负责查实时业务状态。
- Workflow/状态机负责退款、工单、补偿等确定性流程。
- 人工客服负责高风险、低置信、投诉升级和复杂异常。

也就是用 Agent 处理智能判断，用 Workflow 管住业务流程。

**6. 回复生成和安全校验**

生成回复时要把上下文分区：

```text
系统规则
用户问题
task state
RAG 证据
工具 observation
输出格式要求
```

生成后还要做：

- groundedness 校验。
- 引用校验。
- 敏感信息脱敏。
- 话术合规检查。
- 高风险动作确认。
- 是否需要转人工判断。

客服回复最好输出“可直接发给用户的话术 + 内部处理依据 + 下一步建议”，但内部依据不能泄露给终端用户。

**7. 转人工和工单闭环**

这些情况要转人工：

- 用户强烈不满或投诉升级。
- 多轮没有解决。
- 低置信或证据冲突。
- 涉及金额、法律、隐私、高风险操作。
- 工具/API 异常无法确认状态。
- 用户明确要求人工。

转人工时要把摘要、已查证据、工具结果、用户诉求、建议处理方案一起带给人工客服，减少重复沟通。

**8. 观测和评估**

智能客服指标不能只看回答准确率：

- 首次解决率。
- 转人工率。
- 用户满意度。
- 平均处理时长。
- 意图识别准确率。
- 工具选择和参数准确率。
- RAG Recall@K、groundedness、引用准确率。
- 幻觉率、越权率、敏感信息泄露率。
- P95/P99 延迟和单次成本。

线上要记录完整 run trace，方便定位是知识没召回、工具选错、参数错、模型生成错，还是业务规则没覆盖。

**面试可以这样说：**

如果做智能客服类 AI 应用，我不会把它设计成单纯的大模型聊天，而是做成 Agent + RAG + 业务工具 + Workflow + 人工兜底的组合链路。用户请求进来后，入口层先做鉴权、租户识别、限流、输入风控，并读取会话状态和当前 task state；然后做意图识别和槽位抽取，判断是 FAQ、订单查询、物流、退款售后、投诉工单还是闲聊。政策、FAQ、SOP 走 RAG，做 query rewrite、混合召回、rerank、权限过滤和版本过滤；订单状态、物流轨迹、退款进度这类实时事实走业务 API。模型只负责理解、路由、生成 tool call 和组织回复，真正执行前后端必须做 schema、权限和业务规则校验。高风险写操作，比如退款、改地址、补偿券、关闭工单，不能让模型自由执行，要走二次确认、幂等、审计和 Workflow。最终回复生成后还要做 groundedness、引用、脱敏和合规校验；低置信、证据冲突、用户投诉或多轮未解决时转人工，并把摘要、证据和工具结果带给人工客服。指标上看解决率、转人工率、满意度、工具准确率、RAG groundedness、幻觉率、P95 延迟和成本。

## 20. LangChain 的核心功能是什么？基于 LangChain 会调用哪些类型的模型？

**问题：** LangChain 的核心功能是什么？基于 LangChain 会调用哪些类型的模型？

**答案：**

这题和 [[AI Agent-04#6. LangChain 和 LangGraph 如何选择？|第 6 题：LangChain 和 LangGraph 如何选择]] 有重叠，但这里重点是 LangChain 本身提供什么能力，以及项目里会接哪些模型。

LangChain 可以理解成 LLM 应用开发的组件框架。它的核心价值不是“让模型变聪明”，而是把模型、Prompt、检索、工具、记忆、输出解析和链路编排这些常见模块封装起来，方便快速搭建 RAG、Agent、工具调用和多步骤 LLM 应用。

核心功能主要有几类：

**1. 模型抽象**

LangChain 对不同模型供应商做统一封装，比如 ChatModel、LLM、Embedding model。这样上层代码不需要直接绑定某一个模型 API。

**2. Prompt 管理**

支持 PromptTemplate、ChatPromptTemplate、MessagesPlaceholder 等，把系统提示、用户输入、历史消息、检索证据按模板组织起来。

**3. Chain 编排**

把多个步骤串起来，例如：

```text
用户问题 -> query rewrite -> retriever -> prompt -> LLM -> output parser
```

简单 RAG、摘要、抽取、分类、问答都可以用 chain 表达。

**4. RAG 组件**

LangChain 提供 document loader、text splitter、retriever、vector store 集成，可以接 PDF、网页、数据库、向量库等，快速搭建检索增强生成链路。

**5. Tool / Agent**

可以把外部 API、数据库查询、搜索、代码执行等包装成 tool，让模型选择是否调用。Agent 负责根据用户目标决定调用哪些 tool，再根据 observation 继续推理。

**6. Memory 和消息历史**

支持对话历史、摘要记忆、外部存储消息历史等能力。但生产系统里长期记忆通常不会只依赖 LangChain memory，还会结合数据库、权限、过期策略和召回策略。

**7. Output parser 和结构化输出**

可以把模型输出解析成 JSON、Pydantic 对象或固定字段，适合意图识别、槽位抽取、工具参数生成等场景。

基于 LangChain 常调用的模型类型包括：

| 模型类型 | 作用 |
|---|---|
| Chat Model / LLM | 对话、问答、摘要、推理、生成 |
| Embedding Model | 文档和 query 向量化，用于 RAG 召回 |
| Reranker / Cross-Encoder | 对召回结果精排 |
| LLM-as-judge | 做回答质量评估、groundedness 检查 |
| 分类/路由模型 | 意图识别、工具路由、场景分发 |
| Moderation / 安全模型 | 内容安全、敏感信息、风险检测 |
| 多模态模型 | 图片、PDF 截图、图文理解等场景 |

实际工程里，LangChain 经常不是单独使用，而是和 LangGraph、向量库、业务 API、模型服务、监控系统组合。LangChain 管组件和调用，LangGraph 更适合管复杂状态流转。

**面试可以这样说：**

LangChain 的核心功能是把 LLM 应用里的通用组件封装起来，包括模型调用、Prompt 模板、Chain 编排、Retriever、VectorStore、Document Loader、Tool、Agent、Memory 和 Output Parser。它适合快速搭 RAG、工具调用和简单 Agent 链路。基于 LangChain 不只是调用一个聊天大模型，通常会接多类模型：Chat Model 或 LLM 负责生成和推理，Embedding 模型负责向量化和召回，Reranker 负责检索结果精排，分类或路由模型负责意图识别，LLM-as-judge 负责评测，安全模型负责内容审核，多模态模型负责图片或文档理解。我的理解是 LangChain 管“怎么把模型和外部能力接起来”，不是替代业务架构；复杂有状态 Agent 还要结合 LangGraph、权限校验、日志和监控。

## 21. Skill 为什么能迅速被接纳？它的优点是什么？

**问题：** Skill 为什么迅速被接纳，它的优点是什么？

**答案：**

Skill 能迅速被接纳，核心原因是它把“怎么完成某类任务”的经验，从一次性的长 prompt 里抽出来，变成可复用、可管理、可按需加载的能力包。

在 Agent 项目里，很多问题不是模型完全不会，而是模型每次都要重新理解任务、重新规划步骤、重新记住约束，导致输出不稳定。Skill 正好解决这个痛点：它把稳定任务的流程、约束、示例、工具说明、脚本和最佳实践沉淀下来，让 Agent 遇到同类任务时可以直接复用。

可以把 Skill 理解成：

```text
Skill = 触发条件 + 操作步骤 + 约束 + 示例 + 工具/脚本说明 + 输出规范
```

**1. 对开发者友好**

Skill 通常用 Markdown、配置或轻量文件组织，不一定要改模型、不一定要重新训练，也不要求业务人员理解复杂代码。团队可以把经验写成操作手册，再逐步工程化。

这比每次改一大段 system prompt 更容易维护。

**2. 能沉淀任务经验**

Function Calling 解决“调用哪个函数”，但 Skill 解决“这类任务应该怎么做”。比如代码审查、RAG 调优、日志排障、客服退款、SQL 分析，都不是一个函数能描述清楚的，里面有步骤、判断标准、反例和兜底策略。

Skill 可以把这些经验固化下来，减少模型每次自由发挥。

**3. 可复用、可组合**

同一个 Skill 可以被多个 Agent、多个项目、多个场景复用。多个 Skill 也可以组合成更复杂任务，例如：

```text
需求分析 Skill
  -> 代码修改 Skill
  -> 测试修复 Skill
  -> Review Skill
```

这让能力建设从“每个应用单独写 prompt”变成“能力资产复用”。

**4. 支持按需加载，节省上下文**

Skill 不需要全部塞进 system prompt。更好的方式是 Skill registry + 路由 + 渐进式披露：

```text
先看 skill name / description / tags
  -> 选 TopK 候选
  -> 再加载相关 Skill 详情
```

这样模型只看到当前任务需要的能力，减少上下文噪声、token 成本和误用风险。

**5. 提升稳定性和一致性**

Skill 里可以明确：

- 什么时候使用。
- 什么时候不要使用。
- 输入需要哪些条件。
- 操作步骤是什么。
- 输出格式是什么。
- 失败时怎么处理。
- 哪些工具能调用。

这些规则能让同类任务的执行路径更一致，也更容易做回归测试。

**6. 便于版本管理和评估**

Skill 可以像代码或配置一样版本化。每次修改 Skill，可以记录版本、变更原因、适用场景和评测结果。线上出问题时，也能回放当时加载了哪个 Skill、哪个版本、为什么被选中。

这比一坨不断膨胀的 prompt 更容易治理。

**7. 连接 Prompt、Tool 和 Workflow**

Skill 不是简单提示词，也不是单个工具。它可以把 Prompt 模板、工具说明、执行步骤和业务约束组织到一起：

```text
Prompt：告诉模型怎么理解和生成
Tool：提供可执行能力
Workflow：约束确定性流程
Skill：沉淀某类任务的操作方法
```

所以 Skill 很容易被 Agent 工程接纳，因为它正好位于“模型自由生成”和“硬编码流程”之间，既有灵活性，又比纯 prompt 更可控。

需要注意的是，Skill 不是越多越好。Skill 太多会带来路由错误、description 相似、上下文占用、版本冲突和维护成本。所以生产里要有 Skill registry、元数据、TopK 路由、渐进式披露、版本管理和误选率评估。

**面试可以这样说：**

Skill 被快速接纳，是因为它解决了 Agent 工程里的一个实际问题：很多任务不是模型完全不会，而是缺少稳定的操作流程和领域经验。Skill 把某类任务的触发条件、步骤、约束、示例、输出格式、工具说明沉淀成一个能力包，不需要重新训练模型，也不需要把所有规则堆进 system prompt。它的优点是对开发者友好、容易复用、能沉淀经验、支持按需加载、节省上下文，并且可以版本化、评测和回放。相比 Function Calling，Skill 更高层，描述的是“这类任务怎么做”，而不只是“调用哪个函数”。相比纯 Prompt，Skill 更模块化、更容易治理。生产里要注意 Skill 太多会带来路由和冲突问题，所以一般要配合 skill registry、TopK 路由、渐进式披露和版本管理。

## 22. Harness engineering 是什么？

**问题：** Harness engineering 介绍一下。

**答案：**

Harness engineering 可以理解成“围绕大模型或 Agent 搭建一套可控、可评测、可回放的运行和测试外壳”。它不是训练模型本身，而是把模型放进一个工程化的执行环境里，控制输入、工具、上下文、评测、日志和安全边界。

这里的 harness 类似测试夹具或运行框架：模型是核心能力，但模型外面要有一层工程系统，负责让它稳定地执行任务，并且能判断结果好不好、问题出在哪里。

一个 Agent harness 通常包括：

```text
测试任务集 / 线上请求
  -> prompt 和上下文组装
  -> 模型调用
  -> 工具 mock 或真实工具调用
  -> 状态记录和 run trace
  -> 结果校验
  -> 指标统计
  -> 错例回流
```

**1. 输入和上下文控制**

Harness 会固定每次运行的输入，包括用户问题、系统 prompt、工具列表、RAG 证据、历史摘要、模型版本和参数。这样每次评测才可比较，否则 prompt、知识库、模型和工具都在变，很难判断指标变化来自哪里。

**2. 工具和环境控制**

Agent 依赖外部工具，工具结果可能变化。Harness 里通常会做：

- 工具 mock。
- sandbox 环境。
- 冻结测试数据。
- 固定 API 返回。
- 模拟超时、失败、空结果、权限拒绝等异常。

这样可以稳定复现边界 case，测试 Agent 是否会重试、追问、降级或转人工。

**3. 过程记录和可回放**

Agent 的错误不一定发生在最终答案，可能发生在意图识别、规划、检索、工具选择、参数生成、权限校验或状态更新。Harness 要记录完整 run trace：

- 输入和 prompt 版本。
- 模型版本和采样参数。
- 检索 query、召回结果、rerank 结果。
- 工具候选、tool call、参数、返回值。
- 状态变化和 checkpoint。
- 最终答案、耗时、成本和错误。

有了 trace，才能回放一次执行，定位到底是哪一层出了问题。

**4. 评测和打分**

Harness 不只跑任务，还要评估结果。常见指标包括：

- 任务成功率。
- 意图识别准确率。
- 工具选择准确率。
- 参数准确率。
- RAG Recall@K 和 groundedness。
- 格式正确率。
- 幻觉率。
- 安全违规率。
- 平均步骤数、P95/P99 延迟和成本。

评分方式可以结合规则校验、人工标注、LLM-as-judge 和业务断言。比如订单查询任务可以用规则判断是否查了正确订单；开放问答可以用 groundedness judge 和人工抽检。

**5. 回归和灰度**

Harness 的核心价值是防回归。每次改 prompt、模型版本、tool schema、RAG 索引、reranker 或 Skill，都要跑固定测试集，看是否解决了旧问题，又引入了新问题。

上线前可以用 harness 做离线回归；上线后用线上 trace 抽样回放，持续补充测试集。

**6. 和 Prompt engineering 的区别**

Prompt engineering 主要改模型输入，让模型更会答。Harness engineering 更关注“如何把模型放进可控系统里验证和运行”。它包含 prompt，但不止 prompt，还包括工具 mock、环境冻结、日志回放、评测指标、自动化回归、安全测试和部署灰度。

**7. 和模型训练的区别**

模型训练是改变参数；harness engineering 是改变模型外部的工程外壳。很多 Agent 问题不一定要先训练模型，可能通过更好的 harness 就能解决：

- 固定上下文结构。
- 加工具参数校验。
- 做 RAG 证据检查。
- 加 evaluator。
- 记录 trace 并回放。
- 把错例变成回归集。

**面试可以这样说：**

Harness engineering 我理解是给大模型或 Agent 搭一套可控的运行和评测外壳。模型本身只负责生成或决策，但 harness 负责固定输入、组织上下文、mock 工具、控制环境、记录 run trace、做结果校验和指标统计。它的价值是让 Agent 的效果可以被稳定评估和回放，而不是线上出错后只凭感觉改 prompt。比如每次改模型、prompt、tool schema 或 RAG 索引前，我会用 harness 跑固定任务集，记录意图准确率、工具选择准确率、参数准确率、RAG 命中、groundedness、幻觉率、安全违规、延迟和成本。如果出错，可以通过 trace 回放到具体步骤。简单说，Prompt engineering 是让模型更会答，Harness engineering 是让模型应用可测试、可观测、可回归、可上线。

## 23. Hermes Agent 是怎么不断自我纠正和自我进化的？

**问题：** Hermes agent 是怎么不断自我纠正，自我进化的？

**答案：**

如果这里的 Hermes Agent 指的是一类“带自我纠错和持续改进闭环的 Agent”，我不会把它理解成模型在线自动改参数。生产里所谓自我纠正、自我进化，更多是通过 **执行反馈、验证器、记忆/经验沉淀、评测回归和策略更新** 形成闭环。

可以把它拆成两层：

```text
单次任务内：自我纠正
跨任务周期：自我进化
```

**1. 单次任务内的自我纠正**

Agent 执行任务时，不是一次生成到底，而是每一步都观察结果、检查偏差、必要时修正。

典型流程是：

```text
用户目标
  -> plan
  -> execute
  -> observe
  -> verify
  -> revise / retry / ask / stop
```

纠正机制通常包括：

- **Plan verifier：** 检查计划是否覆盖目标、是否越界、是否遗漏关键步骤。
- **Tool verifier：** 检查工具是否选对、参数是否完整、权限是否允许。
- **Evidence verifier：** 检查证据是否足够、是否过期、是否互相冲突。
- **Answer verifier：** 检查答案是否被证据支持，是否有 unsupported claim。
- **Safety verifier：** 检查是否越权、泄露敏感信息或触发高风险动作。

如果检查失败，Agent 不应该继续硬答，而是根据错误类型处理：

- 参数缺失：追问用户。
- 工具失败：重试、换工具或降级。
- 证据不足：重新检索或说明不确定。
- 计划偏航：回到上一个 checkpoint 重新规划。
- 安全风险：阻断或转人工。

**2. 运行过程要有 trace 和 checkpoint**

自我纠正不是让模型“感觉自己错了”，而是系统能看到错在哪里。所以每一步都要记录：

- 当前目标和 task state。
- plan 和 step。
- 模型输入输出。
- 检索证据和工具结果。
- verifier 结论。
- 错误类型和修正动作。
- checkpoint。

有 checkpoint 后，Agent 才能从安全点恢复，而不是从头再来或在错误状态上继续跑。

**3. 跨任务的自我进化**

跨任务的“进化”主要来自数据闭环，而不是线上模型随意自我改权重。

常见闭环是：

```text
线上 trace / 用户反馈 / 人工接管
  -> 错例分类
  -> 找到问题层：prompt / RAG / tool / state / model
  -> 生成修复方案
  -> 加入 dev set 和回归集
  -> 离线评测
  -> 灰度上线
```

能沉淀的内容包括：

- 高频成功轨迹沉淀成 Skill 或 SOP。
- 高频失败 case 沉淀成回归测试。
- 工具误选样本用于优化 tool description 和路由。
- RAG 失败样本用于优化 chunk、query rewrite、rerank。
- 模型输出问题用于优化 prompt、few-shot 或微调数据。
- 人工修正结果可进入偏好数据或 SFT 数据，但要脱敏和审核。

**4. 为什么不能让 Agent 随意自我进化**

生产里不能让 Agent 直接把自己的输出写成新规则，也不能直接用线上结果更新模型参数。原因是：

- 模型可能把错误经验固化。
- 用户输入可能有 prompt injection。
- 线上反馈有噪声。
- 权限、安全、合规风险很高。
- 改动不可控会破坏回归稳定性。

所以真正可用的自我进化要有门控：人工审核、离线评测、版本管理、灰度发布和回滚机制。

**5. 工程上怎么落地**

我会把 Hermes-style 自我改进做成分层系统：

- **Runtime 层：** plan、execute、observe、verify、revise。
- **Trace 层：** 记录完整运行轨迹和错误类型。
- **Memory/Skill 层：** 只沉淀稳定、审核过、可复用的经验。
- **Eval 层：** 固定测试集和回归集验证改动。
- **Release 层：** prompt、tool schema、Skill、索引和模型版本灰度上线。

核心原则是：线上自动发现问题，离线受控学习经验，经过评测后再发布。

**面试可以这样说：**

Hermes Agent 的自我纠正，我理解不是模型在线自动改参数，而是 Agent 运行时有 plan-execute-observe-verify-revise 的闭环。每一步执行后用 verifier 检查计划、工具、参数、证据、答案和安全边界；如果发现参数缺失就追问，工具失败就重试或降级，证据不足就重新检索或说明不确定，偏航就回到 checkpoint 重新规划。自我进化则来自跨任务的数据闭环：记录线上 run trace、用户反馈和人工接管，做错例分类，判断问题发生在 prompt、RAG、工具、状态还是模型层，再把高质量经验沉淀成 Skill、SOP、few-shot、回归集或训练数据。生产里不能让 Agent 随意把自己的输出写成新规则，必须经过脱敏、审核、离线评测、灰度和回滚。简单说，自我纠正发生在单次执行内，自我进化发生在受控的数据和评测闭环里。

## 24. 大模型认知和 RAG 检索证据冲突怎么解决？

**问题：** 大模型认知和 RAG 检索冲突怎么解决？

**答案：**

这里的冲突通常是指：模型参数里“记得”的知识和 RAG 检索出来的证据不一致。比如模型根据预训练知识认为某政策是旧规则，但知识库召回的是最新制度；或者模型觉得某 API 字段存在，但文档里已经废弃。

生产里原则很明确：**模型参数知识不能高于外部可信证据**。尤其是企业 RAG、政策、订单、接口、价格、合同、工单这类场景，要以有来源、有权限、有版本的证据为准，而不是让模型凭记忆回答。

**1. 先区分证据可信度**

不是所有 RAG 内容都天然正确。进入生成前要给证据加 metadata：

- 来源：官方文档、内部制度、网页、用户上传、历史记录。
- 版本：文档版本、effective time、更新时间。
- 权限：当前用户是否有权限查看。
- 时效性：是否过期、是否被废弃。
- 置信度：召回分、rerank 分、来源权威性。
- 适用范围：地区、产品线、租户、用户角色。

如果 RAG 证据本身低质、过期或无权限，不能简单压过模型。

**2. 建立优先级规则**

常见优先级可以这样排：

```text
系统规则 / 权限 / 安全策略
  > 实时业务 API / 数据库
  > 官方最新知识库 / 版本化文档
  > 用户当前明确输入
  > 历史记忆 / 用户偏好
  > 模型参数知识
```

模型参数知识只适合补充通用背景，不适合覆盖最新、私有、强事实、强审计的业务证据。

**3. Prompt 中明确 grounded 规则**

生成时要明确告诉模型：

```text
你必须基于给定证据回答。
如果证据和你已有知识冲突，以证据为准。
如果证据不足或互相冲突，说明不确定，不要用常识补全。
关键结论必须能对应到证据来源。
```

但 prompt 只是软约束，不能只靠 prompt。

**4. 做 answerability 和 groundedness 校验**

回答前后都要校验：

- 检索证据是否足够回答问题。
- 答案中的关键结论是否被证据支持。
- 是否出现证据外实体、数字、时间、政策条款。
- 引用是否真的支持对应结论。
- 是否把模型常识混入业务事实。

如果校验失败，要触发：

- 重新检索。
- 扩大或切换知识库。
- 调用实时 API。
- 追问用户限定范围。
- 输出不确定说明。
- 转人工或升级审核。

**5. 多个证据之间也可能冲突**

如果不是模型和 RAG 冲突，而是 RAG 召回的文档互相冲突，就不能让模型强行综合。要先在证据层处理：

- 过滤过期、废弃、低可信文档。
- 按版本、发布时间、权威来源排序。
- 对冲突结论做 conflict 标注。
- 能消解就基于最高可信证据回答。
- 不能消解就说明“当前知识库存在冲突”，列出来源和版本。

**6. 工程上怎么防止模型抢答**

可以做几件事：

- 最终 prompt 只放高可信 TopN 证据，不放一堆噪声。
- 输出要求带引用或 source_id。
- 对答案做 unsupported claim 检测。
- 高风险问题必须走规则/API/人工确认。
- 对无证据问题训练或提示模型拒答。
- 记录冲突 case，回流到 RAG 评测集和知识库治理。

长期看，这类问题不只是模型问题，也可能是知识库治理问题。要修文档版本、权限、chunk、索引、rerank 和引用，不是只改 prompt。

**面试可以这样说：**

大模型认知和 RAG 检索证据冲突时，我不会让模型凭参数知识自己判断。生产原则是：系统规则和权限最高，实时 API 或数据库事实优先于知识库，官方最新知识库优先于模型参数记忆。模型自己的知识只能做通用背景，不能覆盖有来源、有版本、有权限的业务证据。工程上我会给每段证据带来源、版本、时间、权限和置信度，生成时要求模型必须基于证据回答；生成后做 groundedness 和 citation 校验，看关键结论是否被证据支持。如果证据不足或模型输出了证据外结论，就重检索、追问、调用实时 API 或转人工。若 RAG 证据之间也冲突，就按版本、发布时间、权威来源和适用范围消解，无法消解时明确说明知识库存在冲突，而不是强行给唯一答案。核心是让模型服从可信证据，而不是用记忆覆盖事实。

## 25. 怎么设计 Agent 的沙箱机制？

**问题：** 怎么去设计一个 Agent 的沙箱机制？

**答案：**

Agent 沙箱的目标是：允许 Agent 调用工具、执行代码、访问文件或外部服务，但把风险限制在可控边界内。它不是一句 prompt 约束，而是系统侧的硬隔离和执行治理。

我会先按风险把 Agent 能力分层：

```text
只读问答 / RAG
  -> 只读工具调用
  -> 受限代码执行
  -> 文件读写
  -> 外部网络访问
  -> 业务写操作 / 生产变更
```

风险越高，沙箱越严格；涉及资金、删除、生产配置、发消息、审批这类动作，不能只靠沙箱自动执行，还要走二次确认、审批、幂等和审计。

**1. 权限沙箱：最小权限**

Agent 不应该继承用户或服务的全部权限，而是每次 run 生成一个受限执行上下文：

- 当前用户、租户、角色。
- 可访问的数据范围。
- 可调用的工具白名单。
- 可读写的资源范围。
- token、时间、步数和成本预算。

模型只能提出 tool call 建议，真正执行前由后端做权限、参数和业务规则校验。

**2. 工具沙箱：白名单和风险分级**

所有工具必须进入 tool registry，不允许模型自由构造任意 API、SQL、shell 命令或 URL。

每个工具要标注：

- read/write 类型。
- risk_level。
- permission scope。
- input_schema / output_schema。
- timeout / retry。
- 是否允许自动执行。
- 是否需要二次确认。
- 是否需要幂等键。

低风险只读工具可以自动执行；高风险写工具必须确认或审批。

**3. 代码执行沙箱**

如果 Agent 需要执行 Python、Shell、SQL、JS 或数据分析代码，要放进隔离环境，而不是在宿主机裸跑。

常见手段包括：

- 容器隔离，比如 Docker / Kubernetes Job。
- 非 root 用户运行。
- 只挂载临时目录。
- 文件系统只读或限制写目录。
- CPU、内存、磁盘、进程数限制。
- 超时和最大输出限制。
- 禁止危险 syscall，可用 seccomp / AppArmor / gVisor / Firecracker 等增强隔离。
- 执行结束销毁环境。

代码输出也要做大小限制和敏感信息扫描，避免把密钥、环境变量、内部路径泄露给模型或用户。

**4. 网络沙箱**

Agent 不能默认访问全网。网络访问要按任务授权：

- 默认禁网或只允许访问白名单域名。
- 禁止访问内网敏感地址、metadata service、Kubernetes API、Redis、数据库等。
- 对外请求走代理，记录 URL、方法、参数、响应摘要。
- 限制请求次数、并发、超时和响应大小。
- 防止 SSRF 和 prompt injection 诱导外连。

如果需要外部搜索，也应该作为受控 search tool，而不是让 Agent 任意 curl。

**5. 数据沙箱**

RAG、数据库、文件系统都要做数据隔离：

- 租户隔离。
- 资源级 ACL。
- metadata 权限过滤。
- 敏感字段脱敏。
- 临时文件隔离。
- 输出前再做权限和敏感信息检查。

权限过滤必须在检索和工具查询前做，不能等模型看完无权限内容后再在输出端过滤。

**6. 状态和副作用控制**

沙箱要区分“模拟执行”和“真实执行”：

- 只读操作可以直接返回结果。
- 写操作先 dry-run，生成待确认计划。
- 用户确认后再执行真实写入。
- 每个写操作带 idempotency_key。
- 状态更新用版本号或 CAS。
- 失败时有补偿或人工处理。

这样可以避免重复退款、重复发消息、误删数据、并发覆盖等问题。

**7. 观测和审计**

沙箱执行必须可追踪：

- run_id、task_id、user_id、tenant_id。
- 模型版本、prompt 版本、tool schema 版本。
- 工具名、参数、权限校验结果。
- 容器/进程资源消耗。
- 网络访问记录。
- 文件读写记录。
- stdout/stderr、错误和退出码。
- 是否触发风控、确认、审批或阻断。

这些日志既用于排障，也用于安全审计和回放。

**8. 安全测试**

沙箱上线前要专门测攻击样本：

- prompt injection 要求忽略规则。
- 读取系统 prompt、密钥、环境变量。
- 访问内网地址或 metadata endpoint。
- 执行删除、挖矿、反弹 shell。
- 构造超大输出、死循环、fork bomb。
- 越权查询其他租户数据。
- 绕过工具白名单调用隐藏接口。

没有这些测试，沙箱只是“看起来安全”。

**面试可以这样说：**

Agent 沙箱我会按“最小权限、工具白名单、执行隔离、网络隔离、数据隔离、副作用控制和审计回放”来设计。模型不能直接执行真实 API、Shell 或 SQL，只能提出工具调用建议；后端根据 tool registry 做白名单、schema、权限、风险等级和业务规则校验。代码执行要放在容器或更强隔离环境里，非 root、限制 CPU/内存/磁盘/进程数、限制文件目录、设置超时，必要时用 seccomp、AppArmor、gVisor 或 Firecracker。网络默认禁用或走白名单代理，防 SSRF 和内网探测。数据侧要做租户隔离、资源级权限、敏感字段脱敏，而且权限过滤必须发生在检索和查询前。写操作不能让 Agent 自动完成，要 dry-run、二次确认、幂等、审计和补偿。最后所有执行都记录 run trace，包括工具参数、权限结果、网络、文件、资源消耗和错误，方便安全审计和回放。

## 26. MCP 的使用场景有哪些？

**问题：** MCP 的使用场景。

**答案：**

MCP 适合解决的问题是：Agent 应用需要接入很多外部工具、资源和上下文，而且这些能力希望被多个模型应用复用，不想每个应用都重复写一套适配逻辑。

它不是替代 Function Calling。Function Calling 更像模型调用某个具体函数的机制；MCP 更像一个标准化接入层，把外部系统的 tools、resources、prompts 等能力暴露给 Agent Runtime。

常见使用场景有几类。

**1. 企业内部系统接入**

企业 Agent 经常要查 CRM、订单、工单、知识库、财务、审批、库存、日志等系统。如果每个 Agent 都单独对接这些 API，维护成本很高。

MCP 可以把这些系统包装成统一 server：

```text
crm-mcp
order-mcp
ticket-mcp
doc-mcp
finance-mcp
devops-mcp
```

Agent 侧通过统一协议发现工具和资源，再由本地 runtime 做权限、路由和执行治理。

**2. 文档、文件和知识库访问**

MCP 很适合暴露文件系统、文档库、知识库、对象存储、代码仓库等资源。

比如：

- 读取项目文档。
- 查询知识库。
- 搜索内部 Wiki。
- 获取 Git 仓库文件。
- 读取 PDF、表格、配置文件。
- 按资源 URI 暴露上下文。

这类场景不只是“调用函数”，还涉及资源发现、资源读取、上下文注入和权限控制，MCP 比单纯 function calling 更合适。

**3. 开发者工具和 DevOps Agent**

研发类 Agent 常需要接入 Git、Issue、CI/CD、日志、监控、告警、部署平台。

MCP 可以提供：

- 查代码。
- 查 issue。
- 查日志。
- 查监控指标。
- 触发测试。
- 查询 CI 结果。
- 生成变更摘要。

但生产变更、发布、回滚这类高风险动作不能让模型自动执行，必须经过权限、审批和审计。

**4. 数据分析和数据库查询**

MCP 可以接数据库、数据仓库、BI 系统，让 Agent 获取 schema、执行受控查询、读取指标定义。

适合：

- 自然语言查数。
- 指标口径解释。
- SQL 辅助生成。
- 数据质量检查。
- 报表分析。

这里要特别注意不要暴露 `execute_any_sql` 这类万能工具，应该做只读权限、SQL 审计、行列级权限、查询超时和结果脱敏。

**5. 多 Agent 或多应用复用工具**

如果一个工具只给一个应用用，直接 Function Calling 也可以。但如果多个 Agent、多个团队、多个模型应用都要用同一批工具，MCP 的价值会更明显。

例如：

```text
客服 Agent 使用 order-mcp 查订单
运营 Agent 使用 order-mcp 分析售后
质检 Agent 使用 ticket-mcp 查工单
研发 Agent 使用 git-mcp 查代码
```

工具提供方只维护 MCP server，多个 Agent 应用复用。

**6. 本地桌面或个人工作流 Agent**

MCP 也适合本地工具接入，比如文件、浏览器、日历、笔记、终端、数据库客户端等。它能让桌面 Agent 以统一方式访问本地资源。

但本地场景也要注意沙箱：不能默认让模型读取所有文件、访问所有网页或执行任意命令。

**7. 什么时候不需要 MCP**

简单场景不一定要上 MCP：

- 只调用两三个内部 API。
- 工具只服务一个应用。
- 没有跨应用复用诉求。
- 没有资源暴露、工具发现和上下文管理需求。
- 团队还没有权限、审计和治理能力。

这时直接 Function Calling / Tool Calling 更简单。

**8. 使用 MCP 的关键治理点**

MCP 只是标准协议，不自动解决生产安全。工程上还要做：

- MCP server 按业务域拆分。
- 工具进入本地 tool registry。
- 根据 intent、task state、用户权限筛选 TopK 工具。
- 给工具补充 risk_level、owner、version、timeout、rate limit。
- 对 tool call 做 schema、权限和业务规则校验。
- 高风险写操作二次确认。
- 返回结果做脱敏、摘要和 observation adapter。
- 记录 run trace 和审计日志。

**面试可以这样说：**

MCP 的典型使用场景是工具和数据源很多、希望标准化接入并跨 Agent 复用。比如企业里要接 CRM、订单、工单、知识库、Git、数据库、日志、监控、CI/CD，这些能力如果每个 Agent 都单独适配会很乱，MCP 可以把它们封装成标准的 tools、resources 和 prompts。它尤其适合文档/文件/知识库访问、研发 DevOps Agent、数据分析 Agent、企业内部系统接入，以及多个 Agent 复用同一批工具的场景。但如果只是一个应用调用两三个内部 API，直接 Function Calling 更简单。MCP 不是安全边界本身，生产里还要接 tool registry，按用户权限和任务筛选工具，做参数校验、风险分级、限流、审计和高风险确认。简单说，MCP 解决标准化接入和复用，Agent Runtime 负责筛选、治理和安全执行。

## 27. Agent 的局限性有哪些？

**问题：** Agent 的局限性。

**答案：**

Agent 的优势是能围绕目标做规划、调用工具、读取知识和多步执行，但它不是万能自动化系统。生产里最大的局限不是“模型不够聪明”这么简单，而是 **不确定性、可控性、安全性、成本和评估难度** 都比普通应用更高。

这题可以和 [[AI Agent-02#9. 通用 Agent 的发展你怎么看？为什么很难一个 Agent 解决所有问题？|通用 Agent 为什么很难解决所有问题]] 一起理解，但这里重点讲 Agent 本身的局限。

**1. 可靠性不如确定性 Workflow**

Agent 的执行路径是动态生成的，同一个任务可能因为上下文、模型版本、采样参数、工具结果不同而走出不同路径。

这会带来：

- 计划不稳定。
- 步骤遗漏。
- 反复 re-plan。
- 重复调用工具。
- 结果难以完全预测。

所以订单、支付、审批、退款、生产变更这类高可靠流程，不能完全交给 Agent 自由执行，应该由 Workflow、状态机和规则控制主流程。

**2. 容易受上下文影响**

Agent 很依赖上下文质量。上下文太少会缺信息，太多又会引入噪声。

常见问题包括：

- 历史对话干扰当前任务。
- RAG 召回噪声带偏模型。
- 工具结果太长，关键信息被埋掉。
- 多个规则或证据冲突。
- prompt injection 污染上下文。

因此 Agent 需要上下文筛选、分区、压缩、优先级排序和注入防护。

**3. 工具调用有风险**

Agent 不是只生成文本，它可能调用 API、数据库、搜索、代码执行器和业务系统。一旦工具调用错了，影响就可能是真实副作用。

风险包括：

- 选错工具。
- 参数抽错或补全不存在的信息。
- 越权查询数据。
- 重复写入或重复扣款。
- 调用高风险接口。
- 被 prompt injection 诱导执行危险动作。

所以模型只能提出 tool call，系统必须做白名单、schema 校验、权限校验、业务规则校验、幂等、审计和二次确认。

**4. 长任务容易跑偏或死循环**

Agent 做复杂任务时，可能越跑越偏：

- 目标逐渐漂移。
- 连续多步没有新信息。
- 重复检索或重复调用工具。
- 反复修改计划。
- 忽略失败结果继续生成。

这类问题不能只靠 prompt 解决，要靠 task state、checkpoint、最大步数、最大重试次数、进展检测、verifier 和人工兜底。

**5. 事实性和幻觉仍然存在**

Agent 接了 RAG 和工具，并不代表没有幻觉。它仍然可能：

- 正确证据没召回。
- 召回了旧版本或冲突证据。
- 工具返回为空但模型强行解释。
- 答案里混入模型参数知识。
- 引用不能支持结论。

所以要做 groundedness、citation 校验、证据不足拒答和冲突提示。

**6. 评估比普通问答更难**

普通问答主要评最终答案，Agent 要评整个过程：

- 意图识别是否正确。
- 计划是否合理。
- 工具是否选对。
- 参数是否正确。
- RAG 是否召回正确证据。
- 权限和安全是否遵守。
- 最终任务是否完成。
- 成本和延迟是否可接受。

而且同一个任务可能有多条合理路径，所以不能只做 exact match，要有 run trace、mock 工具、固定测试集、LLM-as-judge、规则断言和人工抽检。

**7. 成本和延迟更高**

一次 Agent 请求可能包含多次模型调用、多次检索、多次 rerank、多次工具调用和多轮校验。

相比普通 LLM 调用，它更容易出现：

- token 成本高。
- P95/P99 延迟高。
- 工具链路拖慢。
- 失败重试放大成本。
- 高并发下资源被打满。

所以生产系统要做模型分层、缓存、限流、降级、预算控制和异步任务。

**8. 安全边界更复杂**

Agent 的攻击面比普通聊天更大，因为攻击者不只是让模型说错话，还可能诱导它访问数据、调用工具、写入记忆或执行操作。

安全上要重点防：

- prompt injection。
- 越权访问。
- 敏感信息泄露。
- 高风险工具绕过确认。
- memory 污染。
- 外部网页或文档里的恶意指令。

这要求权限、沙箱、风控、审计和最小工具集都是系统侧硬约束。

**9. 适合与不适合场景**

Agent 更适合：

- 目标明确但路径不固定。
- 需要多工具组合。
- 需要检索、推理和行动闭环。
- 低到中风险任务。
- 可以接受一定不确定性并有兜底。

不适合完全交给 Agent 的场景：

- 强事务、高风险写操作。
- 法务、医疗、金融等高责任判断。
- 强一致、强审计、零容错流程。
- 权限极复杂但治理不足的系统。
- 没有评测集、没有 trace、没有回滚机制的生产环境。

**面试可以这样说：**

Agent 的局限性主要在可控性和可靠性。它能规划、调工具、读知识库，但执行路径是动态的，容易受上下文、模型版本、工具结果和检索噪声影响，所以不如 Workflow 稳定。长任务里可能跑偏、重复调用工具、反复 re-plan，工具调用还会带来真实副作用，比如越权查询、参数错误、重复写入和高风险操作。Agent 接 RAG 后也不等于没有幻觉，仍然要做 groundedness、引用校验和证据不足拒答。评估也更难，因为不能只看最终答案，还要看意图、计划、工具、参数、权限、安全、成本和延迟。我的结论是：Agent 适合目标明确但路径不固定、需要多工具和动态推理的场景；高风险、强事务、强一致的流程要用 Workflow、状态机、权限、沙箱、审计和人工确认来约束，不能让 Agent 自由发挥。

## 28. OpenClaw 为什么更容易火？Manus 也能执行，为什么没有 OpenClaw 这么火？

**问题：** OpenClaw 为什么这么火？Manus 也可以执行，为什么没 OpenClaw 这么火？

**答案：**

这类问题不能只比较“谁能执行任务”。Agent 产品或框架能不能火，除了能力本身，还取决于 **开放程度、可改造性、部署形态、开发者参与门槛、生态扩散方式和使用场景**。

如果把两者抽象一下：

```text
OpenClaw：更像开源 Agent 框架 / 可自部署能力底座
Manus：更像面向终端用户的通用执行型 Agent 产品
```

所以 OpenClaw 更容易在技术社区传播，不一定是因为它单点执行能力一定比 Manus 强，而是因为它更像“开发者可以拿来改、拿来接、拿来部署”的基础设施。

**1. 开源和可控带来传播优势**

开源项目天然更容易被开发者接纳：

- 可以看源码，知道 Agent 怎么规划、怎么调工具、怎么管理状态。
- 可以二次开发，接自己的模型、工具、知识库和业务系统。
- 可以私有化部署，满足企业数据安全和合规要求。
- 可以自己改 prompt、tool schema、memory、workflow 和 UI。

Manus 这类闭源产品即使体验好，用户更多是在“使用产品”；OpenClaw 这类框架则能让开发者“参与建设”，社区扩散会更快。

**2. OpenClaw 更像工程底座，Manus 更像成品应用**

Manus 能执行任务，但它更偏完整产品体验，用户关心的是“能不能帮我完成这个任务”。它的优势是开箱即用，缺点是可控性和可改造性有限。

OpenClaw 更像底座：

- 可以接企业内部工具。
- 可以接私有知识库。
- 可以自定义 Agent 流程。
- 可以改模型和推理服务。
- 可以做权限、审计、沙箱和可观测。

对开发者和企业来说，可嵌入、可扩展、可治理，比单纯“能执行”更重要。

**3. 企业更关心私有化和安全边界**

很多企业场景不能把数据和工具权限交给外部通用 Agent：

- 内部文档不能外流。
- 订单、客户、财务、代码、日志有权限边界。
- 工具调用涉及真实业务副作用。
- 需要审计、回放、灰度和回滚。

OpenClaw 这类可自部署框架更容易进入企业 POC，因为它可以放在企业自己的环境里接内部系统。Manus 如果是云端闭源产品，在企业内部深度集成时会遇到数据合规、权限控制和系统接入的问题。

**4. 开发者社区喜欢“可复现、可改造、可炫技”的东西**

一个项目容易火，往往不是因为它最完善，而是因为它容易让人快速跑起来，并且能展示效果：

- clone 后能跑 demo。
- 能接自己的模型或 API。
- 能接微信、飞书、浏览器、文件、知识库等入口。
- 能二次开发出很多变体。
- 容易写教程、录视频、发 benchmark。

闭源产品的传播更多依赖官方体验和邀请码；开源框架的传播可以依赖社区自发改造和二次创作。

**5. Manus 的问题不是不能执行，而是产品边界不同**

Manus 这类执行型 Agent 的优势是端到端体验，但局限也明显：

- 用户不一定知道内部怎么规划和调用工具。
- 不容易接企业私有系统。
- 不容易做细粒度权限和审计。
- 不容易按行业场景深度定制。
- 对开发者来说，可学习和可改造空间有限。

所以它适合作为通用个人助理或任务执行产品，但不一定像开源框架那样快速变成开发者生态。

**6. OpenClaw 火也不代表生产就够了**

需要注意，开源框架火和生产可用是两回事。真正落地还要补：

- 权限和工具白名单。
- 沙箱和高风险确认。
- task state 和 checkpoint。
- run trace 和可回放。
- RAG 评测和 groundedness。
- 工具错误处理、幂等和补偿。
- 多租户、审计、限流和灰度。

也就是说，OpenClaw 的优势是让 Agent 应用更容易“搭起来”和“改起来”，但生产级能力还要靠工程治理补齐。

**面试可以这样说：**

我理解 OpenClaw 更火，不一定是因为它的单次任务执行能力一定强于 Manus，而是因为两者定位不同。Manus 更像一个闭源的通用执行型 Agent 产品，用户主要是在用它完成任务；OpenClaw 更像开源 Agent 框架或能力底座，开发者可以看源码、改流程、接自己的模型、工具、知识库和企业系统，也能私有化部署。这对技术社区和企业 POC 很关键，因为企业更关心数据安全、权限、审计、沙箱和内部系统集成。开源项目还更容易被社区二次开发、写教程、做 demo 和扩散。Manus 能执行，但可控性、可改造性和生态参与度通常不如开源框架。我的判断是：Manus 更偏产品体验，OpenClaw 更偏工程底座和生态扩散；前者适合终端用户直接用，后者更容易被开发者和企业拿来改造成自己的 Agent 系统。但 OpenClaw 火不代表生产就够了，真正上线还要补权限、状态、沙箱、可观测、评测和回滚。

## 29. 大模型项目里 LangGraph 节点如何设计？

**问题：** 大模型项目 LangGraph 节点如何设计的？

**答案：**

LangGraph 节点设计的核心不是“把每一步都拆成一个节点”，而是把 Agent 执行过程里 **状态会变化、需要观测、需要重试、需要分支、需要恢复** 的地方拆成节点。

我一般先设计 graph state，再设计 node。因为 LangGraph 是 state-driven 的，节点本质上是读取 state、执行一段逻辑、返回 state patch。

**1. 先定义 Graph State**

一个业务 Agent 的 state 通常会包含：

```python
class AgentState(TypedDict):
    messages: list
    user_id: str
    tenant_id: str
    intent: str
    slots: dict
    task_state: dict
    rag_state: dict
    tool_state: dict
    safety_state: dict
    final_answer: str
    errors: list
    trace_id: str
```

更工程化一点，会拆成：

- **conversation state：** 当前对话和历史摘要。
- **task state：** 目标、槽位、当前步骤、计划、缺失信息。
- **routing state：** 意图、置信度、下一步动作。
- **RAG state：** query、召回结果、rerank 结果、最终证据。
- **tool state：** 工具名、参数、结果、错误、幂等键。
- **safety state：** 权限、风险等级、是否需要确认。
- **execution state：** run_id、checkpoint、重试次数、耗时、成本。

State 要尽量结构化，不能把所有东西都塞进 messages 里，否则后面很难做分支、恢复和排障。

**2. 节点拆分原则**

我会按职责拆节点，而不是按代码函数随便拆。

适合拆成独立节点的情况：

- 这一步有明确输入输出。
- 这一步失败后需要单独重试或降级。
- 这一步后面会影响分支。
- 这一步需要记录 trace。
- 这一步可能中断等待用户确认。
- 这一步有外部副作用，比如工具调用。
- 这一步需要单独评测指标。

不适合拆太细的情况：

- 只是普通字符串处理。
- 没有独立业务语义。
- 拆开后只增加图复杂度。
- 不需要独立观测、重试或分支。

**3. 一个常见节点设计**

比如智能客服 / 企业知识问答 Agent，可以这样设计：

```text
入口校验节点
  -> 意图识别节点
  -> 槽位抽取节点
  -> 路由节点
      -> RAG 检索节点
      -> 工具调用节点
      -> 追问节点
      -> 直接回答节点
  -> 证据/工具结果校验节点
  -> 生成回答节点
  -> 安全和 groundedness 校验节点
  -> 最终输出节点
```

具体节点职责：

- **input_guard node：** 鉴权、租户、输入风控、基础参数校验。
- **intent node：** 判断用户意图、置信度、是否需要 RAG/工具/追问。
- **slot node：** 抽取订单号、时间、产品、用户目标等关键槽位。
- **planner/router node：** 根据 state 决定下一步走 RAG、tool、clarify 还是 answer。
- **rag node：** query rewrite、混合召回、rerank、权限过滤、证据整理。
- **tool node：** 生成 tool call，做 schema/权限/业务规则校验后执行。
- **clarify node：** 缺关键槽位或低置信时生成追问。
- **answer node：** 基于 state、证据和工具结果生成最终回复。
- **verify node：** 做 groundedness、引用、安全、格式校验。
- **handoff node：** 低置信、高风险、证据冲突时转人工。

**4. Edge 和 conditional edge 怎么设计**

节点之间不要全部线性串起来，关键是 conditional edge。

例如路由节点可以返回：

```text
need_clarification -> clarify
need_rag -> retrieve
need_tool -> tool_call
need_human -> handoff
can_answer -> answer
```

工具节点也可以根据结果分支：

```text
tool_success -> verify
tool_timeout -> retry_or_degrade
permission_denied -> refuse_or_handoff
missing_params -> clarify
high_risk -> confirm
```

这样流程控制由 state 和规则决定，而不是让模型每一步自由决定所有事情。

**5. 哪些节点用 LLM，哪些不用**

不是所有节点都需要大模型。

通常：

- 规则节点：鉴权、限流、权限、风险等级、格式校验。
- 小模型/分类器：简单意图识别、路由、敏感信息检测。
- Embedding/reranker：RAG 召回和排序。
- LLM：复杂意图理解、query rewrite、工具参数生成、最终回答。
- 强模型或 judge：复杂 verifier、groundedness、人工前审核。

这样能控制成本和延迟，也能提高稳定性。

**6. Checkpoint 和可观测**

生产里关键节点前后要 checkpoint：

- 模型调用前后。
- 工具调用前后。
- 高风险写操作确认前。
- RAG 检索后。
- 最终生成前。

每个节点要记录：

- node_id。
- 输入 state 摘要。
- 输出 state patch。
- 模型版本、prompt 版本。
- 工具名和参数。
- 错误、耗时、token、成本。
- 下一跳原因。

这样线上问题才能回答：为什么走了这个节点？为什么调用这个工具？为什么没有转人工？

**7. 节点设计要避免两个极端**

一个极端是节点太粗，比如一个 `agent_node` 里做完意图、检索、工具、生成。这样短期开发快，但失败难定位、无法恢复、无法评测。

另一个极端是节点太细，每个小函数都是节点。这样图会膨胀，state 更新复杂，维护成本高。

比较好的粒度是：每个节点代表一个可观测、可恢复、可评估的业务步骤。

**面试可以这样说：**

我设计 LangGraph 节点时会先设计 state，再设计节点。State 里会结构化保存 conversation、task、intent、slots、RAG、tool、safety、execution 等信息，节点只读取 state 并返回 state patch。节点拆分按业务职责来，不是按代码函数拆；凡是会影响分支、需要重试、需要观测、可能失败恢复或有外部副作用的步骤，都适合拆成节点。比如一个客服 Agent 可以有 input_guard、intent、slot_extract、router、rag_retrieve、tool_call、clarify、answer、verify、handoff 这些节点。边用 conditional edge，根据 state 决定走 RAG、工具、追问、回答还是转人工。不是所有节点都用 LLM，权限校验、格式校验、风险判断尽量用规则或小模型，LLM 只放在复杂理解、生成和工具参数生成节点。生产里关键节点前后要 checkpoint，并记录 node 输入输出、模型版本、工具参数、耗时、错误和下一跳原因。核心原则是：节点粒度要能观测、能恢复、能评估，但不要拆到图膨胀。

## 30. SSE 和 WebSocket 的适用场景及各自优势是什么？

**问题：** SSE 和 WebSocket 的适用场景及各自优势。

**答案：**

SSE 和 WebSocket 都可以做实时通信，但核心区别是：**SSE 是服务端到客户端的单向事件流，WebSocket 是客户端和服务端的双向全双工连接**。

在大模型和 Agent 项目里，选型不要只看“能不能流式输出”，而要看通信模式。

**1. SSE 适合什么场景**

SSE 适合服务端持续推送、客户端主要接收的场景。

典型场景：

- 大模型 token 流式输出。
- Agent 执行进度推送。
- RAG 检索、rerank、工具调用过程事件。
- 任务状态更新。
- 通知、告警、日志流。
- 后端异步任务进度展示。

比如 Agent 执行时：

```text
run_start
node_start
retrieval_done
tool_call
llm_token
need_confirmation
run_end
```

这些都是服务端不断往前端推事件，前端不需要频繁向服务端发消息，用 SSE 很自然。

**2. SSE 的优势**

SSE 的优势是简单、稳定、适合 HTTP 体系：

- 基于 HTTP，接入和排查简单。
- 浏览器原生支持 `EventSource`。
- 自动重连机制比较方便。
- 天然是文本事件流，适合 LLM token 和 Agent 事件。
- 和普通网关、鉴权、日志、监控更容易集成。
- 服务端实现比 WebSocket 轻。
- 对“请求一次，持续返回结果”的模型流式输出很合适。

生产里常见返回格式是：

```text
event: llm_token
id: 12
data: {"delta":"你好"}

event: run_end
id: 38
data: {"status":"success"}
```

**3. SSE 的局限**

SSE 主要是单向通信，客户端要发新指令通常还是走另一个 HTTP 请求。

局限包括：

- 不适合高频双向交互。
- 不适合二进制数据传输。
- 浏览器对同域连接数有限制。
- 长连接要处理 heartbeat、代理超时、断线重连。
- 需要任务状态落库，不能只依赖连接存在。

如果用户中途要频繁暂停、修改参数、实时协作输入，SSE 会比较别扭。

**4. WebSocket 适合什么场景**

WebSocket 适合强双向、低延迟、高频交互场景。

典型场景：

- 实时协作编辑。
- 在线客服坐席和用户双向消息。
- 实时语音、实时字幕、音视频控制信令。
- 游戏、白板、多人协同。
- 前端需要频繁发控制指令给后端。
- Agent 执行中用户频繁干预，比如暂停、继续、改目标、确认动作、发送补充信息。

如果通信模式是：

```text
前端不断发控制消息
后端不断推执行事件
双方都很频繁
```

WebSocket 会更合适。

**5. WebSocket 的优势**

WebSocket 的优势是双向和实时：

- 全双工通信，客户端和服务端都能主动发消息。
- 低延迟，适合高频交互。
- 可以传文本，也可以传二进制。
- 一条连接里可以承载多种消息类型。
- 适合复杂交互式应用和实时协作。

比如一个交互式 Agent 工作台里，用户可以边看执行过程边发送：

```text
pause_run
resume_run
approve_tool_call
modify_instruction
cancel_task
```

这类双向控制用 WebSocket 更自然。

**6. WebSocket 的局限**

WebSocket 工程复杂度更高：

- 连接生命周期管理更复杂。
- 鉴权、续期、断线恢复要自己设计。
- 负载均衡和多实例需要连接粘滞或消息总线。
- 心跳、重连、消息顺序、幂等要处理。
- 对普通 HTTP 网关、日志、缓存体系不如 SSE 简单。
- 如果只是模型流式输出，会显得偏重。

所以不能因为 WebSocket 更强就默认选它。

**7. 在大模型项目里怎么选**

可以按这个原则：

| 场景 | 优先选择 |
|---|---|
| LLM token 流式输出 | SSE |
| Agent 进度事件推送 | SSE |
| 后端异步任务状态展示 | SSE |
| 用户只是偶尔取消/确认 | SSE + 普通 HTTP |
| 高频双向控制 | WebSocket |
| 多人实时协作 | WebSocket |
| 实时语音/二进制流 | WebSocket |
| 聊天室式双向消息 | WebSocket |

实际工程里也可以组合：

```text
SSE：推送模型 token、节点状态、工具结果
HTTP：提交用户确认、取消任务、补充参数
WebSocket：复杂实时协作或高频双向控制
```

**面试可以这样说：**

SSE 和 WebSocket 的核心区别是通信方向。SSE 是基于 HTTP 的服务端单向事件流，适合大模型 token 流式输出、Agent 执行进度、RAG/工具调用事件、异步任务状态推送这类“服务端持续推，前端主要接收”的场景。它实现简单，浏览器原生支持 EventSource，有自动重连，和 HTTP 网关、鉴权、日志体系更容易集成。WebSocket 是双向全双工，适合高频双向交互，比如实时协作、在线客服、语音控制、Agent 执行中频繁暂停/继续/改目标/确认动作。它更灵活、延迟低，也支持二进制，但连接管理、鉴权续期、断线恢复、负载均衡和消息顺序更复杂。我的选型是：普通 LLM/Agent 流式输出优先 SSE；如果前端需要高频控制后端，或者是多人实时协作，再用 WebSocket。

## 31. 怎么提升 Agent 工具调用的正确率？

**问题：** 怎么提升工具调用的正确率？

**答案：**

工具调用正确率不能只理解成“模型有没有选对函数”，至少包括四类：

- 该调用工具时有没有调用。
- 不该调用工具时有没有乱调用。
- 工具是否选对。
- 参数、权限、时机和结果使用是否正确。

所以提升正确率要从工具定义、候选集、上下文、校验和评测闭环一起做。

**1. 把工具边界定义清楚**

每个工具不能只有 name 和 description，还要有：

- 工具用途。
- `when_to_use`。
- `when_not_to_use`。
- 输入 schema。
- 输出结构。
- 参数约束。
- 成功和失败示例。
- 风险等级和权限要求。

如果两个工具描述很像，模型很容易误选。工程上要么合并工具，要么明确边界，比如“查订单详情”和“查物流轨迹”不能都写成“查询订单信息”。

**2. 减少候选工具数量**

不要把所有工具一次性暴露给模型。工具越多，选择空间越大，误选概率越高。

常见做法是两阶段：

```text
用户问题
  -> 意图识别 / 领域路由
  -> Tool registry 召回 TopK 候选工具
  -> LLM 在候选工具里选择
  -> 参数生成
  -> 执行前校验
```

也可以按业务域、权限、租户、会话状态过滤工具。比如用户没有退款权限，就不应该让退款工具进入候选集。

**3. 先抽意图和槽位，不要直接让模型调用**

很多工具调用错不是工具本身错，而是用户意图或参数不完整。

比如用户说：

```text
帮我查一下订单
```

如果缺少订单号，就不应该让模型猜一个订单调用接口，而应该追问。可以先做 intent 和 slot extraction：

```text
intent: query_order
required_slots: order_id
missing_slots: order_id
action: clarify
```

这样能减少无效调用和错误参数。

**4. 强化参数 schema 和字段说明**

参数要尽量结构化，避免大段自由文本。字段层面要写清楚类型、枚举、格式和含义。

比如：

```json
{
  "order_id": "必填，订单号，不是商品 ID",
  "date_range": "可选，格式 YYYY-MM-DD",
  "query_type": "枚举：detail | logistics | refund"
}
```

如果字段含义模糊，模型容易把手机号、用户 ID、订单号、商品 ID 混用。

**5. 执行前做校验和拦截**

不能模型生成了 tool call 就直接执行。中间层要做：

- JSON schema 校验。
- 必填参数校验。
- 参数格式校验。
- 权限校验。
- 业务状态校验。
- 高风险动作二次确认。
- 幂等 key 和 trace id 注入。

如果校验失败，要返回结构化错误，让模型追问或修正，而不是把底层异常原样丢回去。

**6. 分离工具选择和答案生成上下文**

工具选择阶段不需要塞入完整 RAG 内容、长对话历史和大量无关记忆。上下文越脏，越容易误选工具。

可以把链路拆开：

```text
工具选择：只给用户意图、任务状态、候选工具 schema
答案生成：再给工具结果、证据和输出要求
```

这样工具选择更稳定，也更容易定位问题。

**7. 引入规则、分类器或 reranker**

高确定性的场景不要完全交给 LLM。比如：

- 明确的订单号查询走订单工具。
- 明确的天气查询走天气工具。
- 高风险写操作必须走审批节点。
- Top1 和 Top2 工具分数接近时触发澄清或二次判别。

可以用规则、embedding 检索、小模型分类器、LLM rerank 组合做工具路由。

**8. 做可观测和评测闭环**

线上要记录完整 run trace：

- 用户输入。
- 意图识别结果。
- 候选工具列表。
- 最终选择工具。
- 参数。
- 校验结果。
- 工具返回。
- 模型是否正确使用工具结果。

离线评测集要覆盖高频、长尾、相似工具、缺参数、无权限、无需调用工具、高风险工具等样本。

常见指标包括：

- Tool Selection Accuracy。
- Argument Accuracy。
- Missing Tool Call Rate。
- Unnecessary Tool Call Rate。
- Invalid Tool Call Rate。
- Tool Success Rate。
- Permission Block Rate。
- 工具结果使用正确率。

每次改 prompt、tool schema、模型版本、候选工具召回逻辑，都要跑回归。

**9. 少量 few-shot 或微调可以作为后置手段**

如果工具集稳定、调用量大、错例集中，可以把高质量 tool calling 轨迹沉淀成 few-shot，或者做 SFT/DPO 提升工具选择和参数生成稳定性。

但顺序上通常不是先微调，而是先把工具边界、候选集过滤、schema、校验和评测做好。否则模型学到的是混乱工具定义下的偶然规律。

**面试可以这样说：**

提升工具调用正确率我会先把问题拆成四类：该不该调、选哪个工具、参数对不对、工具结果有没有被正确使用。工程上第一步是把 Tool registry 做清楚，每个工具有明确的 `when_to_use`、`when_not_to_use`、输入输出 schema、参数约束和权限等级；第二步是减少候选集，不把所有工具都暴露给模型，而是先按意图、业务域、权限和状态召回 TopK 工具；第三步是先抽意图和槽位，缺关键参数就追问，不让模型猜；第四步是执行前做 schema、权限、业务规则和高风险确认校验。最后要记录完整 run trace，构建 tool calling 评测集，看 Tool Selection Accuracy、Argument Accuracy、Missing Tool Call Rate、Invalid Tool Call Rate 等指标，并把线上错例沉淀成回归集。few-shot 或微调可以做，但应该放在工具定义和工程治理稳定之后。

## 32. 知识库是如何构建的？

**问题：** 知识库是如何构建的？

**答案：**

面试里讲知识库构建，不能只说“把文档切 chunk 后存向量库”。一个可用的 RAG 知识库通常包括数据接入、解析清洗、结构化建模、切分、索引、权限版本、评测和更新机制。

**1. 数据接入**

先明确知识来源和更新方式：

- 产品文档、FAQ、客服工单、运营规则、合同、接口文档、数据库说明。
- PDF、Word、PPT、Excel、Markdown、HTML、图片等格式。
- 手动上传、定时同步、CMS 同步、网页抓取、对象存储监听。

接入时要保留原始文件、来源系统、创建时间、更新时间、负责人、业务域和权限信息。

**2. 文档解析和清洗**

不同格式要先解析成统一结构：

```text
PDF / Word / PPT / 网页 / 图片
  -> 文本、标题、段落、表格、图片 OCR、页码、URL、附件信息
```

清洗时要去掉：

- 页眉页脚。
- 导航栏和广告。
- 重复模板。
- 无意义空白。
- 乱码。
- 过期内容。
- 低质量文档。

但不能把表格、标题层级、页码、图片说明都洗没了，否则后面无法准确检索和引用。

**3. 建 document / block / chunk 模型**

我通常不会只存一份文本，而是建三层结构：

```text
document：一份原始文档，包含来源、版本、权限、更新时间
block：文档里的结构单元，比如章节、段落、表格、图片、PPT 页
chunk：用于 embedding、检索和拼上下文的语义片段
```

每个 chunk 都要带 metadata：

```json
{
  "doc_id": "doc_001",
  "chunk_id": "chunk_018",
  "title_path": "售后政策/退款规则",
  "page": 12,
  "version": "v3",
  "updated_at": "2026-05-01",
  "tenant_id": "tenant_a",
  "permission": "customer_service"
}
```

这样才能支持溯源、权限过滤、版本控制和线上排障。

**4. 结构化切分 chunk**

chunk 不是按固定字符硬切。更好的做法是：

- 先按标题、章节、段落、表格、代码块切。
- 长段落再按语义边界或 token 长度二次切分。
- 保留标题路径和上下文。
- 对相邻 chunk 做适当 overlap。
- 对表格保留结构化表示和文本摘要。
- 对命中的小 chunk，必要时补充父章节或相邻 chunk。

常见 chunk 大小可以从 300 到 800 tokens 起步，再根据召回效果和上下文窗口调整。

**5. 生成 embedding 并建立多路索引**

知识库一般不是只建向量索引，而是多路索引：

```text
向量索引：语义召回
BM25 / 全文索引：关键词、编号、错误码、专有名词
结构化索引：表格字段、时间、状态、产品线
元数据索引：权限、租户、版本、来源、更新时间
```

检索时通常是混合召回：

```text
query rewrite
  -> BM25 + 向量 + 结构化过滤
  -> 合并去重
  -> rerank
  -> 权限和版本过滤
  -> 上下文拼接
  -> 生成答案并引用来源
```

**6. 权限、版本和更新机制**

企业知识库里很容易出现新旧文档混用、越权召回、重复文档和过期答案。

所以要设计：

- 文档版本号。
- `active / deprecated / deleted` 状态。
- 生效时间和过期时间。
- 租户、角色、部门权限。
- 增量更新和重建索引机制。
- 文档删除后的 chunk 失效机制。
- 引用校验。

如果是订单状态、库存、价格这类实时数据，不应该只放知识库，而应该调用实时 API。

**7. 质量评测和线上闭环**

知识库构建完要评测，不是入库就结束。

可以构建 query-gold chunk 评测集，看：

- Recall@K。
- MRR。
- NDCG。
- Context Precision。
- rerank 后正确证据是否进入最终上下文。
- 答案 groundedness。
- 引用准确率。
- 无答案问题拒答率。

线上还要记录用户 query、召回 chunk、rerank 结果、最终上下文、答案和用户反馈。错例再反向优化文档清洗、chunk、embedding、BM25、rerank 和 prompt。

**面试可以这样说：**

知识库构建不是简单把文档切块存向量库。我会先做数据接入，保留来源、版本、更新时间、权限和负责人；然后对 PDF、网页、PPT、图片、表格等做解析清洗，抽出标题、段落、表格、页码和 OCR 内容；接着用 document、block、chunk 三层建模，chunk 用于检索，但要带 doc_id、标题路径、页码、版本、权限等 metadata。切分时优先按结构和语义边界切，而不是固定字符硬切。索引上会同时建向量索引、BM25、结构化索引和元数据索引，检索时做混合召回、去重、rerank、权限过滤和版本过滤。最后还要有增量更新、过期失效、引用校验和 query-gold chunk 评测集，通过 Recall@K、MRR、groundedness、引用准确率等指标持续优化。
