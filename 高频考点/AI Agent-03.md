# AI Agent-03

## 1. Embedding chunk 应该怎么做？为什么固定长度切分经常不够？

**问题：** Embedding chunk 应该怎么做？为什么固定长度切分经常不够？

**答案：**

Embedding chunk 的目标不是把文档机械切短，而是让每个 chunk 保持相对完整的语义，同时适合检索、重排和放进上下文。固定长度切分简单，但经常不够，因为它容易切断标题、段落、表格、步骤、代码块和上下文关系，导致召回到的 chunk 信息不完整。

**怎么做 chunk：**

- 优先按文档结构切：标题、章节、段落、列表、表格、代码块。
- 每个 chunk 带上父级标题、章节路径、doc_id、版本、页码等 metadata。
- 控制 chunk 大小，例如 300 到 800 tokens，根据业务和模型窗口调整。
- 设置适当 overlap，例如 50 到 100 tokens，避免边界信息丢失。
- 对表格、FAQ、代码、日志等特殊内容单独切分，不要全按正文规则处理。
- 对过短 chunk 可以合并，对过长 chunk 再按语义边界拆。

**为什么固定长度切分不够：**

- 会把完整语义切断，比如一个规则的条件和结论分到两个 chunk。
- 会丢失标题上下文，模型不知道这段话属于哪个主题。
- 表格和列表结构会被破坏，行列关系丢失。
- 代码、日志、错误堆栈可能被切断，影响排查。
- 检索命中一个 chunk 时，可能只拿到半句话或半个步骤。
- 后续 rerank 和生成阶段即使命中，也缺少足够证据。

更好的方式是 **结构化切分 + 语义切分 + overlap + metadata 增强**。如果文档结构明显，先按结构切；如果段落太长，再用语义或 token 长度做二次切分；最终检索时可以根据命中的 chunk 扩展相邻 chunk 或父章节。

**面试可以这样说：**

Embedding chunk 不能只按固定长度切，因为 RAG 需要召回的是完整证据，而不是固定字数文本。我会优先按文档结构切，比如标题、章节、段落、表格、代码块，再控制 chunk 大小和 overlap，并给每个 chunk 带上标题路径、doc_id、版本、页码等 metadata。固定长度切分的问题是容易切断语义，比如把规则条件和结论切开，或者破坏表格、列表、代码结构，导致召回结果不完整。更合理的是结构化切分和语义切分结合，必要时命中后再扩展相邻 chunk 或父章节。

## 2. 硬切分在实际场景里有哪些典型弊端？

**问题：** 硬切分在实际场景里有哪些典型弊端？

**答案：**

硬切分一般指按固定字符数或固定 token 数直接切 chunk。它实现简单，但在真实 RAG 场景里经常会破坏语义和结构，导致“召回到了，但证据不完整”。

典型弊端：

- **语义被切断：** 条件在上一个 chunk，结论在下一个 chunk，模型只看到一半。
- **标题丢失：** chunk 里只有正文，没有父级标题，模型不知道这段内容属于哪个主题。
- **列表和步骤断裂：** 操作步骤被切开，导致回答漏步骤或顺序错误。
- **表格结构破坏：** 表头和行内容分离，字段关系丢失。
- **代码和日志被截断：** 函数、堆栈、错误上下文不完整，影响技术排查。
- **召回噪声变多：** chunk 可能混入两个主题，embedding 表示变模糊。
- **Rerank 难度变大：** 单个 chunk 信息不完整，相关性分数不稳定。
- **生成阶段容易幻觉：** 模型拿到半段证据后，会自己补全缺失部分。

更好的做法是按文档结构和语义边界切分，并加上适当 overlap、标题路径和 metadata；命中后必要时扩展相邻 chunk 或父章节。

**面试可以这样说：**

硬切分最大的问题是它只保证长度合适，不保证语义完整。实际场景里它容易把条件和结论切开，把标题和正文切开，把表头和表格行切开，也可能截断代码、日志和操作步骤。结果就是检索看似命中了，但模型拿到的是半段证据，rerank 不稳定，生成阶段还容易补全不存在的信息。所以我一般不会只用固定长度切分，而是按标题、段落、表格、代码块等结构切，再配合 overlap、metadata 和命中后的上下文扩展。

## 3. 在 RAG 里，Hard negative 到底该怎么构造？为什么它比随机负样本更有价值？

**问题：** 在 RAG 里，Hard negative 到底该怎么构造？为什么它比随机负样本更有价值？

**答案：**

Hard negative 是指“看起来很像正确答案、但实际上不支持当前 query 的负样本”。它比随机负样本更有价值，因为随机负样本通常太容易区分，模型学不到细粒度差异；hard negative 能训练或评估模型区分相似但错误的文档。

**怎么构造：**

- 从 BM25 或向量检索 TopK 里取高分但非 gold chunk 的结果。
- 选择同标题、同产品、同模块、同错误码附近但结论不同的文档。
- 选择旧版本文档，作为和新版本相似但过期的负样本。
- 选择同一表格中相邻行、相似字段但条件不同的记录。
- 选择同义词相似但业务范围不同的 chunk。
- 从线上误召回、用户点踩、人工标注错例中沉淀。

示例：

```text
Query：已发货订单能否退款？
Positive：已发货订单需退回商品后可申请退款。
Hard negative：未发货订单可直接申请退款。
Random negative：公司年假制度说明。
```

Random negative 太容易排除，hard negative 才能逼模型学会区分“已发货”和“未发货”。

**为什么更有价值：**

- 更接近线上真实错误。
- 能提升 reranker 或 embedding 的区分能力。
- 能暴露检索系统对相似文档、旧版本、相邻规则的误召回。
- 对评估更严格，避免指标虚高。
- 能减少“看起来相关但实际不支持答案”的上下文噪声。

构造 hard negative 时要注意人工校验，避免把真正相关的 chunk 错标成负样本，否则会污染训练和评测。

**面试可以这样说：**

Hard negative 不是随便找一个不相关文档，而是找“语义很像但不能回答当前问题”的负样本。常见做法是从 BM25 或向量 TopK 里选高分但非 gold 的 chunk，比如同产品、同模块、同标题、同表格相邻行、旧版本规则，或者线上误召回的文档。它比随机负样本更有价值，因为随机负样本太容易区分，模型学不到细粒度边界；hard negative 更接近真实线上错误，能提升 embedding 和 reranker 对相似但错误证据的区分能力，也能让离线评估更真实。

## 4. ReAct 机制在生产环境里怎么设计？为什么不能只靠 prompt 写几句 Thought/Action？

**问题：** ReAct 机制在生产环境里怎么设计？为什么不能只靠 prompt 写几句 thought/action？

**答案：**

ReAct 的核心是让模型在“思考、行动、观察”之间循环，但生产环境不能只靠 prompt 里写几句 Thought/Action。真正可用的 ReAct 要有状态机、工具协议、参数校验、权限控制、步数限制、失败处理、可观测和终止条件。否则模型很容易乱调工具、重复调用、无限循环或执行高风险动作。

**生产设计要点：**

- **显式状态机：** 定义 planning、acting、observing、verifying、done、failed 等状态。
- **结构化工具调用：** Action 不能是自然语言，要是 tool_name + JSON arguments。
- **工具白名单：** 当前场景只暴露允许的工具，不把所有工具都给模型。
- **参数强校验：** schema、权限、业务规则都要校验。
- **Observation 结构化：** 工具返回要有 status、data、error、trace_id。
- **最大步数限制：** 限制 max_steps、max_tool_calls、max_retries，防止死循环。
- **进展检测：** 如果连续几步没有新信息，就停止、追问或 re-plan。
- **高风险确认：** 写操作、删除、退款、发消息必须二次确认。
- **日志和回放：** 记录每一步 thought 摘要、action、observation、状态变更。

生产里的 ReAct 更像：

```text
读取 task state
  -> 模型决定 next_action
  -> 系统校验 action
  -> 执行工具
  -> 写入 observation
  -> 判断是否完成 / 重试 / 追问 / 终止
```

而不是简单把下面这种格式写进 prompt：

```text
Thought:
Action:
Observation:
```

**为什么不能只靠 prompt：**

- prompt 是软约束，模型可能不遵守。
- Thought/Action 文本不可控，难以稳定解析。
- 没有权限和参数校验，会造成误调用。
- 没有状态机和步数限制，容易无限循环。
- 没有工具失败处理，异常时会乱重试。
- 没有日志和 trace，线上问题无法排查。

**面试可以这样说：**

ReAct 在生产里不能只是 prompt 里写 Thought/Action/Observation，而要做成受控执行框架。我会用状态机管理每一步，Action 必须是结构化 tool call，系统侧做工具白名单、参数校验、权限校验和业务规则校验。每次工具返回 Observation 后写入 task state，再判断下一步是继续、追问、重试、完成还是终止。同时要限制最大步数、最大工具调用次数和重试次数，高风险动作二次确认，并记录完整 trace 方便回放。Prompt 只能引导模型思考，真正的可控性必须靠工程约束实现。

## 5. 什么样的项目更适合做模型重训练？什么样的项目更适合做 RAG 或规则增强？

**问题：** 什么样的项目更适合做模型重训练？什么样的项目更适合做 RAG 或规则增强？

**答案：**

模型重训练、RAG 和规则增强解决的问题不同。简单说：如果问题是模型能力或稳定输出风格不足，且有大量高质量标注数据，可以考虑重训练；如果问题是知识更新、事实依据、企业私有知识，优先 RAG；如果问题是权限、流程、格式、业务约束和高风险动作，优先规则或 Workflow。

**适合模型重训练的项目：**

- 有大量稳定、高质量、可标注的数据。
- 任务模式固定，输入输出边界清楚。
- 需要模型学会特定风格、分类边界、领域表达。
- 在线低延迟要求高，不希望每次塞大量 prompt。
- 现有 prompt/RAG 很难稳定解决。

例子：

- 意图分类。
- 文本分类。
- 信息抽取。
- 特定格式生成。
- 领域术语理解。
- 客服话术风格对齐。

但重训练不适合频繁变化的知识，因为每次知识更新都训练成本高。

**适合 RAG 的项目：**

- 需要回答企业私有知识。
- 文档经常更新。
- 答案必须可追溯、可引用。
- 知识量大，不适合塞进 prompt。
- 事实正确性比风格更重要。

例子：

- 企业知识库问答。
- 产品文档问答。
- 政策制度查询。
- 技术文档检索。
- 合同、手册、FAQ 问答。

RAG 的优势是知识可更新、答案可溯源，不需要每次更新知识都训练模型。

**适合规则增强的项目：**

- 业务流程明确。
- 权限边界严格。
- 高风险操作。
- 输出格式必须稳定。
- 有确定性判断条件。

例子：

- 退款是否允许。
- 用户是否有权限。
- 金额是否超限。
- 工单状态流转。
- 删除、支付、发消息、改配置。

这类不能靠模型自由判断，应该用规则、状态机、Workflow 和权限系统控制。

**实际工程通常组合使用：**

```text
模型重训练：提升模型基础能力和稳定风格
RAG：补充动态知识和私有知识
规则/Workflow：保证权限、流程和安全边界
```

比如客服 Agent：

- 用 RAG 查退款政策和产品文档。
- 用规则判断订单状态是否允许退款。
- 用模型生成自然语言回复。
- 如果意图分类样本足够，可以训练轻量分类模型。

**面试可以这样说：**

我不会一上来就选择重训练，而是先判断问题类型。如果问题是知识更新和私有知识，比如企业文档、政策、产品手册，优先用 RAG，因为它可更新、可引用、可追溯。如果问题是权限、流程、金额上限、状态流转这类确定性约束，优先用规则或 Workflow，因为这些不能交给模型自由判断。如果问题是模型对某类任务的表达、分类、抽取长期不稳定，并且有大量高质量标注数据，才考虑模型重训练。实际项目里通常是组合方案：RAG 管知识，规则管边界，模型负责理解和生成。

## 6. 微调数据集一般从哪里来？怎么判断一批数据值不值得训？

**问题：** 微调数据集一般从哪里来？怎么判断一批数据值不值得训？

**答案：**

微调数据集通常来自真实业务数据、人工标注数据、线上错例、专家示范、日志回放和合成数据。但不是有数据就值得训，关键要看这批数据是否高质量、稳定、覆盖真实分布，并且能解决 prompt、RAG、规则难以解决的问题。

**数据来源：**

- 线上真实 query 和用户会话。
- 人工标注的意图、槽位、分类、答案。
- 线上失败 case 和用户点踩样本。
- 专家写的标准答案或操作示范。
- 客服、工单、知识库、历史处理记录。
- 工具调用日志和正确执行轨迹。
- 人工审核后的高质量模型输出。
- 合成数据，但需要人工抽检和过滤。

**判断值不值得训：**

- **任务是否稳定：** 如果业务规则和知识经常变，不适合靠训练记住。
- **数据质量是否高：** 标注一致、答案正确、格式统一、噪声低。
- **覆盖是否足够：** 覆盖高频、长尾、边界 case 和负例。
- **是否有明确评测集：** 训练前要有 dev/test set，否则不知道是否真的提升。
- **是否比 prompt/RAG/规则更合适：** 能用规则解决的不要训练；知识更新型问题优先 RAG。
- **是否有足够规模：** 少量零散样本通常更适合 few-shot 或规则。
- **是否有风险：** 隐私、版权、敏感数据要脱敏和合规处理。

**不值得训的情况：**

- 数据噪声大，标注不一致。
- 只是想让模型记住最新知识。
- 需求还在频繁变化。
- 没有评测集。
- 样本太少且分布偏。
- 规则就能稳定解决。
- 线上问题其实来自检索或工具，而不是模型能力。

**面试可以这样说：**

微调数据一般来自线上真实 query、用户会话、人工标注、专家示范、线上错例、工单记录、工具调用轨迹和审核后的高质量模型输出。判断一批数据值不值得训，我会看几个点：任务是否稳定，数据标注是否一致，是否覆盖真实线上分布和边界 case，是否有独立评测集，是否真的属于模型能力问题，而不是 RAG、规则或工具问题。如果只是知识更新，优先 RAG；如果是权限和流程，优先规则；如果数据噪声大、需求变化快、没有评测集，就不适合直接微调。

## 7. 如果线上要做多轮对话，记忆写入策略怎么定，才能避免越聊越脏？

**问题：** 如果线上要做多轮对话，记忆写入策略怎么定，才能避免越聊越脏？

**答案：**

多轮对话里的记忆不能“听到什么就写什么”，否则很容易把临时情绪、模型猜测、错误信息、过期偏好和敏感内容写进长期记忆，导致越聊越脏。比较稳的策略是：默认不写长期记忆，只写经过门控判断的稳定信息。

**写入原则：**

- **用户明确表达优先：** 用户明确说“以后都用英文回答”可以写；模型推断“用户可能喜欢英文”不能直接写。
- **稳定信息才写：** 长期偏好、项目背景、明确事实可以写；临时情绪和一次性任务参数不写长期记忆。
- **敏感信息默认不写：** 身份证、手机号、地址、财务信息、健康信息等要谨慎，必要时脱敏或确认。
- **高影响记忆要确认：** 影响后续长期行为的偏好、身份、权限相关信息要让用户确认。
- **冲突要消解：** 新旧记忆冲突时，不能直接堆叠，要覆盖、合并、失效或询问用户。
- **设置过期和衰减：** 项目状态、临时偏好、阶段性任务要有 TTL 或时间衰减。

**写入流程：**

```text
候选记忆抽取
  -> 类型识别
  -> 稳定性判断
  -> 敏感性检测
  -> 与已有记忆查重/冲突检测
  -> 置信度评分
  -> 写入 / 合并 / 确认 / 丢弃
```

**存储字段：**

每条 memory 不要只存文本，最好存 metadata：

```json
{
  "type": "user_preference",
  "content": "用户偏好中文简洁回答",
  "source": "user_explicit",
  "confidence": 0.95,
  "scope": "user",
  "created_at": "2026-05-08",
  "expires_at": null,
  "status": "active"
}
```

**避免污染的关键：**

- 模型推断不直接写长期记忆。
- 错误工具结果不写。
- 低置信信息不写。
- 与当前任务无关的信息不写。
- 写入后支持用户查看、修改、删除。
- 召回时也要过滤过期、低置信、冲突和无关记忆。

**面试可以这样说：**

多轮对话的记忆写入不能什么都记，否则很容易越聊越脏。我会默认只写短期状态，长期记忆必须经过门控：看信息是不是用户明确表达、是否稳定、未来是否有用、是否敏感、是否和已有记忆冲突。模型推断的信息不直接写，敏感信息默认不写，高影响偏好要用户确认。每条记忆要带 type、source、confidence、scope、created_at、expires_at、status 等 metadata，并支持合并、覆盖、衰减和删除。召回时也要过滤低置信、过期和无关记忆，避免脏记忆继续污染上下文。

**答案：**

这个问题已有答案可以直接使用：

- [[AI Agent-02#13. Agent 评测为什么比普通问答评测更难？|AI Agent-02 第 13 题：Agent 评测为什么比普通问答评测更难？]]

**面试可以这样说：**

如果设计 Agent 评测体系，我会至少覆盖八类指标：第一是任务成功率，看用户目标是否完成；第二是意图识别和规划质量，看 intent、slot、计划步骤是否正确；第三是工具调用质量，看工具选择、参数、顺序、失败处理是否正确；第四是 RAG 效果，看 Recall@K、rerank、groundedness 和 citation accuracy；第五是最终答案质量，看正确性、完整性、格式和幻觉率；第六是安全合规，看越权、敏感信息、prompt injection 和高风险操作；第七是稳定性和可回放，看循环率、重试率、最大步数和 run trace；第八是成本和延迟，看 token、模型调用次数、工具调用次数和 P95/P99。Agent 评测不能只看答案，要评整个执行过程。

## 9. 讲一下你做过的系统架构，别只说用了哪些中间件

**问题：** 讲一下你做过的系统架构，别只说用了哪些中间件。（架构最好按数据流讲，而不是按技术名词堆）

**答案：**

回答系统架构时，可以先按分层讲清楚每层职责，再按一次请求的数据流串起来。这样既不像单纯堆中间件，也能体现工程上的完整性。

可以按这几层讲：

- **入口层：** 网关、鉴权、租户识别、限流、防刷、参数基础校验、请求 trace id 注入。
- **业务编排层：** 会话状态读取、意图识别、任务状态机、RAG / 工具 / 闲聊 / 追问路由。
- **模型与工具层：** query rewrite、混合检索、rerank、上下文组装、LLM 生成、tool calling、工具参数强校验。
- **异步层：** 长任务、重试、补偿、消息队列、离线索引更新、异步评测和日志消费。
- **存储层：** 业务库、会话状态、任务状态、向量索引、全文索引、对象存储、缓存。
- **观测与治理层：** run trace、指标、告警、审计、安全策略、效果评测。

再按数据流串起来：

```text
用户输入
  -> 入口网关：鉴权、租户识别、限流、防刷、基础参数校验
  -> 会话和任务状态读取
  -> 意图识别和路由
  -> RAG 检索 / 工具调用
  -> 上下文组装
  -> 模型生成
  -> 安全和事实校验
  -> 状态写回
  -> 日志和指标上报
  -> 返回用户
```

**示例回答：**

我做的系统可以理解成一个面向企业知识库和业务工具的对话 Agent。整体上我会按入口层、业务编排层、模型工具层、异步层、存储层和观测治理层来讲，但真正说明系统时会按请求的数据流展开。

用户请求进来后，先到入口层。入口层不只是转发请求，还会做鉴权、租户识别、角色校验、限流、防刷、基础参数校验和 trace id 注入。这里会先挡住非法请求、高频请求和明显不合规的输入，避免后面的模型服务、检索服务和业务工具被打穿。

通过入口层之后，进入业务编排层。系统会读取当前 session、task state 和用户权限，判断用户是不是在继续一个历史任务、当前任务缺哪些参数、有没有待确认的工具动作。然后做意图识别和路由，判断用户是在问知识库问题、查业务数据、执行工具操作，还是只是闲聊。如果信息不足，就先追问；如果是高风险操作，就进入确认流程。

如果进入 RAG 链路，系统会先做 query rewrite，然后根据用户权限选择可访问的知识库，走 BM25 和向量混合召回，再用 reranker 排序。召回结果不会直接全塞给模型，而是会做去重、版本过滤、权限二次校验和上下文压缩，最后只把高相关、有来源的 chunk 放进 prompt。

工具链路里，模型只负责提出 tool call，系统负责校验工具名、参数、权限和业务规则。比如查订单是只读工具，可以直接执行；退款、删除、发消息这类高风险操作，需要二次确认、幂等键和审计日志。

模型生成前，系统会把系统规则、当前用户问题、task state、检索证据、工具结果和输出格式组装成上下文。模型生成后，还会做 groundedness 校验、敏感信息检测、引用校验和安全策略检查。如果证据不足，就拒答、追问或转人工，而不是强行回答。

异步层主要处理不适合阻塞主链路的事情，比如长任务执行、失败重试、补偿任务、知识库离线切分和索引更新、日志消费、离线评测。存储层不只是一个数据库，通常会拆成业务库、会话状态、任务状态、缓存、全文索引、向量索引和对象存储。最后，系统会把本轮结果写回 task state，包括已收集参数、工具结果、任务状态和必要的短期记忆，并记录完整 run trace、模型输入输出、检索结果、工具调用、版本信息和 P95/P99 耗时，方便线上排查和离线评估。

**面试可以这样说：**

我讲架构不会只说用了哪些中间件，而是先按层次讲职责，再按数据流讲请求怎么走。入口层负责网关、鉴权、租户识别、限流、防刷和基础参数校验，先把非法请求和高频请求挡住。业务编排层读取 session 和 task state，做意图识别和路由，决定走 RAG、工具调用、追问还是直接回答。RAG 链路会做 query rewrite、权限过滤、混合召回、rerank、去重和上下文压缩；工具链路里模型只提出调用建议，系统做参数、权限和业务规则校验。异步层处理长任务、重试补偿、索引更新和日志消费；存储层保存业务数据、会话状态、任务状态、缓存、全文索引和向量索引。模型生成后还要做 groundedness、引用、敏感信息和安全校验，最后写回状态并记录完整 run trace 和 P95/P99 指标。这样讲能说明系统是怎么流转和闭环的，而不是只堆技术名词。

## 10. 向量数据库的作用是什么？它和普通检索系统的边界在哪里？

**问题：** 向量数据库的作用是什么？它和普通检索系统的边界在哪里？

**答案：**

向量数据库的核心作用是做语义相似检索。它把文本、图片或其他对象通过 embedding 模型转成向量，然后用近似最近邻检索找到“语义上接近”的内容。它适合解决用户表达和文档表达不完全一致的问题，比如同义改写、口语化提问、概念相近的问题。

但向量数据库不是完整的检索系统，也不是知识库本身。它更像检索链路里的一路召回能力，主要负责“语义召回”，不应该承担所有搜索、权限、版本、引用和结构化查询能力。

**边界可以这样分：**

- **向量数据库擅长：** 语义相似召回、模糊表达匹配、多模态 embedding 检索、相似案例推荐。
- **普通检索系统擅长：** 关键词精确匹配、错误码/编号/API 名称检索、字段过滤、排序规则、聚合统计、复杂布尔查询。
- **业务存储负责：** 原文、文档结构、版本、权限、租户、状态、附件、审计信息。
- **RAG 编排层负责：** query rewrite、多路召回、权限过滤、rerank、去重、上下文压缩和引用溯源。

所以工程里通常不会只用向量数据库，而是组合使用：

```text
用户问题
  -> query rewrite
  -> 向量召回 + BM25/关键词召回 + metadata 过滤
  -> 合并去重
  -> rerank
  -> 权限和版本校验
  -> 返回可引用的上下文
```

向量库和普通检索系统的边界，本质上是“语义相似”与“精确可控”的边界。向量库能提高召回的语义覆盖，但对精确词、数字、代码、表格字段、权限过滤和版本控制并不天然可靠；普通搜索更适合确定性检索，但对自然语言改写和语义泛化不如向量检索。

**面试可以这样说：**

向量数据库的作用不是替代搜索引擎或业务数据库，而是提供语义召回能力。它适合处理用户问题和文档表达不一致的场景，比如同义改写、口语化提问和相似案例推荐。但它不擅长精确匹配、权限控制、版本管理、复杂过滤和引用溯源。所以我会把向量库看成 RAG 检索链路中的一路召回，和 BM25、metadata 过滤、业务库、文档库一起配合使用。简单说，向量库解决“语义上像不像”，普通检索解决“关键词、字段、规则是否精确匹配”，业务系统解决“有没有权限、是不是最新、能不能引用”。

## 11. 为什么有些场景会选择多智能体，而不是单智能体把事情全做完？

**问题：** 为什么有些场景会选择多智能体，而不是单智能体把事情全做完？

**答案：**

选择多智能体不是因为“更高级”，而是因为有些任务天然需要分工、隔离和协作。单智能体什么都做，短期看简单，但任务一复杂，就容易出现上下文过长、角色混乱、工具过多、权限边界不清、错误难定位的问题。

多智能体适合这些场景：

- **任务跨度大：** 比如一个任务同时包含需求分析、代码生成、测试、安全审查和文档编写。
- **角色能力差异明显：** 不同 Agent 可以分别负责检索、规划、执行、审核、评测。
- **工具和权限需要隔离：** 只让某个 Agent 访问生产工具，另一个 Agent 只能读文档或做分析。
- **上下文需要隔离：** 每个 Agent 只看自己需要的上下文，减少无关信息干扰。
- **需要互相校验：** 一个 Agent 生成方案，另一个 Agent 做 review 或验证，降低单点幻觉。
- **任务可以并行：** 检索、测试、代码审查、数据分析可以并行做，提高吞吐。

但多智能体也有成本。它会带来通信开销、状态同步、任务分配、结果合并、一致性和可回放问题。所以不是任务越复杂越要多智能体，而是当“分工收益”大于“协调成本”时才值得做。

工程上一般会用一个主 Agent 或调度器负责任务拆解和状态管理，再把子任务分发给专门 Agent。子 Agent 不应该无限自由协作，而要有明确输入、输出、权限、超时、失败处理和审计日志。

**面试可以这样说：**

我不会默认把系统做成多智能体。单智能体适合任务边界清楚、工具数量少、上下文不复杂的场景；多智能体适合任务跨度大、角色差异明显、工具权限需要隔离、上下文容易互相干扰，或者需要并行执行和交叉验证的场景。比如一个复杂研发任务，可以由规划 Agent 拆任务，代码 Agent 实现，测试 Agent 跑验证，Review Agent 做审查。这样能降低单个 Agent 的上下文压力，也能把权限和责任边界拆清楚。但多智能体会增加通信、状态同步、结果合并和排障成本，所以工程上一定要有主调度器、明确的任务协议、权限控制、超时重试和完整 trace，而不是让多个 Agent 随意聊天。

## 12. 如果模型出现幻觉，你会怎么解决？

**问题：** 如果模型出现幻觉，你会怎么解决？

**答案：**

模型出现幻觉时，不能只说“换个更强模型”或者“改 prompt”。我会先把幻觉来源拆开定位：是用户问题本身不清楚，还是检索证据不够，还是上下文里有噪声或冲突，还是模型在没有依据时过度补全。

常见处理方式：

- **输入侧：** 对模糊问题先追问，不让模型自己猜用户意图。
- **检索侧：** 提高召回质量，做 query rewrite、混合检索、rerank，避免正确证据没进上下文。
- **上下文侧：** 过滤低相关、旧版本、无权限和互相冲突的内容，控制上下文长度和证据质量。
- **生成侧：** 要求模型基于证据回答，答案必须带引用；证据不足时明确说不知道、追问或转人工。
- **校验侧：** 做 groundedness、引用一致性、规则校验和高风险人工审核。
- **评测侧：** 把幻觉样本沉淀成回归集，持续看幻觉率、引用准确率和无答案拒答准确率。

如果是开放式闲聊或创作类任务，幻觉不一定都算严重问题；但如果是企业知识库、金融、医疗、法务、运维操作这类事实要求高的场景，就必须让模型有证据、有边界、有兜底。

**面试可以这样说：**

如果模型出现幻觉，我不会只从 prompt 下手，而是先定位幻觉发生在哪一层。输入不清楚就追问；检索证据不足就优化 query rewrite、混合召回和 rerank；上下文有噪声就做去重、版本过滤、权限过滤和冲突处理；生成阶段要求模型基于证据回答并给出引用；生成后再做 groundedness 和 citation 校验。证据不足时要拒答、追问或转人工，而不是让模型强行补全。最后把线上幻觉 case 放进回归评测集，持续跟踪幻觉率、引用准确率和 no-answer 准确率。

## 13. Skill 的渐进式披露是什么意思？为什么它能提升 Agent 的稳定性？

**问题：** Skill 的渐进式披露是什么意思？为什么它能提升 Agent 的稳定性？

**答案：**

Skill 的渐进式披露，指的是不要一开始就把所有 Skill 的完整内容都塞给模型，而是分阶段、按需暴露信息。模型先看到少量 Skill 摘要或 description，用来判断是否相关；只有命中某个 Skill 后，才加载这个 Skill 的详细步骤、约束、示例、脚本或工具说明。

可以理解成三层：

```text
第一层：Skill registry
只暴露 name、description、tags、when_to_use、when_not_to_use

第二层：Skill summary
命中候选后，暴露输入要求、输出格式、关键步骤、风险边界

第三层：Skill detail
确认使用后，才加载完整操作手册、示例、模板、脚本和工具说明
```

它能提升稳定性，核心原因是减少上下文噪声。Skill 太多时，如果全部塞进 system prompt，模型会同时看到大量相似规则、工具说明和示例，容易注意力分散、选错 Skill、混用步骤，甚至被无关 Skill 干扰当前任务。

渐进式披露的好处：

- **降低上下文占用：** 只加载当前任务相关 Skill，节省 token。
- **降低误路由：** 先用短描述和边界字段筛选候选，再加载详情。
- **减少规则冲突：** 避免多个 Skill 的操作步骤同时进入 prompt。
- **提升可控性：** 每次加载哪个 Skill、为什么加载，都可以记录和回放。
- **降低成本和延迟：** 不需要每轮都传大量无关 Skill 内容。
- **便于版本治理：** Skill 更新后可以按 registry、summary、detail 分层管理。

工程上通常会把 Skill 做成 registry，而不是 prompt 文本堆叠。路由阶段可以用规则、embedding、分类模型或 LLM 从 registry 里选 TopK 候选，再做二次判断；真正执行前，还要校验输入是否满足该 Skill 的必要条件。如果低置信度，就追问用户或不加载，而不是强行套用。

**面试可以这样说：**

Skill 的渐进式披露就是按需加载，而不是一上来把所有 Skill 完整塞进上下文。第一阶段只给模型看 Skill 的 name、description、tags、适用和不适用条件，用来做路由；第二阶段只展开候选 Skill 的摘要、输入输出和关键约束；确认使用后才加载完整步骤、示例、模板或脚本。这样能提升 Agent 稳定性，因为模型看到的信息更少、更相关，减少了上下文噪声、Skill 误选、规则冲突和 token 浪费。工程上还可以记录每次 Skill 召回和加载过程，方便排查为什么选错能力。

## 14. OpenClaw 这类框架，如果真的要做生产级 Agent，最先要补的是什么？

**问题：** OpenClaw 这类框架，如果真的要做生产级 Agent，最先要补的是什么？

**答案：**

OpenClaw 这类框架通常能快速搭出 Agent demo，比如有模型调用、工具调用、Skill、记忆、会话和多渠道入口。但要做生产级 Agent，最先补的不是更多工具，而是工程护栏和可观测闭环。

我会优先补这几类能力：

- **权限和安全边界：** 工具白名单、用户权限、租户隔离、敏感接口审批、高风险操作二次确认。
- **状态管理：** 显式 task state、step state、tool result、memory 读写记录，不能每轮都靠模型从对话里猜。
- **工具执行治理：** 参数 schema 强校验、幂等键、超时、重试、失败补偿、熔断和审计日志。
- **可观测和可回放：** 记录每次模型输入输出、Skill 选择、工具调用、检索结果、状态变化、耗时和错误。
- **评测体系：** 离线任务集、工具 mock、回归测试、线上 A/B、幻觉率、任务成功率、P95/P99 延迟。
- **上下文和 Skill 治理：** Skill registry、渐进式披露、TopK 路由、上下文预算、版本管理和误加载排查。
- **兜底机制：** 低置信追问、拒答、人工接管、最大步数、最大工具调用次数和死循环终止。

如果只能选一个最先补，我会选“可观测和可回放”。因为生产环境里 Agent 出错不一定是模型错，可能是意图识别、Skill 路由、上下文、工具参数、权限、外部服务或状态更新的问题。没有完整 trace，就无法定位，也无法做评测和持续优化。

**面试可以这样说：**

OpenClaw 这类框架适合快速搭 Agent 原型，但生产级 Agent 最先补的不是更多 Skill 或更多工具，而是可控性和可观测性。首先要有权限边界，限制模型能调用哪些工具、哪些用户能访问哪些资源，高风险动作必须二次确认。其次要有显式任务状态和工具执行治理，包括参数强校验、幂等、超时、重试、补偿和审计。再往上要有完整 run trace，能记录模型输入输出、Skill 选择、工具调用、状态变化和耗时，这样线上出问题才能回放。最后才是评测、上下文治理和兜底策略。我的判断是：框架解决“能跑起来”，生产系统要补“可控、可查、可评估、可恢复”。

## 16. 主 Agent 和子 Agent 的模型该怎么分配？为什么不一定都用同一个大模型？

**问题：** 主 Agent 和子 Agent 的模型该怎么分配？为什么不一定都用同一个大模型？

**答案：**

主 Agent 和子 Agent 的模型不一定要用同一个。模型分配应该看任务复杂度、风险等级、上下文长度、延迟、成本和稳定性要求，而不是默认全部上最强大模型。

一般可以这样分：

- **主 Agent / 调度器：** 负责理解目标、任务拆解、路由、状态管理和结果合并，通常需要更强的推理能力和更大的上下文。
- **检索 Agent：** 主要做 query rewrite、检索策略选择、证据整理，可以用中等模型或规则 + embedding。
- **工具执行 Agent：** 如果只是结构化参数生成和校验，可以用小模型、规则或专用分类器。
- **审核 / Review Agent：** 负责发现错误、幻觉、安全风险，通常需要较强模型，但可以只在高风险或低置信场景触发。
- **摘要 / 格式化 Agent：** 任务相对稳定，可以用轻量模型。
- **高风险决策 Agent：** 涉及资金、权限、删除、生产变更时，不能只靠模型，要加规则、权限系统和人工确认。

不全用同一个大模型，主要有几个原因：

- **成本：** 所有子任务都用大模型，调用成本会迅速上升。
- **延迟：** 多 Agent 串并行调用时，大模型会放大 P95/P99 延迟。
- **稳定性：** 简单分类、参数抽取、格式转换用小模型或规则反而更稳定。
- **安全边界：** 不同 Agent 应该有不同权限和工具集合，模型能力强不等于应该拥有更多权限。
- **可评估性：** 子任务越专门，越容易用单独指标评估和优化。

工程上更常见的是模型分层路由：默认用轻量模型处理简单、低风险任务；复杂规划、跨轮推理、结果汇总用强模型；低置信度、高风险或冲突场景再升级到强模型或人工审核。

**面试可以这样说：**

主 Agent 和子 Agent 不一定都用同一个大模型。主 Agent 负责目标理解、任务拆解、路由和结果合并，通常需要更强模型；但很多子 Agent 做的是检索改写、参数抽取、格式化、摘要、规则校验，这些任务边界清楚，用小模型、embedding 或规则反而成本更低、延迟更稳。只有复杂推理、审核、高风险决策或低置信场景才需要升级到强模型。这样做的核心是模型分层：让强模型处理真正需要推理的部分，让轻量模型和规则处理确定性部分，同时用权限、工具白名单和 run trace 控制风险。

## 17. 多 Agent 系统里，state 管理和 checkpoint 机制为什么是核心？不只是工程细节

**问题：** 多 Agent 系统里，state 管理和 checkpoint 机制为什么是核心？不只是工程细节？

**答案：**

多 Agent 系统里，state 管理和 checkpoint 不是普通工程细节，而是系统能不能稳定协作、恢复和排障的核心。因为多 Agent 不是一次模型回答，而是多个角色、多轮步骤、多工具调用和多个外部状态共同推进一个任务。如果没有显式 state，系统就会退化成“每个 Agent 都从对话里猜当前进度”。

state 管理解决的是“现在任务到底处于什么状态”：

- 主 Agent 拆了哪些子任务。
- 每个子 Agent 正在执行哪一步。
- 哪些步骤已完成，哪些失败，哪些等待用户确认。
- 工具调用结果是什么，是否已经写入外部系统。
- 当前是否允许继续执行，还是需要暂停、重试、补偿或人工接管。

checkpoint 解决的是“出错、中断或重启后从哪里恢复”：

- 模型调用失败后，不需要从头重跑所有步骤。
- 工具已经执行成功时，不能因为重试导致重复写入。
- 子 Agent 部分完成时，主 Agent 可以基于 checkpoint 合并结果。
- 长任务暂停后，可以从安全点继续，而不是重新猜上下文。
- 线上问题可以按 checkpoint 和 run trace 回放，定位是哪一步出错。

在多 Agent 里，这尤其关键。因为多个 Agent 可能并行执行，如果没有统一状态源，就会出现重复执行、结果覆盖、顺序错乱、权限状态不一致、失败后无法恢复等问题。checkpoint 还能把不确定的模型过程变成可追踪的执行过程，让系统具备一致性、幂等性和可回放能力。

工程上通常会把它设计成：

```text
run_state：一次完整任务运行
task_state：任务目标、计划、状态、下一步
agent_state：每个子 Agent 的输入、输出、进度、错误
tool_state：工具参数、结果、幂等键、外部资源版本
checkpoint：关键步骤后的快照和可恢复点
event_log：每次状态变更的事件日志
```

**面试可以这样说：**

多 Agent 里的 state 和 checkpoint 不是普通工程细节，而是协作协议的一部分。因为多个 Agent 会拆任务、并行执行、调用工具、等待用户确认和合并结果，如果没有显式 state，每个 Agent 都只能从上下文里猜当前进度，很容易重复执行、漏步骤、覆盖结果或失败后无法恢复。我会把 run_state、task_state、agent_state、tool_state 和 event_log 作为事实来源，并在模型调用前后、工具调用前后、高风险写操作前后设置 checkpoint。这样中断后可以从安全点恢复，已完成工具不会重复执行，线上问题也能按 trace 回放。简单说，state 决定系统当前是什么，checkpoint 决定系统失败后怎么回来。

## 18. LangGraph 里的 checkpoint 和 memory 到底有什么区别？

**问题：** LangGraph 里的 checkpoint 和 memory 到底有什么区别？

**答案：**

在 LangGraph 里，checkpoint 和 memory 不是同一个概念。

**Checkpoint 是执行状态快照。**  
它保存的是某个 thread 在某个执行步骤上的 graph state，比如 messages、当前节点、下一步要执行的节点、metadata、pending tasks 等。它的核心用途是恢复执行、支持中断续跑、human-in-the-loop、time travel、debug 和回放。

**Memory 是让 Agent 记住信息。**  
它关注的是“未来回答或任务中要不要用到这些信息”。LangGraph 里 memory 可以分成短期 memory 和长期 memory：

- **短期 memory：** 通常是 thread-scoped 的对话状态，作为 graph state 的一部分保存，底层依赖 checkpointer 持久化。
- **长期 memory：** 跨 thread、跨会话保存用户偏好、稳定事实、历史经验，通常放在 store 里，并按 namespace 查询。

可以这样区分：

```text
checkpoint：保存一次执行到哪了
memory：保存以后还要记住什么

checkpoint：偏运行时恢复和回放
memory：偏上下文召回和个性化

checkpoint：thread 内的状态快照
memory：可以跨 thread、跨会话复用
```

举个例子：用户说“我叫 Lulu”，这句话在当前对话里会作为 messages 进入 state，并通过 checkpoint 保存，所以同一个 thread 继续问“我叫什么”可以回答出来。这属于短期 memory。但如果希望下周新开一个 thread 时系统仍然记得用户叫 Lulu，就需要把它写入长期 memory store，而不是只依赖 checkpoint。

所以 checkpoint 更像运行时的“存档点”，memory 更像可召回的“用户或任务知识”。两者有关系：短期 memory 常常通过 checkpoint 实现持久化；但长期 memory 不是 checkpoint，它需要单独的写入策略、召回策略、过期策略和冲突处理。

**面试可以这样说：**

LangGraph 里的 checkpoint 和 memory 要分开理解。Checkpoint 是 graph 执行状态的快照，按 thread 保存，用来中断恢复、回放、time travel 和 human-in-the-loop；它回答的是“这个任务执行到哪一步了”。Memory 回答的是“系统以后要记住什么信息”。短期 memory 通常作为 graph state 的一部分，通过 checkpoint 持久化；长期 memory 则应该放在 store 里，跨 thread、跨会话召回，比如用户偏好、稳定事实和历史经验。所以 checkpoint 是恢复执行的机制，memory 是影响未来上下文的知识管理机制，不能混为一谈。

## 19. MCP 工具接入后，模型调用工具前后的处理流程一般是什么样的？

**问题：** MCP 工具接入后，模型调用工具前后的处理流程一般是什么样的？

**答案：**

MCP 工具接入后，不能理解成“模型想调什么就直接调什么”。更合理的流程是：MCP 负责标准化暴露工具，Agent Runtime 负责工具发现、候选选择、权限校验、参数校验、执行治理、结果处理和状态写回。

完整流程一般是：

```text
MCP server 初始化
  -> 能力协商和工具发现
  -> 工具注册到 tool registry
  -> 根据用户输入和任务状态筛选候选工具
  -> 把少量候选工具 schema 暴露给模型
  -> 模型生成 tool call
  -> 系统做工具名、参数、权限、风险校验
  -> 必要时用户确认
  -> 通过 MCP tools/call 执行工具
  -> 校验和清洗工具结果
  -> 写回 tool state / task state / checkpoint
  -> 把结果交给模型继续推理或生成最终回答
```

**1. 接入和发现阶段**

MCP client 和 MCP server 先初始化连接，完成协议版本和能力协商。server 如果声明了 tools capability，client 可以通过 `tools/list` 获取工具列表。工具定义通常包括 name、description、inputSchema，有些还会有 outputSchema、annotations 等信息。

拿到工具后，不应该无脑全部塞给模型，而是进入本地 tool registry，补充业务侧 metadata，比如风险等级、权限要求、是否只读、是否需要确认、超时、重试策略、幂等策略。

**2. 模型调用前**

模型真正看到工具前，系统要先做候选筛选：

- 根据 intent、task state、用户权限筛选可用工具。
- 高风险工具默认不直接暴露，或只在特定状态下暴露。
- 只把 TopK 候选工具的 schema 给模型，减少误调用。
- 对工具 description 做边界说明，避免相似工具混淆。

模型输出 tool call 后，系统不能立刻执行，要做：

- tool name 是否在白名单。
- arguments 是否符合 JSON Schema。
- 用户是否有权限访问目标资源。
- 参数是否满足业务规则。
- 是否涉及高风险写操作。
- 是否需要用户二次确认。
- 是否带幂等键、trace_id、run_id。

**3. 工具执行中**

执行阶段才通过 MCP 的 `tools/call` 请求调用 server。这里要加超时、重试、熔断、限流、审计和错误分类。只读工具和低风险工具可以自动执行；写操作、删除、转账、发消息、生产变更这类操作要更严格，必要时走人工确认或审批。

**4. 工具调用后**

工具返回后，也不能直接把原始结果塞给模型。系统要先处理：

- 校验 outputSchema 或结果结构。
- 清洗敏感字段。
- 判断 `isError` 或业务错误。
- 把大结果摘要、裁剪或结构化。
- 标注来源、时间、资源版本和可信度。
- 写入 tool state、task state 和 run trace。
- 必要时触发重试、补偿、追问或人工接管。

最后再把“可给模型看的工具结果”放回上下文，让模型基于结果继续下一步，或者生成最终答案。

**面试可以这样说：**

MCP 接入后，我不会让模型直接裸调工具。流程上先是 MCP client 和 server 初始化，完成版本和能力协商；然后通过 tools/list 做工具发现，把工具 name、description、inputSchema 注册到本地 tool registry，并补充权限、风险等级、是否只读、是否需要确认等业务 metadata。每轮请求进来后，系统根据 intent、task state 和用户权限筛选少量候选工具给模型。模型生成 tool call 后，系统侧先做工具白名单、参数 schema、权限、业务规则和风险校验，高风险动作还要二次确认。真正执行时通过 tools/call 调 MCP server，并加超时、重试、限流、审计和幂等。工具返回后还要校验结果、脱敏、摘要、写回 task state 和 run trace，再把可用结果交给模型继续生成。核心原则是：MCP 负责标准化接入，生产系统负责校验、权限、状态和治理。

## 20. FastAPI + SSE 做流式输出时，后端通常怎么把多节点执行结果实时推给前端？

**问题：** FastAPI + SSE 做流式输出时，后端通常怎么把多节点执行结果实时推给前端？

**答案：**

FastAPI + SSE 做 Agent 流式输出时，核心不是简单把模型 token 流出来，而是把 Agent 执行过程里的多类事件统一成事件流：节点开始、节点结束、工具调用、工具结果、模型 token、错误、需要用户确认、最终完成等。

典型链路是：

```text
前端发起请求
  -> FastAPI 建立 SSE 连接
  -> 创建 run_id / task_id
  -> 后端启动 Agent 执行任务
  -> 每个节点执行时产生事件
  -> 事件写入 async queue / Redis PubSub / Stream
  -> SSE async generator 持续读取事件
  -> 转成 text/event-stream 推给前端
  -> 前端按 event type 更新 UI
```

**1. 后端要先定义统一事件格式**

多节点执行不能只返回字符串，最好统一成结构化事件：

```json
{
  "run_id": "run_123",
  "node_id": "retriever",
  "event": "node_end",
  "seq": 12,
  "timestamp": "2026-05-08T10:00:00Z",
  "data": {
    "status": "success",
    "summary": "召回 5 个文档"
  }
}
```

常见 event type：

- `run_start`
- `node_start`
- `node_end`
- `tool_call`
- `tool_result`
- `llm_token`
- `progress`
- `need_confirmation`
- `error`
- `run_end`

**2. Agent 执行层负责产出事件**

每个节点执行前后都发事件：

- RAG 节点：推送“正在检索”“召回完成”“rerank 完成”。
- 工具节点：推送工具名、参数摘要、执行状态和结果摘要。
- LLM 节点：推送 token 或 sentence-level chunk。
- 审核节点：推送安全校验、引用校验、是否需要人工确认。

事件不要直接等整个任务结束后一次性返回，否则前端无法展示真实进度。

**3. SSE 层只负责传输，不负责业务编排**

FastAPI 通常用 `StreamingResponse` 或 `EventSourceResponse` 返回 `text/event-stream`。SSE 的 async generator 从队列里不断取事件，格式化成：

```text
event: node_end
id: 12
data: {"run_id":"run_123","node_id":"retriever","status":"success"}

```

如果 Agent 执行和 SSE 连接在同一个进程，可以用 `asyncio.Queue`。如果是多 worker、异步任务或分布式部署，更常见的是用 Redis Pub/Sub、Redis Stream、Kafka 或消息队列做事件总线。

**4. 要处理连接断开和重连**

SSE 是长连接，生产里必须考虑：

- 前端断开时，后端停止无意义推送或只保留任务继续执行。
- 事件要带 `seq` 或 `event_id`，支持前端断线后从最后位置恢复。
- 定期发送 heartbeat，避免代理层超时断开。
- 任务最终状态要落库，不能只存在 SSE 连接里。
- 错误事件也要推给前端，而不是让连接静默断开。

**5. 多节点并行时要保证顺序和可解释**

如果多个节点并行执行，事件到达顺序可能不等于计划顺序。所以要带：

- `run_id`
- `node_id`
- `parent_node_id`
- `step_id`
- `seq`
- `status`
- `timestamp`

前端可以按 `seq` 展示时间线，也可以按 `node_id` 更新对应节点状态。最终结果合并要由后端状态机决定，不能让前端自己猜哪个节点结果有效。

**面试可以这样说：**

FastAPI + SSE 做 Agent 流式输出时，我会把后端执行过程抽象成事件流，而不是只流模型 token。请求进来后先创建 run_id 和 task_id，然后 Agent 每个节点在开始、结束、工具调用、工具返回、模型生成、报错和完成时都产出结构化事件。单进程可以用 asyncio.Queue 连接 Agent 执行层和 SSE generator；多实例或异步任务场景会用 Redis Pub/Sub、Redis Stream 或消息队列做事件总线。SSE 层只负责把事件格式化成 text/event-stream 推给前端，前端按 event type 更新进度、工具状态和最终答案。生产里还要处理 heartbeat、断线重连、seq 顺序、错误事件、任务状态落库和 run trace，这样多节点执行才可展示、可恢复、可排查。

## 21. 在执行流里捕获每个 node 的结果并推到前端，为什么不能只在最终节点统一汇总？

**问题：** 在执行流里捕获每个 node 的结果并推到前端，为什么不能只在最终节点统一汇总？

**答案：**

不能只在最终节点统一汇总，核心原因是 Agent 执行不是一个黑盒函数，而是一个多步骤、多工具、可能中断和失败的执行过程。只看最终结果，会丢掉过程状态，前端体验、排障、恢复和安全控制都会变差。

逐 node 捕获和推送有几个价值：

- **用户体验：** 长任务如果一直等到最终节点才返回，用户只看到加载中，不知道系统是否卡住。
- **进度展示：** 前端需要知道当前是检索中、工具调用中、模型生成中，还是等待确认。
- **失败定位：** 如果最终失败，只看最终节点很难知道是检索失败、工具超时、权限拒绝还是模型生成失败。
- **中断恢复：** 每个 node 的结果写入 state / checkpoint 后，任务可以从最近成功节点恢复。
- **安全控制：** 高风险工具调用前需要把中间状态推给用户确认，不能等最终节点再说。
- **部分结果可用：** 有些节点虽然后续失败，但检索结果、工具结果或分析摘要仍然有价值。
- **可观测和评测：** Agent 效果不能只评最终答案，还要评每一步的路由、检索、工具和状态更新是否正确。

如果只在最终节点统一汇总，会出现几个问题：

```text
长时间无响应 -> 用户重复提交或关闭页面
中间节点失败 -> 只能看到最终失败，无法定位
工具已执行成功 -> 失败重试可能重复写入
需要用户确认 -> 没有机会在中间拦截
并行节点完成顺序不同 -> 最终汇总难解释过程
线上问题复盘 -> 缺少 node-level trace
```

工程上更稳的做法是：每个 node 开始、结束、失败时都产出事件；事件既推给前端，也写入 run trace 和 task state。前端拿它做进度展示，后端拿它做恢复、审计、评测和排障。最终节点只负责汇总最终答案，不应该承担整个执行过程的唯一记录职责。

**面试可以这样说：**

我不会只在最终节点统一汇总，因为 Agent 是一个多步骤执行系统，不是普通接口调用。每个 node 的结果都代表一次状态变化，比如检索完成、工具调用成功、权限拒绝、需要用户确认或模型生成中。如果只等最终节点返回，用户体验上会长时间无反馈，工程上也无法定位是哪一步失败，更没法做中断恢复、幂等控制和安全确认。我会让每个 node 产出结构化事件，同时写入 task state、checkpoint 和 run trace，再通过 SSE 推给前端。最终节点只负责汇总答案，过程事件负责可见性、可恢复性和可排查性。

## 22. 为什么很多团队在 Agent 编排里选择 LangGraph，而不是直接用更轻的链式框架？

**问题：** 为什么很多团队在 Agent 编排里选择 LangGraph，而不是直接用更轻的链式框架？

**答案：**

很多团队选择 LangGraph，不是因为链式框架不能用，而是因为生产级 Agent 通常不是一条简单的 `prompt -> model -> output` 链路。它更像一个有状态的执行图，里面有分支、循环、工具调用、中断恢复、人审、重试、并行节点和状态写回。

轻量链式框架适合：

- 简单 RAG。
- 固定 prompt 链。
- 单次工具调用。
- 输入输出比较稳定的流程。
- 不需要复杂中断、恢复和状态追踪的任务。

但 Agent 一旦进入生产，常见需求会变成：

- 根据当前 state 决定下一步走哪个节点。
- 工具失败后重试、降级或换路径。
- 高风险节点中断，等待用户或人工确认。
- 长任务执行到一半可以恢复。
- 多节点并行执行后合并结果。
- 每一步都要 checkpoint 和 run trace。
- 线上问题要能回放和定位。

LangGraph 的价值就在于它把 Agent 编排显式建模成 graph：state 表示当前任务状态，node 表示执行逻辑，edge / conditional edge 表示流转规则。这样比线性 chain 更适合表达复杂控制流。

更关键的是，LangGraph 提供持久化和 checkpoint 机制。graph 执行过程中可以按 thread 保存 state snapshot，这让 human-in-the-loop、中断恢复、time travel debug、故障恢复和长任务续跑成为系统能力，而不是每个团队自己重新造一套。

所以选 LangGraph 的核心原因不是“更重”，而是它解决了链式框架在复杂 Agent 里的几个短板：

- **状态显式：** 不用每轮从对话历史里猜任务进度。
- **控制流清晰：** 支持分支、循环、并行和条件路由。
- **可恢复：** checkpoint 能支持中断后继续执行。
- **可观测：** 每个 node 的输入输出和状态变化都能记录。
- **适合人审：** 高风险步骤可以暂停、检查、修改 state 后继续。
- **适合长任务：** 不要求一次请求里跑完整个流程。

但这不代表所有项目都要用 LangGraph。如果只是简单问答、简单 RAG 或固定链路，轻量 chain 更快、更简单；如果任务有多步骤状态、工具调用、循环分支、中断恢复和线上排障要求，LangGraph 更合适。

**面试可以这样说：**

很多团队选 LangGraph，是因为生产级 Agent 往往不是一条线性链路，而是一个有状态的执行图。轻量链式框架适合简单 RAG、固定 prompt 链和单次工具调用；但复杂 Agent 会有分支、循环、并行工具、人审、中断恢复、失败重试和状态写回。LangGraph 用 state、node、edge 把这些流程显式建模，并且有 checkpoint 和 persistence，可以按 thread 保存执行状态，支持 human-in-the-loop、time travel、故障恢复和长任务续跑。我的判断是：链式框架解决“顺序执行”，LangGraph 解决“有状态、可恢复、可观测的 Agent 编排”。简单场景不用上 LangGraph，复杂生产 Agent 才值得用。

## 23. Checkpoint 持久化一般会存什么？中断后恢复最难的点是什么？通常持久化到哪里？选型看什么？

**问题：** Checkpoint 持久化一般会存什么？Checkpoint 中断后，恢复到之前状态最难的点通常是什么？通常持久化到哪里？选型是看什么？

**答案：**

Checkpoint 保存的不是一段聊天记录，而是一次 Agent / Graph 执行到某个安全点时的状态快照。它的目标是让任务中断、失败或重启后，可以知道“之前执行到哪里、哪些结果已经产生、下一步该从哪里继续”。

**1. Checkpoint 一般会存什么**

通常包括：

- **run 信息：** `run_id`、`task_id`、`thread_id`、用户、租户、模型版本、prompt 版本。
- **graph / task state：** 当前节点、下一步节点、任务状态、计划、槽位、已完成步骤、待执行步骤。
- **message state：** 当前 thread 内必要的 messages、历史摘要、系统上下文。
- **node 输出：** 每个节点的输入、输出、状态、错误、耗时。
- **tool state：** 工具名、参数、结果、错误、幂等键、外部资源版本。
- **control state：** 是否暂停、是否等待用户确认、重试次数、超时状态、取消状态。
- **metadata：** 时间戳、seq、trace_id、checkpoint_id、schema version。

如果是生产系统，还要记录事件日志 event log，因为 checkpoint 是某个时间点的快照，event log 能还原状态变化过程。

**2. 中断后恢复最难的点**

最难的不是把 JSON 状态读回来，而是处理“外部副作用”和“不确定状态”。

典型难点：

- **工具已经执行成功，但 checkpoint 没来得及写。**
- **checkpoint 写成功了，但外部 API 实际失败或超时。**
- **写操作被重试，可能重复扣款、重复发消息、重复创建资源。**
- **并行节点部分成功、部分失败，恢复时不知道哪些可以跳过。**
- **用户在中断期间修改了任务目标或权限发生变化。**
- **外部数据版本变化，恢复后的上下文和当时不一致。**

所以恢复不能简单“从 checkpoint 继续跑”。写操作要有幂等键、外部状态查询、资源版本号和补偿机制。恢复时通常要先做 reconcile：检查 checkpoint、工具日志和外部系统真实状态是否一致，再决定跳过、重试、补偿、追问或转人工。

**3. 通常持久化到哪里**

常见选择：

- **Redis：** 适合短期运行态、低延迟 checkpoint、TTL、任务恢复、SSE 进度配合。
- **PostgreSQL / MySQL：** 适合长期保存、事务一致性、审计、查询和报表。
- **MongoDB / 文档库：** 适合 checkpoint 结构变化大、JSON state 较复杂的场景。
- **对象存储：** 适合大体积上下文、工具原始结果、文件、长 trace 附件。
- **Kafka / Redis Stream / EventStore：** 适合 event sourcing，保留完整状态变更事件。

实际项目里常常是组合：Redis 存热状态，数据库存正式 checkpoint 和任务状态，对象存储放大结果，事件流存执行日志。

**4. 选型看什么**

主要看这些因素：

- **恢复时效：** 是否需要秒级恢复。
- **持久化时长：** 只保留几小时，还是要审计几个月。
- **一致性要求：** 是否涉及资金、审批、生产变更等高风险写操作。
- **查询需求：** 是否需要按用户、任务、状态、错误类型检索。
- **数据大小：** checkpoint 是小状态，还是包含大量工具结果和上下文。
- **并发规模：** checkpoint 写入频率和任务数量有多大。
- **合规审计：** 是否要求不可篡改、可追溯、长期保存。
- **成本和性能：** 同步写强一致更安全，但会增加延迟。

**面试可以这样说：**

Checkpoint 持久化一般存的是一次执行的状态快照，包括 run_id、task_id、thread_id、当前节点、下一步、task state、messages、node 输出、tool 参数和结果、错误、重试次数、幂等键、trace_id 和 schema version。中断恢复最难的不是把状态读回来，而是处理外部副作用：比如工具到底有没有执行成功、写操作会不会重复、并行节点哪些已经完成、外部数据版本有没有变化。所以恢复前要做 reconcile，结合 checkpoint、工具日志和外部系统真实状态判断是跳过、重试、补偿还是人工介入。存储上，Redis 适合短期热状态和快速恢复，PostgreSQL/MySQL 适合长期 checkpoint、审计和查询，对象存储适合大结果，事件流适合完整回放。选型主要看恢复时效、一致性要求、保留时长、查询需求、数据体积和合规审计。

## 24. 你怎么理解 Agent 里的“状态”，而不是“上下文”？

**问题：** 你怎么理解 Agent 里的“状态”，而不是“上下文”？

**答案：**

Agent 里的状态和上下文不是一回事。状态是系统事实源，表示任务当前真实处于什么阶段、已经发生了什么、下一步允许做什么；上下文是给模型看的输入视图，是从状态、历史、检索结果、工具结果和规则里挑出来的一部分信息。

可以简单区分：

```text
状态 state：系统用来控制执行
上下文 context：模型用来理解和生成

状态 state：结构化、可更新、可校验、可持久化
上下文 context：拼接后的 prompt/input，受 token 预算限制

状态 state：事实来源
上下文 context：状态的一个投影
```

比如一个订票 Agent，状态里会保存：

- 当前任务类型是订票。
- 出发地、目的地、日期是否齐全。
- 当前步骤是询价、确认还是支付。
- 哪些工具已经调用过。
- 是否等待用户确认。
- 是否允许执行支付。

上下文里则可能只放当前用户问题、最近几轮对话、必要的 task state 摘要、工具结果摘要和输出格式。模型不需要也不应该看到所有状态字段。

为什么不能把状态当成上下文？

- **上下文会被截断，状态不能丢。**
- **上下文可能有噪声，状态必须结构化可信。**
- **上下文主要服务模型生成，状态负责系统控制流。**
- **上下文里的信息可能来自用户或文档，状态变更必须经过校验。**
- **上下文不适合做恢复、幂等、权限和审计，状态可以。**

所以生产 Agent 一般是状态驱动，而不是上下文驱动。每轮请求进来，系统先读取 state，再决定要给模型哪些 context；模型可以建议状态更新，但最终写 state 要经过 schema 校验、权限校验、状态机校验和业务规则校验。

**面试可以这样说：**

我理解 Agent 里的状态不是上下文。状态是系统事实源，记录任务目标、槽位、当前步骤、工具结果、权限、安全状态、等待确认和下一步动作；上下文只是每轮给模型看的输入，是从状态、历史对话、检索结果和工具结果里筛出来的一部分。上下文会受 token 限制，也可能有噪声，不能承担控制流和恢复责任。状态要结构化、可校验、可持久化、可回放，决定系统能不能继续执行、重试、恢复和审计。所以生产 Agent 应该是 state-driven：系统读状态、拼上下文、让模型决策，再把模型建议经过规则校验后写回状态，而不是每轮让模型从一大段上下文里重新猜。

## 25. 一个 Agent 系统里，什么时候应该追问用户，什么时候应该自己继续推理？

**问题：** 一个 Agent 系统里，什么时候应该追问用户，什么时候应该自己继续推理？

**答案：**

追问和继续推理的判断，本质上是看“缺的信息是否影响执行结果或风险”。如果缺的是关键约束、权限确认或高风险参数，就应该追问；如果缺的是可以从上下文、工具、知识库或默认规则中可靠补齐的信息，就可以继续推理或继续调用工具。

**应该追问用户的情况：**

- **关键槽位缺失：** 例如订票缺日期，退款缺订单号，生成方案缺目标对象。
- **存在多个合理解释：** 用户说“帮我处理一下那个问题”，但上下文里有多个候选任务。
- **高风险操作前：** 删除、支付、退款、发消息、生产变更、权限修改等必须确认。
- **用户意图低置信：** intent、tool route 或 task type 不确定。
- **状态冲突：** 当前输入和 task state、工具结果或历史信息冲突。
- **证据不足：** RAG 没有召回可靠证据，继续回答会幻觉。
- **用户偏好影响结果：** 比如要保守方案还是激进方案、中文还是英文、详细还是简洁。

**可以自己继续推理的情况：**

- 缺的是非关键细节，不影响主要结果。
- 可以从 task state、最近上下文或用户历史偏好中明确推断。
- 可以通过只读工具或 RAG 安全补充信息。
- 有明确默认规则，并且默认规则不会带来风险。
- 当前是低风险分析、摘要、格式化或解释类任务。
- 可以先给出假设，并在答案里说明假设条件。

工程上可以做成决策规则：

```text
缺信息
  -> 是否关键槽位？是 -> 追问
  -> 是否高风险动作？是 -> 确认
  -> 是否多解释且影响结果？是 -> 追问
  -> 是否能通过只读工具/RAG补齐？是 -> 自己查
  -> 是否低风险且有默认规则？是 -> 继续
  -> 否则 -> 追问或给出带假设的回答
```

好的 Agent 不是追问越少越好，也不是一直追问最安全。追问太多会打断用户体验；不该追问时追问，显得系统不聪明。但该追问时不追问，会导致错执行、越权、幻觉或业务风险。

**面试可以这样说：**

我判断是否追问，核心看缺失信息是否关键、是否高风险、是否会改变执行结果。如果缺的是订单号、日期、金额、目标对象、权限确认这类关键槽位，或者用户意图有多个解释，就必须追问；删除、支付、退款、发消息、生产变更这类高风险动作也必须确认。如果缺的信息可以从 task state、上下文、只读工具或 RAG 里可靠补齐，或者只是低风险摘要、解释、格式化任务，就可以继续推理。工程上我会结合 intent confidence、missing_slots、risk_level、tool_type 和 evidence_score 做决策。原则是：低风险可推理，高风险要确认；能可靠查到就自己查，不能可靠判断就追问。

## 26. 如果工具调用是成功的，但返回结果语义不完整，模型容易误判，怎么设计中间层？

**问题：** 如果工具调用是成功的，但返回结果语义不完整，模型容易误判，怎么设计中间层？

**答案：**

工具调用成功只能说明接口层面成功，比如 HTTP 200、RPC success、MCP tools/call 没报错；但这不等于结果在语义上足够支持模型决策。生产里要在工具和模型之间加一个 tool result adapter / observation layer，把原始工具返回转换成可解释、可校验、可追溯的 observation。

中间层一般做几件事：

- **结构校验：** 校验字段是否完整，类型是否正确，是否符合 output schema。
- **语义完整性检查：** 判断回答当前任务需要的关键字段是否齐全。
- **业务状态解释：** 把枚举、错误码、空结果、部分成功状态翻译成明确含义。
- **置信度标注：** 标注结果是否 complete、partial、ambiguous、stale、conflict。
- **补充查询：** 如果缺关键字段，自动调用补充工具或二次查询。
- **风险拦截：** 不完整结果不能直接驱动高风险动作。
- **上下文压缩：** 把大结果转成模型容易理解的摘要和证据。
- **可追溯记录：** 保留 raw_result、normalized_result、source、timestamp、version、trace_id。

可以设计成这样的结构：

```json
{
  "tool_status": "success",
  "semantic_status": "partial",
  "can_answer": false,
  "missing_fields": ["refund_policy", "order_payment_status"],
  "confidence": 0.62,
  "summary": "订单存在，但缺少支付状态和退款规则，不能判断是否可退款。",
  "normalized_data": {
    "order_id": "123",
    "order_status": "shipped"
  },
  "next_action": "call_payment_status_tool",
  "raw_result_ref": "s3://trace/run_1/tool_result_3.json"
}
```

这样模型看到的不是一段模糊 JSON，而是明确的判断：工具成功，但语义不完整，不能直接下结论，下一步应该补查或追问。

核心是把“工具是否成功”和“结果是否足够回答问题”拆开。很多线上误判都来自模型把空数组、缺字段、默认值、部分结果理解成确定结论。例如库存接口返回空，可能是没权限、筛选条件错、数据延迟，也可能是真的没库存；中间层要把这些情况区分开。

**面试可以这样说：**

工具调用成功不代表结果语义完整，所以我会在工具和模型之间加一层 observation adapter。它先做 schema 校验和字段完整性检查，再结合当前任务判断结果是否足够支持下一步决策。比如接口 HTTP 200，但缺订单支付状态、退款规则或权限字段，就不能让模型直接判断“可以退款”。中间层会输出结构化 observation，包括 tool_status、semantic_status、missing_fields、confidence、summary、next_action 和 raw_result_ref。对于 partial、ambiguous、stale、conflict 的结果，要自动补查、追问或阻断高风险动作。这样模型拿到的是经过解释和标注的工具观察结果，而不是容易误读的原始返回。

## 27. 如果 RAG 召回了很多相互矛盾的文档，Agent 应该怎么处理？

**问题：** 如果 RAG 召回了很多相互矛盾的文档，Agent 应该怎么处理？

**答案：**

RAG 召回到互相矛盾的文档时，Agent 不能把所有内容混在一起让模型自己“综合一个答案”。这很容易产生幻觉，或者把旧规则和新规则拼成一个不存在的结论。

正确做法是先做证据治理，再生成答案：

- **版本过滤：** 优先保留 active、latest、effective 的文档，过滤 deprecated、expired、draft。
- **权限过滤：** 只保留当前用户有权限访问的文档。
- **来源分级：** 按权威性排序，比如制度文档 > 产品手册 > FAQ > 历史工单 > 用户评论。
- **时间判断：** 新版本通常优先，但要看 `effective_from` 和 `expires_at`，不是简单看更新时间。
- **冲突检测：** 对同一问题的不同结论做分组，标注 conflict。
- **重排降噪：** 把低相关、旧版本、重复和弱来源证据降权。
- **无法消解时说明不确定：** 不强行给唯一答案，要展示冲突来源或转人工。

可以把检索结果整理成结构化证据：

```json
{
  "answerability": "conflict",
  "conflict_type": "policy_version_conflict",
  "preferred_evidence": {
    "doc_id": "policy_2026",
    "version": "v3",
    "effective_from": "2026-01-01",
    "authority": "official_policy"
  },
  "conflicting_evidence": [
    {
      "doc_id": "faq_2024",
      "version": "v1",
      "status": "deprecated"
    }
  ],
  "next_action": "answer_with_latest_policy_and_cite_conflict"
}
```

如果能根据版本、时间、权威来源明确消解，就基于最高可信证据回答，并引用来源。如果无法判断哪个是权威，Agent 应该说“当前知识库存在冲突”，列出冲突点，建议用户确认来源或转人工，而不是编造一个确定结论。

**面试可以这样说：**

RAG 召回到互相矛盾的文档时，我不会直接把所有 chunk 塞给模型让它综合。会先在检索后处理层做证据治理：过滤无权限、过期、废弃和低可信文档；按版本、effective time、来源权威性和业务优先级排序；对同一问题的不同结论做 conflict 标注。如果能明确判断最新有效政策，就用最高可信证据回答并引用来源；如果无法消解，就明确告诉用户知识库存在冲突，展示冲突来源、时间和版本，必要时追问或转人工。核心原则是：证据冲突时不能强行合并，Agent 要先判断 answerability，再决定回答、追问还是拒答。

## 28. 你怎么设计 Agent 的失败恢复机制？

**问题：** 你怎么设计 Agent 的失败恢复机制？

**答案：**

Agent 的失败恢复不能只靠简单重试。因为 Agent 失败可能发生在意图识别、RAG、模型调用、工具调用、权限校验、状态写回、外部服务或用户中断任一环节。恢复机制要先分类，再决定重试、降级、补偿、追问、转人工还是终止。

**1. 先做失败分类**

常见失败类型：

- **模型失败：** 超时、限流、输出格式错误、工具参数生成失败。
- **检索失败：** 召回为空、证据冲突、索引不可用、权限过滤后无结果。
- **工具失败：** 超时、5xx、参数错误、权限拒绝、业务规则不满足。
- **状态失败：** checkpoint 写失败、状态冲突、并行结果合并失败。
- **安全失败：** prompt injection、越权工具调用、高风险动作未确认。
- **用户侧失败：** 用户取消、长时间不回复、输入冲突。

**2. 不同失败用不同恢复策略**

- **瞬时错误：** 限流、网络抖动、临时 5xx，可以指数退避重试。
- **参数错误：** 让模型修正参数，或回到槽位抽取节点重新生成。
- **证据不足：** query rewrite、多路检索、扩大召回，仍不足就追问或说明不确定。
- **权限失败：** 不重试，直接提示无权限或走授权流程。
- **高风险未确认：** 暂停在 checkpoint，等待用户确认。
- **写操作未知状态：** 先查外部系统真实状态，再决定跳过、补偿或重试。
- **多次失败：** 降级到人工、返回部分结果或安全终止。

**3. 必须依赖 state 和 checkpoint**

失败恢复要知道：

- 当前执行到哪个节点。
- 哪些步骤已经成功。
- 哪些工具已经产生外部副作用。
- 当前能否重试。
- 重试是否幂等。
- 是否需要用户或人工介入。

所以每个关键节点前后都要保存 checkpoint，工具调用要有 idempotency_key、tool_log、external_resource_version 和 trace_id。

**4. 恢复流程可以这样设计**

```text
捕获异常
  -> 标准化 error object
  -> 写入 run trace 和 task state
  -> 判断 error_type / risk_level / retryable
  -> 如果可重试：按策略重试
  -> 如果需要补偿：执行补偿或状态查询
  -> 如果信息不足：追问用户
  -> 如果高风险：暂停并等待确认
  -> 如果不可恢复：返回部分结果或转人工
```

**面试可以这样说：**

我设计 Agent 失败恢复时，不会只做统一 retry，而是先把失败分类。模型超时、工具 5xx、网络抖动属于瞬时错误，可以指数退避重试；参数错误可以回到参数生成节点；RAG 证据不足可以 query rewrite 或扩大召回；权限失败不能重试，要提示无权限；高风险动作没确认要暂停；写操作状态未知时要先查外部系统，避免重复执行。恢复机制一定依赖 task state、checkpoint、tool log 和幂等键，知道哪些节点已经成功、哪些工具产生了副作用、能不能安全重试。最终策略是：可重试就重试，可补偿就补偿，缺信息就追问，高风险就暂停，不可恢复就返回部分结果或转人工。

## 29. 怎么判断一个 Agent 该做成单 Agent，还是多 Agent？

**问题：** 怎么判断一个 Agent 该做成单 Agent，还是多 Agent？

**答案：**

判断单 Agent 还是多 Agent，不是看哪个概念更先进，而是看任务复杂度、权限边界、上下文隔离、并行收益和协调成本。

**更适合单 Agent 的情况：**

- 任务目标比较单一。
- 工具数量不多，权限边界简单。
- 上下文能放进一个模型窗口，不会互相干扰。
- 执行路径主要是线性的。
- 不需要多个角色互相审核。
- 失败恢复和状态管理比较简单。
- 成本和延迟要求高，不适合多轮多模型调用。

比如普通知识库问答、简单客服问答、单工具查询、固定流程表单填写，通常先用单 Agent 或 Agentic Workflow 就够了。

**更适合多 Agent 的情况：**

- 任务跨度大，一个 Agent 容易角色混乱。
- 需要明显不同的专业角色，比如规划、检索、代码、测试、安全审查。
- 工具权限差异大，需要隔离高风险工具。
- 上下文差异大，全部塞给一个 Agent 会噪声很重。
- 有可并行子任务，拆开能明显降低端到端时间。
- 需要交叉验证，降低单点幻觉和单点误判。
- 组织或系统边界天然分离，比如多个业务系统各有自己的 Agent。

但多 Agent 有额外成本：

- 通信成本。
- 状态同步。
- 任务分配。
- 结果合并。
- 失败恢复。
- 权限隔离。
- 可回放和评测复杂度。

所以我的判断标准是：如果单 Agent 加上明确状态、工具治理、权限控制和 workflow 约束已经能稳定解决，就不要过早拆多 Agent；只有当单 Agent 出现上下文过载、工具误用、角色混乱、权限难隔离、并行收益明显或需要独立审核时，再拆成多 Agent。

**面试可以这样说：**

我判断单 Agent 还是多 Agent，会先看单 Agent 能不能在清晰边界内稳定完成任务。如果任务目标单一、工具不多、上下文不复杂、流程基本线性，就优先做单 Agent，因为简单、低延迟、好排查。如果任务跨度很大，比如同时要做规划、检索、代码、测试、安全审查，或者不同工具权限差异很大、上下文互相干扰、子任务可以并行、需要独立审核，我才会拆成多 Agent。多 Agent 不是免费收益，它会带来通信、状态同步、结果合并、失败恢复和评测复杂度。我的原则是：先用单 Agent + Workflow/状态机/权限控制做到稳定，只有当分工收益明显大于协调成本时，才上多 Agent。

## 30. 什么是 Agent？它与普通 LLM 的本质区别是什么？

**问题：** 什么是 Agent？它与普通 LLM 的本质区别是什么？

**答案：**

Agent 可以理解成“以大模型为核心、能围绕目标自主规划、调用工具、维护状态并根据反馈持续执行的系统”。它不只是生成一段文本，而是能把用户目标拆成步骤，在执行过程中观察结果，再决定下一步。

普通 LLM 更像一个无状态的文本生成器：

```text
输入 prompt -> 输出文本
```

Agent 更像一个带执行闭环的系统：

```text
用户目标
  -> 理解意图
  -> 制定计划
  -> 调用工具 / 检索知识 / 查询状态
  -> 观察结果
  -> 更新状态
  -> 决定继续、追问、完成或失败恢复
```

两者的本质区别在于：

- **目标导向：** LLM 主要回答当前输入，Agent 围绕任务目标持续推进。
- **工具使用：** LLM 只生成文本，Agent 可以调用 API、数据库、搜索、RAG、代码执行等工具。
- **状态管理：** LLM 通常依赖上下文，Agent 会维护 task state、tool state、memory、checkpoint。
- **多步执行：** LLM 单轮生成，Agent 可以规划、执行、观察、再规划。
- **环境反馈：** Agent 会根据工具结果和外部状态调整行为。
- **工程约束：** Agent 需要权限、参数校验、失败恢复、审计、可观测和安全控制。

但要注意，Agent 不是“模型自己完全自由行动”。生产级 Agent 一般是模型负责理解、规划和生成，系统负责边界、状态、权限、工具执行、失败处理和评估。

**面试可以这样说：**

Agent 不是一个更长 prompt 的 LLM，而是一个围绕目标执行任务的系统。普通 LLM 主要是输入 prompt 后生成回答，而 Agent 会先理解用户目标，再做任务规划，必要时调用工具或 RAG，观察工具结果，更新 task state，然后决定下一步是继续执行、追问用户、完成任务还是失败恢复。它和普通 LLM 的本质区别在于有没有行动闭环：目标、计划、工具、观察、状态和反馈。生产里 Agent 不能完全靠模型自由发挥，还要有权限控制、参数校验、状态管理、checkpoint、审计和可观测，模型只是决策和生成的一部分。
